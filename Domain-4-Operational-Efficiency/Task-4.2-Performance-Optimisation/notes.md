Topic 1: Responsive AI Systems — Detailed Notes
1. Conceptual Framework: Actual vs. Perceived Latency
In generative AI architectures, latency must be analyzed through two distinct lenses:
Actual Latency (System Performance): The exact total execution time required for the system to process an incoming payload, invoke the foundation model, receive complete generated tokens, and deliver the final response back to the client.
Perceived Latency (User Experience): The subjective duration of time a user feels they are waiting before seeing meaningful progress or interaction from the application.
+-------------------------------------------------------------------------------+
| WITHOUT STREAMING (High Perceived Latency)                                    |
| [Request Sent] ------ 8 Seconds Spinner / Loading Bar -------> [Full Answer]  |
+-------------------------------------------------------------------------------+

+-------------------------------------------------------------------------------+
| WITH STREAMING (Low Perceived Latency)                                        |
| [Request Sent] -> [0.5s First Token] -> [Tokens Stream Continuously...] (8s) |
+-------------------------------------------------------------------------------+
2. Pre-computation and Caching Architectures
To eliminate unnecessary foundation model calls for static or predictable prompts, pre-computation shifts processing upstream.
User Request

     |

[ AWS Lambda ] ---> Check Cache / Store ---> [ DynamoDB / ElastiCache ] ---> Return ~10ms
     |                                              |
     | (If Cache Miss)                              | (If Cache Hit)
     v                                              v

Workflow:
Identify highly predictable queries (e.g., standard FAQs, product summaries, daily aggregate reports).
Pre-calculate outputs asynchronously using AWS Lambda.
Store results in a fast lookup store (Amazon DynamoDB or Amazon ElastiCache).
Incoming application requests execute direct key-value lookups instead of model invocations.
Latency Differential:
Model Invocation: ∼3,000 ms
Key-Value Store Lookup: ∼10 ms
Storage Comparison Matrix
Storage Service	Target Latency	Characteristics & Primary Use Cases
Amazon DynamoDB	Single-digit millisecond (<10 ms)	Persistent storage for larger datasets, structured metadata, persistent responses. Requires appropriate Read Capacity Units (RCUs) / Auto Scaling to avoid throttling.
Amazon ElastiCache (Redis OSS / Valkey)	Sub-millisecond (<1 ms)	In-memory key-value caching for extremely hot, frequently accessed model responses, query embeddings, and active user session states.
3. Latency-Optimized Bedrock Models
Mechanism: Amazon Bedrock provides optimized variants of specific Foundation Models tuned specifically for speed.
Trade-off: Directly trades off a small margin of generation accuracy/reasoning capability for significantly faster token generation rates.
Target Workloads: Time-critical or SLA-bound applications (e.g., live interactive voice assistants, clinical triage assistants, real-time chat support) where minimal latency is mandatory and slight quality concessions are acceptable.
4. Response Streaming (Perceived Latency Lever)
Mechanism: Utilizes HTTP chunked transfer encoding / Server-Sent Events (SSE) or WebSockets to stream tokens incrementally back to the client interface as they are generated by the model.
Impact Profile:
Actual Latency: Unchanged (e.g., total execution time remains 8 seconds).
Time-to-First-Token (TTFT): Reduced drastically from 8,000 ms to ≈500 ms.
Exam Rule: Streaming is the most cost-effective architectural pattern to drastically lower perceived latency without altering infrastructure scale or changing underlying model choices.
5. Parallelization via AWS Step Functions
When an architectural workflow requires multiple independent model invocations or tool calls, sequential processing creates additive latency bottlenecks.
Sequential Execution:
[ Task A (2s) ] ---> [ Task B (2s) ] ---> [ Task C (2s) ] = Total 6 Seconds

Parallel Execution (Step Functions Parallel State):
+---> [ Task A (2s) ] ---+
|                        |
+---> [ Task B (2s) ] ---+ ---> Total 2 Seconds
|                        |
+---> [ Task C (2s) ] ---+
Prerequisite: Operations must be strictly non-dependent (i.e., Task B does not require Task A's output payload as input context).
6. Systematic Benchmarking & Production Experimentation
To validate latency reduction strategies without impacting production performance, AWS provides specific measurement and deployment tools:
Amazon CloudWatch: Used for collecting operational performance metrics, tracking model latency distributions (p50,p90,p99), logging invocation errors, and observing API throttles.
CloudWatch Evidently: Built specifically for feature flagging and A/B testing/experimentation.
Allows statistical hypothesis testing to compare model variants, latency optimizations, and prompt designs in live production traffic with statistical significance.
Exam Key Distinction:
AWS AppConfig: Best used for feature flag deployments, configuration management, and progressive rollout schedules.
CloudWatch Evidently: Best used for quantitative experimentation, A/B testing, and statistical comparison of performance/latency metrics across user segments.



Topic 2: Retrieval Performance — Detailed Notes
1. Vector Index Algorithms: HNSW vs. IVF
Vector search performance directly influences Retrieval-Augmented Generation (RAG) system latency and accuracy. Choosing the correct vector indexing algorithm involves balancing latency, memory footprint, recall accuracy, and index build time.
HNSW (Graph-Based Structure):
Layer 2 (Coarse Nodes)   :  [ A ] -----------------------> [ B ]
                              |                              |
Layer 1 (Medium Nodes)   :  [ A ] --------> [ C ] --------> [ B ]
                              |              |               |
Layer 0 (Dense Fine Nodes): [ A ]->[ D ]->[ C ]->[ E ]---->[ B ]
(Descends through layers to rapidly pinpoint nearest neighbors)

IVF (Cluster-Based Structure):
Dataset Vectors ---> Partition into Voronoi Clusters (Centroids)
Query Execution ---> Find Nearest Centroids ---> Search strictly within those clusters
Algorithm Comparison Matrix
Feature / Metric	HNSW (Hierarchical Navigable Small World)	IVF (Inverted File Index)
Structure Type	Multi-layer proximity graph	Cluster-based partitioning (Voronoi cells)
Search Speed	Extremely fast (sub-millisecond lookups)	Fast, proportional to the number of clusters searched
Recall / Accuracy	Very high recall	Slightly lower recall compared to HNSW
Memory Consumption	High (RAM-intensive) due to edge graph storage	Low to moderate (memory efficient)
Index Build Speed	Slower to construct	Faster index creation
Optimal Use Case	When high speed + maximum recall are mandatory and sufficient RAM is allocated.	Extremely large datasets where memory constraints exist.
2. HNSW Tuning Parameters
Optimizing HNSW requires fine-tuning parameters that govern index build behavior versus runtime search speed.
Build Phase Parameters (m,ef_construction)⟶Affects Index Construction Time & RAM
Query Phase Parameter (ef_search)⟶Affects Runtime Search Latency & Recall
Parameter	Execution Phase	Effect of Increasing Parameter Value
m	Build	Controls maximum outgoing connections per graph node. Increasing m improves recall but significantly increases memory usage and slows index creation.
ef_construction	Build	Controls size of the dynamic candidate list evaluated during index construction. Increasing it improves index quality/recall, but slows index build time. Has zero impact on query search speed.
ef_search	Query / Runtime	Controls candidate list evaluated during vector lookup. Increasing it improves recall accuracy, but increases search latency (slower query processing).
3. Hierarchical Indices and Query Preprocessing
Hierarchical Vector Indices: Utilizes a coarse-to-fine routing strategy. Top-level vector indices route queries to high-level domain categories, while lower-level indices perform precise similarity matching within specific sub-domains.
Query Preprocessing Pipeline (AWS Lambda): Executing query transformation upstream of the vector database prevents expensive vector misses and reduces retry loops:
Normalization: Standardizing text formatting, casing, and removing stop-words.
Query Expansion / Decomposition: Expanding acronyms or breaking multi-part complex prompts into smaller sub-queries using Bedrock models.
Spelling & Syntax Correction: Resolving typos prior to embedding generation to avoid bad vector projections.

Topic 3: Throughput Optimisation — Detailed Notes
1. Throughput vs. Latency Trade-offs
In production Generative AI deployments, throughput and latency often exist in direct tension:
Latency: The elapsed time required to process a single discrete request from invocation to completion (time/request).
Throughput: The total volume of transactions or tokens the architecture processes within a given timeframe (requests/second or tokens/second).
Core Trade-off: Strategies that maximize total system throughput—such as batching multiple prompts together—frequently increase individual per-request latency. Conversely, optimizing purely for single-request speed often leads to resource under-utilization and lower throughput capacity.
2. Token Processing and Workload Batching
Token Efficiency: In Task 4.1, token reduction was driven by cost containment. In Task 4.2, token minimization directly enhances performance: shorter prompt inputs and bounded completion outputs execute faster, freeing system concurrency capacity to serve more total requests.
Batch Inference Architecture: For non-interactive, asynchronous workloads (e.g., nightly document summarization, offline embeddings processing), synchronous model calls are replaced with batch inference.
Decoupling with Amazon SQS: High-volume ingress traffic is routed through Amazon Simple Queue Service (SQS) buffers to smooth out peak load spikes and form micro-batches before hitting foundation model endpoints.

3. Concurrent Invocation Control & Throttling Mitigation
Uncontrolled, unlimited parallel calls to foundation model APIs trigger HTTP 429 (Too Many Requests) throttling exceptions, leading to exponential backoff retries and severe overall performance degradation.
UNCONTROLLED PARALLELISM:
[ 100 Parallel Calls ] ---> [ Model Endpoint ] ---> HTTP 429 Throttling Error ---> System Latency Spikes

CONTROLLED CONCURRENCY (Step Functions Map State):
[ 100 Requests ] ---> [ Step Functions Map State ]
                             |
                             +---> MaxConcurrency: 10
                             |
                             v
                     [ 10 Calls Executing ]  (90 Requests Waiting Safely in Queue)
Step Functions MaxConcurrency: When orchestrating parallel model processing using AWS Step Functions Map state, MaxConcurrency caps the maximum active parallel executions (e.g., MaxConcurrency: 10). Remaining executions wait safely in state queue buffers rather than failing due to endpoint throttling.
Resilience Patterns: Combines rate limiting, token-bucket controls, and exponential backoff with jitter to maintain continuous throughput at maximum quota capacity without breaching service limits.
4. Request Prioritisation & Priority Queuing
During high-demand peak traffic, critical business transactions must not be blocked by low-priority asynchronous tasks.
Ingress Payload
       |
       v
[ API Gateway / Application Router ]
       |
       +---> High-Priority Message Attribute ---> [ SQS Priority Queue ] ---> Fast-Track Processing
       |
       +---> Low-Priority Message Attribute  ---> [ SQS Standard Queue ] ---> Batched / Throttled
Implementation Pattern: Dual SQS queues or SQS Message Attributes are configured to establish emergency/high-priority pathways.
Worker processes drain high-priority queues first, ensuring strict SLAs for critical user-facing requests while lower-priority workloads wait for available throughput capacity.


Topic 4: FM Parameter Tuning — Detailed Notes
1. Foundation Model (FM) Hyperparameters
Foundation model parameters control generation behavior, output variability, token selection constraints, and overall token generation dynamics.
Parameter	Control Scope	Operational Impact
Temperature	Randomness (0 to 1)	0 produces deterministic, highly repeatable outputs. 1 produces highly creative, diverse, and unpredictable token generations.
Top-K	Fixed Token Count	Restricts token selection to the top K most probable candidates (e.g., K=50 always considers 50 candidates regardless of probability distribution confidence).
Top-P	Nucleus Sampling Probability Mass	Dynamically samples from the smallest set of tokens whose cumulative probability exceeds threshold p (e.g., p=0.9).
2. Top-K vs. Top-P Mechanics
Top-K (Fixed): Maintains a rigid count limit. If the model is extremely certain or highly uncertain, it strictly limits choices to K tokens.
Top-P (Adaptive): Adjusts dynamically based on model confidence:
High Confidence: The model requires only a few tokens to reach 90% cumulative probability → fewer candidate choices.
Low Confidence: The model spreads probability across many plausible tokens to reach 90% → wider candidate pool.
Exam Golden Rule: Tune either temperature or top-p, but never both simultaneously, as they interact to skew the probability distribution in unpredictable ways.
3. Tuning Workflow
Systematic configuration testing ⟶ Evaluation via Model Evaluation frameworks ⟶ Production A/B testing via CloudWatch Evidently ⟶ Optimum parameter adoption. Specialized use-case prompt templates may require distinct, isolated parameter profiles.
Topic 5: Efficient Resource Allocation — Detailed Notes
1. Why GenAI Workloads Differ from Traditional Applications
Generative AI applications present unique infrastructure challenges that break conventional FinOps patterns:
Significant compute (GPU/ASIC) and memory requirements.
Highly variable inference latency under peak demand.
Strict throughput and quota limits tied to provider tokens-per-minute (TPM) and requests-per-minute (RPM).
2. SageMaker Inference Recommender & Provisioned Throughput
SageMaker Inference Recommender: An automated tool that executes systematic load tests across diverse instance configurations to recommend the optimal instance type, balancing cost-effectiveness and performance across real-time and serverless deployment options. It replaces guesswork with empirical data.
Provisioned Throughput: Dedicated, reserved infrastructure providing stable, guaranteed throughput capacity exceeding standard on-demand quotas. Cross-region inference profiles can be used to distribute high demand across multiple AWS regions.
3. GenAI-Specific Utilization Monitoring
Traditional application monitoring focuses primarily on CPU and memory utilization. GenAI monitoring requires tracking domain-specific metrics:
Token Length Monitoring: Tracking input prompt lengths and output completion token counts, as token volume is the primary driver of infrastructure utilization and latency.
Idle Period Detection: Identifying periods of low activity to scale down or suspend expensive endpoints.
SageMaker Model Monitor: Continuously monitors deployed model endpoints for data drift and output quality degradation.
4. Autoscaling & Predictive Scaling Architectures
Predictive Scaling: Anticipates traffic spikes using historical usage data and scheduled events (e.g., financial market open and close times). Reactive scaling is insufficient for GenAI workloads because spinning up GPU instances takes time, causing requests to time out before capacity arrives.
Request Queuing: Placing an architectural buffer (such as Amazon SQS) between the client application and the model endpoint prevents request denial under strict throughput constraints.

5. Hardware Acceleration
Amazon EC2 Inferentia: Purpose-built AWS silicon chips optimized specifically for deep learning inference workloads. They offer significantly higher cost-efficiency and lower latency than general-purpose GPUs for model serving. (Note: AWS Trainium is the dedicated counterpart designed for model training).


Topic 6: System Performance Optimisation — Detailed Notes
1. API Profiling with AWS X-Ray
Mechanism: AWS X-Ray traces incoming API requests through the entire microservices architecture down to foundation model invocations.
Focus Area: Building on Task 2.4's subsegments and annotations, X-Ray in Task 4.2 is used specifically to profile prompt-completion patterns—identifying which prompt shapes, token lengths, or tool-calling sequences introduce latency bottlenecks.
2. Log Analysis & Insights
Amazon CloudWatch Insights: Used to query and analyze massive volumes of application logs and API call patterns.
Objective: Uncover systemic inefficiencies, recurring throttling patterns, or sub-optimal payload structures across distributed inference pipelines.
3. Edge Caching and Intelligent Routing
To minimize global latency and route requests efficiently across distributed client bases:
Amazon CloudFront: Deployed at edge locations to cache static or semi-static model outputs, reducing origin round-trips for repetitive global queries.
Amazon API Gateway: Provides efficient request routing, rate limiting, and payload validation before requests reach backend orchestration services.
CloudWatch Dashboards: Real-time operational dashboards tracking latency percentiles (p50,p90,p99), error rates, and throughput metrics.
