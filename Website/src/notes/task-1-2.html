FM Selection & Lifecycle — Cheat Sheet

End-to-end architectural lifecycle notes, worked through a healthcare document analysis scenario: model selection criteria, HIPAA-safe dataset prep, LoRA fine-tuning mechanics, the three-tier evaluation gate, and production drift monitoring. No Build Log yet for this task — notes only, taken ahead of building it.

Step 1 · Model Selection & Capability Filtering

Define metrics first
Compliance, medical boards, and engineering leadership set strict thresholds before testing any models, to prevent post-hoc bias.
Key healthcare metrics
PHI detection >99% (mandatory for HIPAA), medical accuracy >90%, JSON validity >95% (EHR integration), p95 latency <3s, cost/document <$0.02.
Capability filtering (pre-benchmarking)
Hard technical cutoffs before any scoring: multimodal support (scanned PDFs/handwriting/images → text-only models auto-fail) and a large context window (100k+ tokens, for a 50-page patient history in one call).

Step 2 · Dataset Prep & HIPAA Security

Human-in-the-loop, JSONL on S3
Clinicians + data engineers curate 100–300 high-quality pairs (de-identified prompt + ideal referenceResponse) in JSON Lines format.
Prompting vs. fine-tuning
Few-shot prompting burns tokens/latency every call and risks being ignored; fine-tuning burns the structural style into the model once, for minimal prompt overhead in production.
HIPAA & PHI compliance
Names/SSNs/addresses de-identified before touching S3 or training pipelines; S3 datasets encrypted with KMS to maintain BAA compliance.

Step 3 · LoRA Mechanics

The "deck extension" analogy
Full fine-tuning alters billions of parameters — heavy, slow, expensive. LoRA doesn't.
Base model (the house)
Completely frozen and untouched — core capabilities and safety guardrails preserved.
Adapter (the deck)
A tiny trainable layer (<1% of model size), attached and trained on the JSONL medical dataset to master clinical JSON formatting.
Benefit
Modular, fast, cheap — swap the adapter without rebuilding the base model.

Step 4 · The Three-Tier Evaluation Gate

Tier 1 — automatic (fast, cheap)
BLEU (word-overlap precision) + ROUGE (reference-coverage recall) + JSON schema validators. Checks syntax/word-matching, not meaning — filters 15–20 candidate models down to a shortlist.
Tier 2 — LLM-as-a-judge
A high-end judge model (e.g. Claude 3.5 Sonnet) checks semantic correctness, clinical logic, hallucinations against a strict rubric.
Tier 3 — human clinical sign-off
Hospital doctors / domain experts do the final, non-negotiable regulatory review.

Exam trap

Latency (p95) and cost are not part of model evaluation. Evaluation tests quality/accuracy only — speed and expense need separate load-testing scripts and CloudWatch metrics (InvocationLatency, token counts).

Step 5 · Adversarial Testing & Drift Monitoring

Adversarial testing (red teaming)
Feed tricky/contradictory inputs (e.g. a contradicted patient history mid-note) to check whether the model tracks shifting updates or falls into the trap.
Slice & OCR failure analysis
Test performance separately on messy scanned documents / heavy medical abbreviations vs. clean text — aggregate accuracy can hide a failing slice.
Failure mode & data drift
Proactively watch for JSON parsing crashes (e.g. markdown breaking the EHR parser), clinical hallucinations, confidence drops, and drift from real-world change (new medications, billing codes, shifting doctor shorthand) months after deployment.
AWS tooling
CloudWatch tracks error rates and triggers SNS alarms on JSON failure-rate spikes; low-confidence outputs route to human clinicians for review (feeding a retraining loop).
