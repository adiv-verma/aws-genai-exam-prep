What each task is actually about

One line each, then the few things most worth remembering.

4.1

Cost Optimization & Resource Efficiency

Paying for the answer you need, and not for the one you don't.

  • You are billed twice, unevenly. Input tokens and output tokens are charged separately, and output costs more per token. Capping the answer is the cheapest change you can make.
  • Model choice beats everything else. Prompt work and caching get you 10–20%. Routing the easy questions to a smaller model gets you up to 80%.
  • Summarising can cost more than it saves. A summary is itself a model call. It only pays off if the summary gets reused — summarise once, read many times.
  • Quality bar first, then price. Pick the cheapest model that clears the bar, not the best model you can afford. 89% at a fifth of the price usually wins.
  • Not real-time? Batch it. Bedrock Batch is roughly half price for work that can wait, like overnight description generation.

4.2

Performance Optimisation

Making it quick, and — separately — making it feel quick.

  • Streaming changes nothing and everything. The job still takes eight seconds. The user sees the first token in half a second, and that is the number they remember.
  • The fastest model call is the one you skip. Pre-compute predictable answers and read them back in milliseconds instead of seconds.
  • Parallel only works if the steps are independent. Three two-second calls become two seconds — unless B needs A's output.
  • Throughput and latency pull against each other. Batching serves more people and makes each of them wait longer. Pick which one the workload needs.
  • Scale before the spike, not during it. GPU instances take too long to start for reactive scaling; requests time out before the capacity lands.
  • Tune temperature or top-p, never both. They interact and the result stops being predictable.

4.3

Monitoring

Noticing that the answers got worse, before a customer does.

  • Every dashboard can be green while the model lies. CPU, memory and HTTP 200s say nothing about whether the answer was right.
  • Trace the prompt, not just the request. When the answer is wrong you need to know whether retrieval, a tool, or the model itself caused it.
  • The logs you need are off. Bedrock model invocation logs are disabled by default — and once on, they hold full prompts and responses, so PII becomes your problem.
  • Hallucination has to be made into a metric. Nothing ships it out of the box. A second model marks answers against a golden set, and that score is what the alarm watches.
  • HTTP 200 is not success. If the user clicks “talk to a human” straight after the answer, the request succeeded and the system failed.
  • A cost spike is a bug report. Runaway agents, recursive loops and denial-of-wallet attacks all show up on the bill first.

Why the same thing keeps coming up

Domain 4 reuses a small set of levers across all three tasks. The lever is the same; the reason for pulling it is what changes — and that reason is usually what the exam is testing.

Tokens, for three different reasons
4.1 cuts tokens because they are the bill. 4.2 cuts the same tokens because shorter prompts execute faster and free up concurrency. 4.3 watches token counts because a sudden 10× spike means context leakage or an agent stuck in a loop.
Batching, a cost feature and a throughput feature
4.1 uses Bedrock Batch for the ~50% discount on offline work. 4.2 uses runtime request batching to keep the GPU busy — which raises throughput and raises per-request latency at the same time.
Caching, at four different distances
4.2 keeps pre-computed answers in ElastiCache and DynamoDB, and hot query embeddings in the retrieval layer. Both exist to avoid a model call you have already paid for once.
Chunking, asked three ways
Task 1.5 chunks for retrieval quality. 4.1 chunks to minimise cost. 4.2 picks the index — HNSW or IVF — for latency and memory. Same corpus, three different questions.
CloudWatch, doing four jobs
4.1 segments token spend by query type. 4.2 tracks latency percentiles and runs A/B tests through Evidently. 4.3 holds the custom quality metrics and anomaly detection, and 4.3 again adds RUM for what the browser actually rendered.
Stopping conditions, cost and correctness at once
4.1 caps agent loop iterations to stop runaway spend. 4.2 caps concurrency to stop HTTP 429 throttling. 4.3 alarms when a tool that normally fires 100 times a day fires 5,000 — the same failure, caught from the other end.
Technical numbers vs. the numbers anyone asks for
4.3 is blunt about it: latency dropping from 2.0s to 1.8s matters to engineering. “Escalation rate down 20%” is what proves the system was worth building. Put both on the same dashboard.

Coming from the other maps? Domain 1 builds the system — documents in, answer out. Domain 2 puts that system inside a company and keeps it running. Domain 3 keeps it out of trouble. Domain 4 is what you do once it is live and someone is paying for it: make it cheaper, make it quicker, and be able to tell when it quietly stops being either.
