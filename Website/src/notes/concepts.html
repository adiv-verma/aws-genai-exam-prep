Cross-Domain Reference

One Concept, Every Place It Appears

Some ideas turn up in a dozen tasks. That is not repetition — each task uses the same thing for a different job, and knowing which task owns the detail is half the battle. Every entry below names the one page to read, then says what each other task adds, and why it differs there. Built from all 20 sets of notes. Start with the whole map if you want the shape first.

Group A

Data & retrieval

The RAG spine. Everything here is about getting the right few paragraphs in front of the model.

Chunking

5 of 20 tasks #
The detail lives here 1.5 · Document Segmentation

Four strategies — fixed-size, structure-aware, hierarchical parent–child, semantic — plus Bedrock Knowledge Bases’ five options including Lambda custom chunking, the ~10% boundary overlap, and the exam rule: chunking strategy is chosen per document type, never applied uniformly across a corpus.

  • 4.1
    For cost, not retrieval quality. Too large and you pay input tokens for noise; too small and you need more chunks, adding prompt overhead. The notes flag this 1.5-vs-4.1 split explicitly.
  • 5.2
    As the actual bug. Fixed-size chunking decoupled research findings from their methodology, so a finding arrived without its constraints. Fix: structure-aware chunking preserving [Methodology] + [Findings] + [Conclusions].
  • 2.5
    A different thing with the same name. Request chunking and recursive summarization fit an oversized prompt inside a token window. Nothing to do with indexing a corpus.
  • 4.3
    Hygiene before indexing. Glue and Data Wrangler clean data before embedding, because once flawed text is in vector space, filtering it back out is brutal.

Embeddings & dimensionality

6 of 20 tasks #
The detail lives here 1.5 · Embedding Solutions

Titan at 1,536 dimensions (V2 also offers 1024/512/256), dense vs sparse, binary embeddings and FP16 quantization for ~32× storage reduction, domain-vocabulary traps (“consideration”, “party”), and the golden rule: the same embedding model must serve both ingestion and query, or the vector space shifts and the corpus needs a full rebuild.

  • 5.2
    Drift and domain misalignment. Diagnosed by projecting vectors with SageMaker and looking at the clustering. Its verdict is the sharp one: domain fit matters more than dimensionality.
  • 3.2
    Redact before you embed. Once PII is inside vector coordinates it is mathematically opaque and cannot be cleanly deleted.
  • 3.1
    Embeddings reused to verify, not retrieve. Embed the generated answer, compare it against the source chunks; low similarity means the model fabricated.
  • 2.2
    The embedding cache. A separate cache from the response cache, so repeated phrasings never re-invoke the embedding model.
  • 4.1
    The economics that make caching work. Generating an embedding is negligible next to an LLM call — which is the whole basis of semantic caching.

Vector store selection

6 of 20 tasks #
The detail lives here 1.4 · Core Vector Store Architecture

Bedrock KB for managed public data, OpenSearch + neural plugin for confidential and hybrid, RDS + S3 + custom store (metadata pre-filter → vector math → raw file fetch), DynamoDB for live flags — plus sharding, parallel fan-out, and access control evaluated before vector math runs.

  • 1.1
    The decision matrix and its hard rule. OpenSearch Serverless is mandatory for SaaS connectors (SharePoint, Salesforce, Confluence). Also S3 Vectors at scale, Aurora pgvector for existing Postgres, Neptune Analytics for GraphRAG multi-hop.
  • 1.5
    Multi-tenant shapes. Silo / pool / bridge, with the warning that pool-model tenant filters must live in the query layer and never in client code.
  • 4.3
    Operating one, years in. Index fragmentation, query-latency drift, and snapshot restore (minutes) versus re-embedding the whole corpus (hours and full inference cost).
  • 4.2
    Tuning the index you picked. HNSW parameters and the coarse-to-fine hierarchical index.
  • 5.2
    Choosing between four algorithms. See the next entry.

ANN index algorithms

2 of 20 tasks #
The detail lives here 5.2 · ANN Algorithm Selection

The four-way comparison: LSH (fastest, lowest recall), HNSW (best speed-to-accuracy, memory-hungry), IVF (scalable, moderate memory), PQ (lossy compression, tiny footprint) — and the conclusion that there is no best one; benchmark against your own dataset and SLA.

  • 4.2
    How to tune the one you chose. m and ef_construction affect build time and RAM; ef_search affects query latency and recall. The trap: ef_construction has zero effect on query speed.

Hybrid search (dense + BM25)

4 of 20 tasks #
The detail lives here 1.5 · Advanced Search Architectures

Why both are needed — dense for concepts, sparse for statute codes and proper nouns — configured via OverrideSearchType = HYBRID, with the constraint that the underlying store must support hybrid scoring.

  • 1.4
    The worked example. “Section 10b-5” needs keyword matching; “fraudulent stock market practices” needs semantic. One query wants both.
  • 4.2
    Hybrid feeding a custom reranker. Final Score = Relevance·w₁ + Recency·w₂ + Authority·w₃ — because the closest match can still be stale or low-authority.
  • 5.2
    Hybrid as the prescribed fix. What you reach for when retrieval returns irrelevant results and exact codes (ICD-10) keep getting missed.

Reranking & two-stage retrieval

3 of 20 tasks #
The detail lives here 1.5 · Two-Stage Retrieval with Rerankers

Stage 1 retrieves the top ~100 cheaply; stage 2 reranks to the top 10 with cross-attention. The reason is arithmetic: running cross-attention across 15 million documents is computationally impossible, so you pay for precision only on a shortlist.

  • 4.2
    Reranking as weighted domain logic. Recency and authority enter the score, not just semantic relevance.
  • 2.5
    Dynamic RAG. Scale k by query complexity — k=3 for simple, k=20 for multi-faceted — then cross-encoder rerank.

Query expansion & decomposition

3 of 20 tasks #
The detail lives here 1.5 · Query Handling Systems

Expansion adds alternative terminology for up to +23% recall; decomposition splits a multi-part question into independent sub-queries run in parallel through Step Functions for up to −40% latency.

  • 4.2
    A fuller preprocessing pipeline. Normalization, stop-word removal and spelling correction upstream of the vector DB — typos produce bad vector projections before expansion even matters.
  • 5.2
    Model-driven rewriting as a fix. Expanding physician queries with domain synonyms and acronyms when retrieval precision stays stubbornly low.

Metadata & filtering

4 of 20 tasks #
The detail lives here 1.4 · Metadata Frameworks

Taxonomies and structured attributes, AI-powered tagging at ingestion, and the example that shows why metadata beats similarity: a case matches the query 100% semantically, but the relationship graph says it was overturned on appeal, so the framework blocks it.

  • 1.5
    The timing constraint. Metadata must be attached during chunking. Adding it after vectors are stored requires a full, costly re-ingestion.
  • 3.3
    The same tags as governance. DataSensitivity, RegulatoryScope, Jurisdiction — driving tag-based access control, with SCPs denying creation of untagged resources outright.
  • 2.5
    Metadata extraction as a managed service. Q Business tagging documents by claim type and coverage category instead of you wiring it.
Group B

Model choice, routing & money

Which model answers, how the request gets to it, and what that costs.

Model cascading

5 of 20 tasks #
The detail lives here 4.1 · Cost-Effective Model Selection

The tiered-routing vs cascading table, model choice named as the single largest cost lever (up to 80%, where prompt work and caching give 10–20%), and the discipline: set the quality bar first, then buy the cheapest model that clears it.

  • 2.2
    Framed as cost. A small model answers ~80% of queries. The honest trade-off: escalated queries cost two calls and more latency, so cascading only pays if most queries really are simple.
  • 2.4
    Framed as routing. Confidence 0.7–0.9 triggers escalation, and intermediate findings are passed forward so the big model does not restart from nothing.
  • 2.1
    As a fallback inside dynamic selection. Model chosen at runtime from performance history, budget and throttling status — worth −42% response time.
  • 2.3
    Centralised. The GenAI Gateway owns cascading and failover once, for every team, instead of each team rebuilding it.

Confidence thresholds

8 of 20 tasks #
The detail lives here 2.1 · Collaborative AI Systems

The escalation ladder: >0.9 fully automated, 0.7–0.9 automated with asynchronous human review, <0.7 synchronous approval before anything executes — with Step Functions wait tokens holding state rather than terminating.

  • 2.4
    The same band gating a different thing. 0.7–0.9 decides whether to escalate to a bigger model, not whether a human sees it.
  • 2.5
    80–90% for critical decisions. Plus the UI requirement: visually separate AI-generated from human-verified so the adjuster can decide what to trust.
  • 1.6
    Below 0.70, ask rather than escalate. Comprehend intent confidence under threshold triggers a clarification question, because guessing between Wire, ACH and SEPA invents advice.
  • 3.1
    High / medium / low as output routing. Answer directly, answer with a compliance disclaimer, or block and flag for human review.
  • 3.3
    Confidence weighted by source reliability. Recommendations built on unverified data are programmatically assigned lower scores.
  • 3.4
    Where the number actually comes from. Token log-probabilities, ensemble disagreement, and calibration — a “90% confident” answer should be right 90% of the time.
  • 1.2
    Confidence drops as a tracked failure mode. Monitored in production alongside JSON crashes and clinical hallucinations.

Provisioned Throughput vs On-Demand

4 of 20 tasks #
The detail lives here 4.1 · Provisioned Throughput Break-Even

Break-even analysis. Buy provisioned capacity only when total on-demand token spend exceeds the Model Unit commitment; below that you are buying idle capacity. Under-utilised PMUs waste money, over-utilised PMUs cause 429s.

  • 2.2
    The sizing formula and the lock-in. Peak requests/sec × average tokens/request → required TPS → Model Units — on a 1- or 6-month term you are billed for even if traffic collapses.
  • 4.2
    The same purchase for a throughput reason. Guaranteed capacity above on-demand quotas, plus cross-region inference profiles to spread demand.
  • 3.2
    Provisioned vs on-demand as a permission. IAM can restrict which feature a role may use, not just which model.

Batch inference vs request batching

3 of 20 tasks #
The detail lives here 4.1 · Disambiguating “Batching”

The distinction the exam leans on. Bedrock Batch Inference is a cost feature — offline, roughly 50% cheaper. Request batching is a throughput feature — grouping concurrent calls on the GPU at runtime. Same word, unrelated mechanisms.

  • 4.2
    Batching plus SQS micro-batches. And the honest tension: batching serves more people while making each of them wait longer.
  • 2.2
    Continuous batching as a necessity. Static batching starves the GPU on LLM workloads; Batch Transform exists as its own endpoint type for offline bulk.

Caching — five different caches

6 of 20 tasks #
The detail lives here 4.1 · Intelligent Caching Systems

Semantic caching at 85–95% similarity (70% returns answers to questions nobody asked; 99% degenerates to exact-match), result fingerprinting by deterministic hashing, prompt caching at ~90% off the static prefix only if the static part comes first, and L1/L2/L3 tiering. A hit rate under 5% means the cache costs more than it saves.

  • 2.2
    Two caches, different keys. Embedding cache stores text→vector; response cache stores query→final answer. Conflating them is the mistake.
  • 2.3
    Caches stacked, and invalidated. Across API Gateway, ElastiCache and the database — with TTL, event-driven purge and write-through as the three invalidation mechanics.
  • 2.5
    The client-side one. Matching at 85–95% similarity in the browser rather than on exact text.
  • 4.2
    Pre-computation as a cache. A ~3,000 ms model call becomes a ~10 ms key-value lookup for predictable questions.
  • 1.4
    A query cache for hot content. Standard statutes and boilerplate clauses served without touching compute.

Token economics

6 of 20 tasks #
The detail lives here 4.1 · Token Efficiency Systems

Billed twice and unevenly — output costs more per token than input. Pre-call counting for cost prediction and context-limit validation; context pruning (drop 30% of noise, pay 30% less); max_tokens as the cheapest single change you can make; “lost in the middle” so critical instructions go first; and summarise once, reuse many times, because a summary is itself a model call.

  • 2.5
    Fitting a conversation into the window. Token windowing, recursive summarization, and prompt-chaining reduction by compression, summarization or key-information extraction — the last being most reliable, since summaries drift.
  • 4.2
    The same reductions for speed. Shorter prompts and bounded outputs execute faster and free concurrency for other requests.
  • 4.3
    A 10× token spike as a bug report. Context leakage from over-stuffed windows, or an agent looping.
  • 5.2
    The failure mode nobody is warned about. Context overflow causes silent truncation — no error is raised, the model drops trailing context and answers confidently anyway. An 8,000-token wall hit only by specific document types.
  • 3.4
    Token count as a fairness signal. Systematically shorter output for one demographic is the proxy metric for completeness bias.
Group C

Prompting & output control

Making a probabilistic system produce something you can rely on and audit.

Chain-of-Thought

4 of 20 tasks #
The detail lives here 1.6 · Enhancing FM Performance

Why it works, mechanically: models generate tokens sequentially, so forcing the reasoning out first puts each step into working memory for the next. Demanding an immediate answer squeezes the whole calculation into one generation step. Plus the auditability benefit — the chain is logged even when hidden from the customer.

  • 2.1
    Workflow CoT instead of prompt CoT. Each reasoning step is a separate call persisting to state, so a failure at step 4 does not destroy steps 1–3. Worth +37% decision quality.
  • 3.4
    The opposite UI decision from 1.6. Show the reasoning. Transparency outranks simplicity when a clinician needs to check the logic before acting on it.
  • 5.2
    CoT as a diagnostic instrument. Make the model show its work, then read the chain to find exactly where the logic broke.

Prompt versioning & rollback

5 of 20 tasks #
The detail lives here 1.6 · Prompt Management and Governance

A prompt is a code artifact: changing one line is deploying new production logic. Bedrock Prompt Management versions them, and rollback is a pointer move from v8 back to v7 in seconds with no redeploy. Three-tier approval (author → compliance → admin) with separation of duties so nobody ships their own prompt.

  • 5.2
    Rollback on a threshold, automatically. v6 91% → v7 94% → v8 88% → auto-revert to v7, with no human in the decision.
  • 2.5
    The registry as a debugging tool. Latency spiked because v8, shipped yesterday, doubled the prompt length. The registry is what makes that a two-minute diagnosis.
  • 3.4
    The same discipline for guardrails. Guardrail JSON, prompt templates and evaluation rubrics all version-controlled and deployed through IaC.
  • 3.3
    Versioning for reproducibility. Same model version plus same data version must reproduce the same output, years later.

Golden datasets & regression testing

4 of 20 tasks #
The detail lives here 1.6 · Quality Assurance Systems

The v7-vs-v8 table that makes the point concrete: Joint Accounts improved 62% → 94%, but International Transfers fell 91% → 73%, so the pipeline blocked the deploy. Fixing one scenario routinely breaks another, and only a fixed dataset catches it.

  • 5.1
    The same gate, as CI/CD enforcement. Automated thresholds in CodePipeline produce a hard RELEASE BLOCKED state — plus the rule that changing the eval dataset makes v7 and v8 scores statistically non-comparable.
  • 3.1
    Golden datasets pointed at accuracy. Automated regressions against known-good banking answers, reusing the 1.2 and 1.6 patterns.
  • 4.3
    What turns hallucination into an alarm. A second model marks answers against the golden set, and that score is the metric CloudWatch watches.

Temperature, top-p, top-k

4 of 20 tasks #
The detail lives here 4.2 · FM Parameter Tuning

The full parameter table and the mechanic that matters: top-k is a fixed count regardless of how certain the model is; top-p is adaptive — few candidates when confident, a wide pool when not.

  • 1.3
    Why regulated work locks 0.0–0.2. The same claim assessed tomorrow must reach the same financial conclusion. And the golden rule stated plainly: tune temperature or top-p, never both — the effects overlap and you can no longer debug why behaviour shifted.
  • 3.4
    The same knobs as policy controls. Listed as in-processing enforcement alongside reasoning monitoring.
  • 5.1
    Parameters as the A/B subject. Comparing prompt variations, temperature and top_p is the worked example of comparative analysis.

JSON Schema & structured output

5 of 20 tasks #
The detail lives here 1.6 · Model Instruction Frameworks

Text instructions ask; schema enforces. Models stay probabilistic, so marking disclaimer as a required field is what makes legally mandated text structurally impossible to drop — where a prompt only makes it likely.

  • 3.1
    A failure mode similarity cannot catch. Schema rejects a syntactically perfect response carrying a 150% interest rate. Conversely semantic similarity catches perfect JSON full of invented rules. Different layers, different blind spots.
  • 1.2
    JSON validity as a hard gate. >95% required, and the real-world break: the model appends ```json fencing and the downstream EHR parser dies instantly.
  • 2.4
    Schema validation before a token is spent. API Gateway request validators enforce max_tokens <= 4096 and required fields at the edge, rejecting malformed payloads with a 400.
  • 5.2
    Schema across templates and responses. Part of prompt maintenance, not just output safety.

Flows vs Agents

4 of 20 tasks #
The detail lives here 1.6 · Prompt Flows vs. Agents

The comparative matrix: execution path, behavioural consistency, auditability, industry fit. Regulated work wants a fixed graph a regulator can inspect; exploratory work wants ReAct. The trade is consistency against adaptability, and it is a compliance decision more than a technical one.

  • 1.1
    The short version. Flows are node-based and 100% predictable; Agents are ReAct and decide at runtime.
  • 2.1
    The hybrid that dissolves the choice. Step Functions ReAct — a macro-deterministic state machine with micro-non-deterministic reasoning inside each state. Stopping conditions and auditability without giving up intelligence.
  • 2.5
    Flows as a non-developer tool. Drag-and-drop builders so business analysts design workflows, which needs human-readable error paths rather than stack traces.
Group D

Agents

What changes once the system decides its own next step.

The agent loop & memory tiers

4 of 20 tasks #
The detail lives here 2.1 · Autonomous Systems, Agents and Memory

Reason → Act → Observe; the three Bedrock Agent components (foundation model, instructions, action groups) with Knowledge Bases and Guardrails optional; single vs multi-agent; Bedrock Agents vs Strands vs Agent Squad; and the three-tier memory hierarchy — operational (ElastiCache/DynamoDB), tactical scratchpad (DynamoDB), strategic (S3 or a Knowledge Base).

  • 2.5
    Supervision and handoff validation. If Agent A read the claim as auto collision and Agent B as property damage, the pipeline halts rather than passing bad context downstream.
  • 3.4
    Tracing the loop open. enableTrace=true exposes reasoning paths, KB retrievals with relevance scores, tool payloads and per-step confidence — for debugging, and for proving which sources were used.
  • 4.3
    Operating a fleet of them. The AgentCore tab in CloudWatch, handoff idle time, and loop detection: a tool that normally runs 100×/day suddenly firing 5,000×/hour.

Agent runaway control

5 of 20 tasks #
The detail lives here 2.1 · The 5 Security Layers

Five layers the notes call non-interchangeable: IAM least privilege (action groups are not a security boundary), input validation on model-generated parameters (block delete_inventory(quantity: -500)), timeouts, stopping conditions (max iterations, max time, confidence), and circuit breakers that degrade gracefully instead of crashing.

  • 2.5
    Rate limiting as a sixth layer. Built into the tool config, so a looping agent is capped at the tool rather than the orchestrator.
  • 4.1
    Stopping conditions as pure cost control. The same mechanism, bought for a different reason: recursive loops generate runaway bills.
  • 4.3
    The bill as the detector. Runaway agents, recursive loops and denial-of-wallet attacks all surface on cost before they surface anywhere else.
  • 2.3
    The same attack from outside. WAF rate-based rules against scripts designed to trigger millions of token requests.

Tool definitions — OpenAPI, action groups, MCP

4 of 20 tasks #
The detail lives here 2.1 · Tool Integrations & OpenAPI Design

The OpenAPI schema is the agent’s instruction manual, so descriptions decide whether the right tool gets picked. Two-level validation (Bedrock for types, Lambda for business rules). Model-readable errors — return valid alternative IDs, not a bare 404, so the agent self-corrects. Action groups are Bedrock-only; MCP is portable. Lambda for short stateless tools, ECS for heavy stateful ones.

  • 1.5
    MCP as the standard connector. Described as a USB cable between models and enterprise data sources, removing bespoke connector code per tool — alongside function calling that lets the model choose search_cases() or check_overturned().
  • 2.5
    The same spec written for humans. OpenAPI documenting token usage and generation metadata for partner integrations — explicitly contrasted with 2.1, where it described tools to an LLM.
  • 4.3
    The diagnostic inversion. A 40% tool failure rate is almost never the API’s fault. It means the tool description is ambiguous and the model is passing malformed parameters.
Group E

Safety, security & privacy

Keeping bad input out, bad output in, and the person out of the data.

Guardrails

7 of 20 tasks #
The detail lives here 3.1 · Output Safety Controls

The two execution modes — block the whole response, or filter out only the offending part — plus content-filter severity with its counter-intuitive inversion: LOW is the strictest setting; HIGH blocks only extreme content. Denied topics, word filters, and a clear statement of what guardrails cannot do.

  • 1.6
    Layer 2 of instruct / block / structure. Guardrails sit outside the model and outside the prompt, which is exactly why prompt injection cannot disable them — and one policy applies across Claude, Llama and Nova alike.
  • 3.4
    Context-aware and two-layered. Filtering that adapts to user role and pipeline stage, built-in FM filters backed by an external LLM for nuanced rules, and the real cost: aggressive filters block legitimate clinical words like “bleeding” and “dosage”.
  • 3.2
    Guardrails for privacy. PII filters plus role-contextual configuration, so one model serves a doctor and a billing clerk under entirely different rules.
  • 1.1
    An independent safety net. Placed outside the raw inference path so it filters both directions.
  • 3.3
    The output-filtering stage of the governance loop. Combined with prompt engineering and RAG context limits to mitigate hallucinated output.
  • 2.5
    The hand-rolled equivalent. Content-filtering middleware validating prompts and responses, logging violations, triggering safe fallbacks.

Defense in depth & the cheap-to-expensive order

4 of 20 tasks #
The detail lives here 3.1 · Defense in Depth

WAF → Lambda regex → Comprehend → Guardrails → model, ordered by cost, plus the blind-spot table that justifies every single layer: WAF cannot read “ignore previous rules”; Comprehend misses zero-days; Guardrails cannot check whether this account belongs to this user; post-processing is too late to stop the token bill. Throttling is listed here as a security control — it stops brute-forcing prompt variants.

  • 1.6
    The three-layer version. Prompt instructs, guardrails block, schema structures. No single layer is sufficient alone.
  • 3.4
    Pre- / in- / post-processing enforcement. The same shape applied to written policy rather than to attacks.
  • 2.3
    The enterprise request lifecycle. Federation → Cognito trigger → WAF → PrivateLink → IAM → Verified Permissions → KMS → CloudTrail, in that order, on every request.

Prompt injection vs jailbreak

4 of 20 tasks #
The detail lives here 3.1 · Advanced Threat Detection

Injection overrides instructions; jailbreak bypasses filters (role-play, hypotheticals, Base64/ROT13, language switching, multi-turn probing). And the architectural danger: indirect injection hides the payload in a document that RAG later retrieves, so it fires for an innocent user’s query. Red teaming runs as a four-stage Step Functions loop that breeds new variants from successful attacks.

  • 1.6
    Why system prompts are not a defense. They can be bypassed by indirect injection and adversarial jailbreaks, which is the argument for guardrails existing outside them.
  • 1.2
    Red teaming on the model itself. The negated-statement trap: does the model register the corrected update, or stay stuck on the retracted one?
  • 3.3
    Detecting the campaign, not the request. Misuse anomaly detection — off-hours access, 100× volume spikes, systematic probing patterns.

PII / PHI handling

7 of 20 tasks #
The detail lives here 3.2 · De-identification

The masking table everything else refers back to: redaction (irreversible, least context — the model cannot tell if two mentions are the same person), tokenization (reversible, consistent references), pseudonymization (reversible, most context, reads as natural text), format-preserving encryption (keeps length and shape for strict parsers). Then dataset-level anonymization — generalization, perturbation, synthetic data — differential privacy with its ε budget (without a budget, repeated queries average the noise away), and k-anonymity. Plus the named failure mode: over-anonymizing until the data is useless, which is why the pipeline needs a utility check.

  • 3.1
    Why a Lambda still runs after Guardrails. Guardrails replace an entity with [PII]; compliance wants XXXX-XXXX-XXXX-1234 with a Luhn check. Deterministic code is also the fail-safe for a guardrail false negative.
  • 3.3
    Token-level rather than request-level. Endpoint handlers combining regex with NER, stripping sensitive tokens while leaving the rest of the answer intact and useful.
  • 1.5
    Scrub before embedding. Once PII is in vector coordinates it cannot be cleanly removed.
  • 1.2
    De-identify before training. PHI masked before data touches a training pipeline, with KMS-encrypted buckets, to hold BAA and HIPAA compliance.
  • 4.3
    Logging creates the exposure. Turning on model invocation logs captures full prompts and responses — so enabling observability makes PII your problem.
  • 2.3
    Tokenization as a border control. The real value never crosses a jurisdictional boundary; only the token does.

Comprehend vs Macie

2 of 20 tasks #
The detail lives here 3.2 · PII Detection — Two Services, Two Places

Comprehend works on text in flight, at request time (25+ PII types; Comprehend Medical for PHI and clinical entities). Macie works on data at rest in S3, discovering and classifying with built-in and custom identifiers. Picking the wrong one is a stock exam distractor.

  • 3.1
    Comprehend as input-safety layer 2. Sentiment, key phrases and PII detection, scoring risk so Step Functions can branch — placed before Guardrails because it is faster and cheaper.

Network isolation

3 of 20 tasks #
The detail lives here 3.2 · Protected AI Environments

Bedrock is a public AWS service by default. The detail that decides questions is the endpoint table: interface endpoints create an ENI with a private IP and are governed by security groups and NACLs; gateway endpoints exist only for S3 and DynamoDB, live in the route table, consume no subnet IPs, and have no security groups attached. Plus private subnets with no IGW/NAT and strict egress filtering.

  • 2.2
    PrivateLink to SageMaker endpoints. Traffic never traverses the public internet, which buys privacy and lower latency at once.
  • 2.3
    Endpoint policies and network guarantees. Policies restricting calls to claude-* and to bedrock:InvokeModel only — forbidding fine-tuning or deletion; Transit Gateway black-hole routes guaranteeing no Dev→Prod path can exist; Network Firewall domain filtering to stop exfiltration from a compromised component.

IAM & access models

5 of 20 tasks #
The detail lives here 3.2 · Fine-Grained Access Control

Least privilege on three axes — specific models, specific features, specific operations. RBAC vs ABAC, where ABAC scales without a new policy per condition. Condition keys including aws:sourceVpce. Resource-based policies on Knowledge Bases and custom models. And Lake Formation for column, row and cell-level control inside the tables used for training and RAG grounding.

  • 2.3
    Application-level authorization. Condition keys for source IP and business hours; permission boundaries capping delegated admin; and the split that matters — IAM says whether you may call Bedrock, Cedar says whether you may see this document in this context. Plus RAM for cross-account sharing.
  • 3.3
    The three-layer hierarchy. SCPs set a ceiling and never grant — even root in a member account cannot escape one → IAM grants → resource policies. Plus tag-based access control.
  • 2.1
    Stated bluntly. Action groups are not a security boundary. IAM policies are.
  • 1.4
    Enforced before the maths. Fine-grained access control evaluates the JWT and drops unauthorized documents before vector similarity is computed.

Edge & data residency

3 of 20 tasks #
The detail lives here 2.3 · Cross-Environment AI Solutions

“If the data cannot move to the cloud, move the model to the data.” Three options with three distinct motives: Outposts for residency when law forbids data leaving the premises, Local Zones for metro-area latency, Wavelength inside 5G carrier networks for mobile. Plus Direct Connect with BGP policies prioritising inference over bulk sync on a shared link, and Control Tower blocking non-compliant deployments before they provision.

  • 3.2
    The in-region version of the same instinct. VPC isolation and egress filtering when the data can stay in AWS but must not touch the internet.
  • 2.4
    Failover that must respect borders. Route 53 multi-region health checks constrained by regional compliance and data-residency boundaries.
Group F

Governance & responsible AI

Proving later what you did, and checking it was fair.

CloudTrail vs CloudWatch Logs

4 of 20 tasks #
The detail lives here 1.6 · Audit Trail Mechanics

The table: CloudTrail records API metadata — who called InvokeModel, when, which prompt version, which model — kept ~7 years for regulators. CloudWatch Logs records payloads — full prompt, full response, token counts, latency — for operational debugging. Proving which prompt version was live when a complaint arrived is a CloudTrail job, not a CloudWatch one.

  • 3.3
    The distinction that decides exam questions. Management events are on by default; data events are OFF. Without enabling them you cannot prove which S3 objects were read during training or RAG context assembly. Plus multi-region trails and Athena for audit reporting.
  • 4.3
    The two paired for forensics. CloudTrail answers who and when; CloudWatch Logs supplies the payload needed to reconstruct the incident step by step.
  • 3.2
    The wider detection stack. CloudTrail plus Logs Insights, GuardDuty for anomalous access, and Security Hub aggregating findings with automated remediation.

Model Cards

2 of 20 tasks #
The detail lives here 3.3 · SageMaker Model Cards

Both birth certificate and report card: intended business use and explicitly unsupported uses, data lineage, evaluation metrics, known risks and failure modes, SEC/FINRA audit fields, fairness and explainability scores. And the operational insight — generate them programmatically in CI/CD from training and processing jobs, because manual documentation goes stale the moment a model retrains.

  • 3.4
    The Responsible-AI angle. Bedrock Model Cards carrying disaggregated metrics per demographic group, so strong aggregate accuracy cannot hide a failing protected cohort.

Lineage & reproducibility

2 of 20 tasks #
The detail lives here 3.3 · Data Source Tracking

Lineage as a DAG of Artifacts (S3 URIs, weights, metrics files, ECR images), Actions (ETL, training jobs) and Contexts (endpoints, experiments, pipeline runs). Glue tracks data lineage while SageMaker tracks model lineage; cross-account AddAssociation keeps the chain unbroken. S3 versioning plus Feature Store time travel delivers what regulators actually ask for: same model version + same data version = same output.

  • 5.1
    The practical corollary. Prompts, weights and evaluation datasets version together as one snapshot — change the dataset and v7-vs-v8 scores mean nothing.

Bias & fairness metrics

3 of 20 tasks #
The detail lives here 3.4 · Fairness Evaluations

The criteria and their limits: demographic parity (flawed — forcing equal rates distorts when base rates genuinely differ), equal opportunity (TPR parity), equalized odds (strictest — TPR and FPR), and counterfactual fairness, called out as most practical for GenAI because changing only the demographic attribute isolates causation. Group vs individual fairness. And completeness bias: factually correct but systematically shorter answers for one cohort is still bias.

  • 3.3
    The three metrics Clarify actually computes. DPPL (difference in positive proportions), DI (disparate impact — below 0.8 is the red flag), DCR (difference in conditional rejection) — and the pre-training vs post-training split, because balanced data can still train a biased model.
  • 3.4
    Turned into a deployable control. Policy translation sets DI tolerance to 0.8–1.25, emits it to CloudWatch, and alarms halt the deployment on breach.

Drift — five unrelated things

7 of 20 tasks #
The detail lives here 3.3 · Model Monitor & Drift Types

The only place drift is taxonomized: Model Monitor’s four modules — data quality drift, model quality drift (needs ground-truth labels), bias drift, feature attribution drift. Measured by Jensen-Shannon divergence against a training-time baseline, and requiring careful threshold calibration to trade false alarms against missed drift.

  • 1.2
    Data drift. New approved medications, ICD-10 revisions, changed physician shorthand — the world moves and extraction quality sinks.
  • 5.2
    Embedding drift. The vector space diverges as new literature introduces terminology the embedding model never saw.
  • 1.6
    Prompt drift. Thirty regional prompt files where updates fail to propagate evenly — the argument for one parameterized template.
  • 2.5
    Multi-agent drift. What supervision and handoff validation exist to prevent.
  • 4.3
    Latency and index drift. Fragmentation and query-latency creep that accumulate invisibly day to day.
  • 5.1
    Behavioural drift, detected. Regression benchmarking against a fixed dataset is the instrument.

Human in the loop

6 of 20 tasks #

The mechanism, not just the principle: confidence bands choose the review mode, Step Functions wait tokens pause the workflow and preserve state with a 24-hour timeout rather than terminating, and corrections land in DynamoDB with GSIs by decision type and reviewer so rejection patterns can be queried without a full table scan.

  • 1.6
    Approval as structure. Three-tier gate with separation of duties — the author cannot approve or deploy their own prompt — and the loop where a human agent’s edit becomes ground truth driving prompt v9.
  • 1.2
    The gate that cannot be automated away. Automatic evaluation and an LLM judge narrow the field, but clinical sign-off by a medical board is non-negotiable before go-live.
  • 1.3

  • 5.1
    Two audiences, two blind spots. Customers judge helpfulness but cannot detect a confident hallucination; only domain experts in Ground Truth catch factual and regulatory errors.
  • 3.3
    Separation of duties as governance. Whoever trained the model is barred from approving its deployment.

Retry, backoff, jitter, circuit breaker

5 of 20 tasks #
The detail lives here 2.4 · Resilient FM Systems

The actual numbers: backoff 100/200/400/800 ms, jitter ±100 ms, 3–5 attempts, a 20-second cap (without one, exponential growth compounds into minutes). The breaker trips at 50% failures over a 10-request window, recovers after 30–60 s, and half-opens at 10–20% traffic to test before fully reopening.

  • 2.5
    Split by status code — the sharper framing. 429 retries almost immediately with 100–300 ms jitter because capacity will return. 5xx backs off exponentially from 500 ms. 4xx never retries — it will fail identically forever.
  • 2.3
    Why jitter exists at all. The thundering herd: thousands of clients failing on the same millisecond and reconnecting in lockstep, creating a second outage.
  • 2.1
    The breaker as an agent safety layer. One of five, enabling graceful degradation — switch to conservative planning mode rather than crash.
  • 5.2
    Breaker plus load shedding, in anger. Step Functions breaker states managing Bedrock quotas, with low-priority traffic deliberately dropped to protect emergency queries.

Timeouts — three unrelated senses

6 of 20 tasks #
The detail lives here 2.5 · Multi-Level Timeout Alignment

The alignment rule: Model < Lambda ≤ API Gateway < Client — and what breaks when you get it wrong. If Lambda times out after the gateway has already cut the connection, the client gets a generic 504 while Lambda keeps burning resources invisibly, with nobody listening for the result.

  • 2.4
    Sized by how hard the job is. 4–5 s for real-time clinical queries (failing fast to a fallback beats a spinner), 15–30 s for simple inference, up to 120 s for complex generation.
  • 2.2
    The trap that catches people. A 100 GB+ model takes 20–40 minutes to download from S3 and load into VRAM, while default container health checks allow 5–10. Raise them to 60 minutes or AWS fails a perfectly healthy deployment.
  • 2.1
    A limit repurposed as a safeguard. Lambda’s hard 15-minute ceiling used as an agent stopping condition, with partial work saved on graceful termination.
  • 1.3
    Why orchestration moves up a level. A long Transcribe job breaches Lambda’s 15 minutes, so Step Functions coordinates and waits natively instead.
  • 1.1
    Working around a 30-second ceiling. AppSync’s integration limit, solved with an async mutation that returns a conversationId immediately and streams tokens over a subscription.

Throttling & concurrency

5 of 20 tasks #
The detail lives here 2.4 · Multi-Level Throttling

The hierarchy — account ~10,000 RPS → stage 1,000–5,000 → route 50–500 — and why route level matters most: a heavy reasoning model may sustain only 50 RPS where a classifier handles 500, so limits must be derived from downstream model capacity, not picked arbitrarily.

  • 4.2
    Capping parallelism before it 429s. Step Functions Map MaxConcurrency: 10 runs 100 requests ten at a time, with the rest waiting safely in state rather than triggering a retry storm.
  • 2.3
    Per-team isolation and chargeback. API Gateway usage plans and API keys stop one team’s runaway bug starving everyone else, and make token spend attributable. Plus reserved vs provisioned Lambda concurrency.
  • 4.1
    Concurrency as a cost control. Reserved concurrency as a ceiling protecting Bedrock’s limits; provisioned concurrency billed continuously even while idle.
  • 3.1
    Rate limiting as a security control. It stops an attacker grinding through thousands of prompt variations to find a bypass.

Queues — three different motives

5 of 20 tasks #
The detail lives here 4.1 · Queue-Based Architecture

The cost motive, stated cleanly: without a queue you provision for peak and idle most of the time; with one you provision for average and let peaks drain. The price is latency during bursts.

  • 2.2
    The reliability motive. Requests are never rejected during a spike, they wait. SageMaker Asynchronous endpoints do this natively — queue, write output to S3, notify via SNS.
  • 4.2
    The throughput motive. Micro-batching, plus priority queues or SQS message attributes so emergency requests never queue behind routine documentation.
  • 2.3
    Ordering, which is a fourth motive. SQS FIFO with Message Group IDs keyed on customer id preserves sequence within a customer while processing customers in parallel. And Amazon MQ instead of SQS when the legacy system already speaks JMS/AMQP — it exists so you need not rewrite the legacy side.
  • 5.2
    Shedding rather than queuing. Under severe load, low-priority traffic is dropped on purpose to preserve capacity for core functions.

Streaming

5 of 20 tasks #
The detail lives here 4.2 · Responsive AI Systems

The split that makes streaming make sense: actual latency is unchanged at 8 seconds, perceived latency drops from 8,000 ms to ~500 ms time-to-first-token — and that second number is the one the user remembers. Named the most cost-effective way to cut perceived latency without touching infrastructure or model choice.

  • 2.4
    The wire-level detail. SSE vs WebSockets, and why SSE usually wins for LLM output — the client has nothing to send back. Its superpower is Last-Event-ID: reconnect and resume from event 48 instead of regenerating everything. Buffer 5–20 chunks and flush on size, on 100–500 ms, or on a semantic boundary so half-sentences never render.
  • 2.5
    The part nothing else covers. Streamed tokens are invisible to screen readers unless the container is an ARIA live region. Without one, a blind user hears nothing at all. Plus progressive rendering at 50–200 ms and the correct text/event-stream content type.
  • 1.1
    Streaming over GraphQL. AppSync subscriptions carrying tokens, with an async mutation pattern to escape the 30-second integration limit.
  • 4.3
    The reality check. The server logged 2.0 s. CloudWatch RUM says the user’s screen finished rendering at 5.0 s.

X-Ray & distributed tracing

6 of 20 tasks #
The detail lives here 2.4 · X-Ray Subsegments & Annotations

Subsegments splitting preprocessing, invocation and postprocessing; annotations as filterable tags (model name, input complexity, output quality, workflow context) so you can later ask for “every slow cardiology request”; and percentiles — p50 is the typical user, p99 is the worst 1% that averages hide.

  • 2.3
    Sampling, because tracing everything is unaffordable. 5% of normal requests, 100% of slow ones and errors — full traces exactly where you need them.
  • 4.2
    Profiling prompt shapes. Which token lengths and tool-calling sequences actually introduce the latency, rather than which service.
  • 2.5
    GenAI annotations answering a specific question. “Why do prompts over 4,000 tokens lag disproportionately?”
  • 5.2
    The best single argument for tracing. It proved the bottleneck was the authentication middleware, not the model — which every dashboard had been blaming.
  • 4.3
    Trace maps inside agent runs. Per-step latency across agent tool calls, integrated into CloudWatch.

No owner, by design. This is the most-repeated service in the notes — 14 of 20 tasks — and the reason it feels confusing is that every task uses it for something different. The disambiguation is the entry.

  • 1.3
    Parallel multimodal processing. Chosen specifically because Lambda’s 15-minute cap cannot hold a long Transcribe job.
  • 1.5
    Parallel sub-query execution. Running decomposed sub-queries at once, then merging before the reranker.
  • 1.6

  • 2.1
    The deterministic shell around a ReAct loop. Macro structure fixed by the developer, micro reasoning left to the model. Also stopping conditions and human wait tokens.
  • 2.3

  • 2.4

  • 2.5
    Declarative half of a hybrid. Step Functions defines what runs; EventBridge reacts to when it starts.

CloudWatch — what it is actually doing

9 of 20 tasks #
No single owner — that is the point

Also no owner — 16 of 20 tasks. The service is everywhere; the job differs each time, and that is the thing worth memorising.

  • 1.3
    Watching a trend, not a batch. A validation pass rate drifting 94% → 91% → 87% means an upstream system changed its export format without telling you.
  • 1.2
    Alarms wired to SNS. JSON parse failures above 1% in an hour pages the on-call data engineer directly.
  • 1.6
    The early-warning indicator. Human escalation rate spiking while API error rates stay flat means the model is failing quietly.
  • 2.2
    Two rules of thumb. GPU utilisation averaging 20% means the instance is oversized. A 5% cache hit rate means the caching strategy is not earning its keep.
  • 2.3
    Composite alarms. Latency high AND confidence low AND errors elevated — combining metrics to kill false positives.
  • 4.2
    Experimentation, specifically. CloudWatch Evidently for A/B testing and statistical comparison — distinguished from AppConfig, which is for feature flags and progressive rollout.
  • 4.3
    The deepest treatment. Unified GenAI views, anomaly detection with seasonality awareness (Monday-morning peaks are not incidents), custom metrics for hallucination and relevance, RUM for client-side truth, and the AgentCore tab.
  • 3.3
    Metric filters as governance. Extracting compliance signals from structured JSON log streams into custom metrics and alerts.
  • 5.2
    Logs Insights hunting prompt confusion. Unsubstituted {{variables}} leaking to users, the model discussing the template instead of answering, acknowledged instruction conflicts.

Evaluation — what is measured, where

6 of 20 tasks #
The detail lives here 5.1 · Assessment Frameworks

The four core quality dimensions — relevance, factual accuracy, consistency, fluency — and crucially their independence: a response can be perfectly fluent and entirely wrong, or strictly accurate and irrelevant. Domain dimensions layer on top (compliance, tone). LLM-as-a-judge with one hard constraint: never let a model judge itself (self-preference bias). And the dual-phase RAG split — retrieve-only vs retrieve-and-generate — which is the root-cause isolator: if retrieval passes and the answer is still wrong, the generator hallucinated, not the vector search.

  • 1.2
    The three-tier gate, and a trap. Automatic → LLM judge → human sign-off. Plus the exam trap: latency and cost are not part of model evaluation — that is a load test. See also the BLEU vs ROUGE deep-dive and their shared blindness: both are text overlap, so “patient has chest pain” scores well against “patient does not have chest pain”.
  • 3.1
    The same machinery aimed at safety. Toxicity and harmful content instead of accuracy — with custom metrics, because generic toxicity scoring cannot see domain hazards like unlicensed investment advice.
  • 3.4
    The judge aimed at fairness. Correctness, harmfulness and completeness per cohort — plus judge-bias mitigation: explicit rubrics, ensemble judging, human calibration.
  • 4.3
    The judge as an alarm source. Marking production answers against a golden set so hallucination becomes a number a threshold can watch.
  • 4.1
    Evaluation with a price column. Cost per accuracy point: 89% at a fifth of the price beats 94%, if 89% clears the bar.

A/B, canary, blue-green, feature flags

5 of 20 tasks #
The detail lives here 5.1 · Model Deployment Testing

The purpose split: A/B testing is comparative analysis — which variant is actually better, with statistical significance. Canary is risk mitigation — ship the thing you have already chosen, by degrees, watching health metrics as you scale up.

  • 2.4
    The mechanics. 5–10% of live traffic to the candidate, 90–95% on baseline, then significance testing before any decision.
  • 4.2
    The AWS-service distinction worth memorising. CloudWatch Evidently for quantitative experimentation; AppConfig for feature flags and progressive rollout. Same shape, different tool.
  • 3.3
    Blue/green as automated remediation. When a drift or bias alarm fires, traffic shifts back to the last known-compliant version without waiting for a human.
  • 5.2
    A/B across prompts, not models. Benchmarking prompt variants for consistency and accuracy under identical load.

Hallucination — the control stack

6 of 20 tasks #
The detail lives here 3.1 · Accuracy Verification Systems

The five-layer pipeline, and the honest admission at layer 1: grounding reduces hallucination but does not eliminate it — models still extrapolate beyond retrieved context. Then semantic similarity to prove the answer came from the sources, confidence routing, schema bounds, and the structural answer: text-to-SQL, where the model writes a query instead of an answer, a Lambda validates it is SELECT-only against whitelisted tables, and the figure comes from the database — making hallucination structurally impossible.

  • 1.6
    Contextual grounding as a guardrail feature. Mathematically verifying the response is supported by the retrieved chunks, as part of the block layer.
  • 4.3
    Making it a metric. Nothing ships hallucination detection out of the box; you build it from a judge model and a golden set.
  • 5.1
    Assigning blame between retrieval and generation. Retrieve-only passing while end-to-end fails points squarely at the generator.
  • 2.5
    The retrieval log as the decisive evidence. If the logged chunks were already irrelevant, the model behaved correctly and the RAG tier is at fault. This stops teams tuning the wrong component mid-incident.
  • 1.2
    Why automated metrics alone cannot catch it. ROUGE and BLEU will pass a negation flip with a high score.

Fine-tuning vs prompting vs RAG

4 of 20 tasks #
The detail lives here 1.2 · LoRA Mechanics

The base model’s weights stay completely frozen; a trainable adapter under 1% of parameters is attached and trained alone, so it is modular, cheap and swappable without rebuilding anything. Plus the comparison that drives the choice: few-shot prompting pays tokens on every single call and risks instruction drift, while fine-tuning bakes the behaviour in and leaves the prompt short. 100–300 curated JSONL pairs is the scale.

  • 2.2
    The deployment consequence. Keep one base model resident in VRAM and swap LoRA adapters in seconds. And Custom Model Import economics: your fine-tuned model on serverless pay-per-token pricing instead of a 24/7 GPU endpoint bill.
  • 1.5
    The same instinct for embedding models. General models misread domain vocabulary, so embeddings need domain adaptation for exactly the same reason.
  • 3.3
    The legal dimension. Per-vendor licensing recording whether a dataset may be used for pre-training, fine-tuning, or RAG prompt injection at all.

Models remember nothing, so state is infrastructure: DynamoDB with PK session_id and SK timestamp. And the governance twist — a 90-day TTL is a regulatory retention control, not database hygiene. It enforces GDPR-style deletion with no cron job and no custom pipeline.

  • 1.3
    The hybrid sliding window. Compress older turns into a summary, keep recent turns verbatim — short-term context without token bloat.
  • 2.1
    Three tiers instead of one table. Operational, tactical and strategic memory, each with its own store and latency profile.
  • 2.5
    Reduction when the window is the constraint. Compression, summarization, or key-information extraction to carry context through a chain.
  • 5.2
    A sliding window in anger. Step Functions walking a long medical record in segments, preserving clinical context across the joins.
  • 2.3
    The same mechanism for something unrelated. DynamoDB + TTL as an idempotency store rather than a conversation store.

Idempotency

2 of 20 tasks #
The detail lives here 2.3 · Webhook Handlers & Idempotency

External webhooks are delivered at least once, so duplicates are a certainty, not a risk. Event IDs are checked against DynamoDB with TTL and the cached result is returned instead of re-invoking the model — otherwise the email sends twice and you are billed twice.

  • 2.4
    The same bug from the other direction. An SQS visibility timeout set too short means SQS assumes the worker died while it is still mid-inference, re-delivers the message, and you pay for the call twice. Set it to 5–15 minutes.

Correlation IDs & blame attribution

4 of 20 tasks #
The detail lives here 4.3 · Correlation Systems & Outcome Tracking

Correlation IDs binding user request → model invocation → business event, and the insight that gives them teeth: HTTP 200 is not success. If the user clicks “talk to a human” immediately after the answer, the request succeeded and the system failed. Same logic as tool success vs tool effectiveness — a 200 OK with an empty JSON body is 100% success and 0% effectiveness.

  • 3.3
    Correlation IDs for audit. Tracing one transaction across distributed microservices and gateways to satisfy a regulator, not to debug.
  • 2.5
    Full-lifecycle logging. Preprocessing, retrieval results, model I/O and post-processing — with retrieval as the critical audit point.
  • 5.2
    The symptom-to-tool table. Incomplete responses → CloudWatch metrics; API failures → structured logging; slow latency → X-Ray; inconsistent answers → A/B and diffing; irrelevant retrieval → embedding visualization; faulty reasoning → CoT analysis.

The GenAI Gateway

4 of 20 tasks #
The detail lives here 2.3 · The Grand Finale: The GenAI Gateway

Defined by what breaks without it: spend becomes untrackable, guardrails get applied inconsistently or forgotten, there is no unified audit trail, and swapping the underlying model means every team rewrites code. One gateway centralises access control, per-team rate limits and chargeback, uniform guardrails nobody can bypass, routing and fallback, shared caching, and audit logging — and becomes an abstraction layer so a model swap is a gateway change rather than twelve team migrations.

    Where the audit trail lands. One choke point produces one complete, consistent record instead of twelve partial ones.
  • 2.4
    Where the routing lands. Cascading, fallback and A/B splits implemented once, centrally, rather than per team.
