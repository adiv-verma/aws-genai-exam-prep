Domain 3 · The Map

All Four Tasks, One Picture

Domain 3 is one idea done four times: stop the bad thing, then be able to show later that you stopped it. Here are all four tasks as a single request — what gets checked before the model, what gets checked after it, and what you write down either way. Each box says what it does, lists the concepts it teaches, and links straight to the section of the notes that covers it.

Scroll the diagram sideways if it does not fit.

What each task is actually about

One line each, then the few things most worth remembering.

3.1

Input & Output Safety

Stopping the bad thing going in, and the bad thing coming out.

  • Cheapest check first. WAF, then a Lambda doing pattern matching, then Comprehend, then Guardrails, then the model. Anything caught early is a model call you never pay for.
  • Every layer is blind to something. WAF knows web attacks but cannot read plain English like “ignore your previous rules”. Guardrails cannot know your own business rules. That is why you need all of them.
  • Block it all, or just the bad bit. Block mode when it is serious. Strip the bad part and keep the rest when it is minor.
  • Make the numbers impossible to invent. Let the model write the SQL, check the SQL, then let the database do the sums. A figure that comes from the database cannot be made up.
  • Three answers, not one: sure, send it. Half sure, send it with a warning. Not sure, a person looks first.

3.2

Data Security & Privacy Controls

Keeping the data inside, and keeping the person out of it.

  • Two kinds of endpoint. Interface endpoints get a network card and a security group. Gateway endpoints are a line in a route table, and only work for S3 and DynamoDB.
  • Deleting the name breaks the sentence. Swap it for a stand-in instead, so the model can still tell that two mentions are the same person.
  • Two places to look for personal data. Comprehend reads text as it arrives. Macie scans what is already sitting in S3.
  • If the data cannot move, move the model. Outposts when the law says the data stays put, Local Zones for distance, Wavelength for phones.
  • Deleting is not enough. You also have to be able to show when you deleted it, and how.

3.3

Governance & Compliance

Being able to prove, a year later, how a model was built and who said yes.

  • A model card is a birth certificate. What it is for, what it was trained on, what it is bad at, and who signed it off.
  • Turn data events on. CloudTrail records who called the API by default, but not who read the file. That second part is off until you switch it on — and it is the part auditors ask for.
  • Same model, same data, same answer. That is what lets you show what the model said on a date two years ago.
  • The person who built it cannot approve it. Step Functions checks the bias numbers and the paperwork, then asks somebody else to sign.
  • An SCP is a ceiling, not a key. It never gives permission, only takes it away — and not even the root user of that account can get around it.

3.4

Responsible AI

Showing your working, checking it is fair, and turning written rules into code.

  • One setting opens the box. Turn tracing on and you can see every step the agent took, every page it read, and how sure it was at each one.
  • Models sound confident when they are wrong. Measure how sure they really are, and send the shaky ones to a person.
  • Right answer, thinner answer. A model can be correct for everybody and still be unfair, if one group always gets the short version.
  • The judge has opinions too. A second model marking the first brings its own bias. Use a strict marking scheme, several judges, and real people to check them.
  • Write the rule down, then point at the code that does it. Policy, then a spec, then an automatic test, then the evidence an auditor can read.

Why the same thing keeps coming up

Some ideas show up in several tasks. That is not repetition — each task uses the same tool for a different job. Knowing which task owns the detail is half the battle in the exam.

Guardrails, three different jobs
3.1 catches rude or dangerous wording going in and coming out. 3.2 uses them to stop personal data leaking into the answer. 3.4 uses them to enforce rules the compliance team wrote down. Same service, three jobs.
Model cards, written twice
3.3 says what goes in one and who signs it. 3.4 adds the awkward part: what the model is bad at, and how it scores for each group separately.
Confidence scores
3.1 uses the score to decide whether a person needs to look. 3.4 asks the harder question — is the score honest? Something marked 90% sure should be right nine times out of ten.
Bias: the maths and the manners
3.3 gives you the maths (DPPL, DI, DCR) and when to run it. 3.4 gives you the human version: the same question for every group, and a second model marking the answers.
Nothing is trusted on its own
3.1 stacks safety checks. 3.2 stacks network walls. 3.3 stacks permissions — the SCP, then IAM, then the resource itself. 3.4 stacks guardrails before, during and after. Same shape every time.
Four logs, four different questions
3.1 logs what was blocked. 3.2 logs who touched the data. 3.3 logs how the model was built and who approved it. 3.4 logs why the answer came out the way it did.

Coming from the other maps? Domain 1 builds the system — documents in, answer out. Domain 2 puts that system inside a company and keeps it running. Domain 3 is the part that keeps it out of trouble: what it is allowed to say, what it is allowed to see, and what you can show an auditor afterwards.
