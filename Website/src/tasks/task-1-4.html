Domain 1 · Task 1.4 · Bonus Assignment

Two Vector Stores,
One Knowledge Assistant

The assignment: build a knowledge assistant that can answer questions about technical documentation, research papers, and company policies. The brief specifically calls for standing up two different kinds of vector store over that same document set — a fully managed one (Bedrock Knowledge Bases) and a custom one with full control over indexing and search (OpenSearch) — so this build is designed as a side-by-side comparison of both approaches, not just one. This page lays out exactly how that would be built — which AWS services, in what order, and why each one earns its place — but nothing on this page has been deployed yet. Two of the pieces this design calls for (a provisioned OpenSearch domain and a Bedrock Knowledge Base) bill by the hour whether they're being used or not, so the build is being held until there's a deliberate, single build-test-and-tear-down session, instead of risking something expensive running unattended by mistake.

Build Plan

The order it would get built in, and what each step proves

Every step below is written the same way the other tasks' completed steps are — what would get built, where to check it, why it matters — except nothing here has actually run yet. Scope follows the same pattern as Tasks 1.1–1.3: a real, live, scaled-down PoC of the parts that actually teach vector-store concepts (Phases 1–3 of the brief), not the full enterprise brief. See the note at the bottom of this section for why Phases 4–6 (external connectors, sync automation, a full web app) are being left as design-only.

Why this whole task is on hold before deploying

Every task before this one (1.1–1.3) only used pay-per-request services — Lambda, S3, DynamoDB on-demand, Bedrock's pay-as-you-go model calls — so leaving something running by accident overnight cost, at most, a few cents. This task is different: it calls for a provisioned OpenSearch domain and a Bedrock Knowledge Base, and both of those bill by the hour the moment they exist, whether or not a single query ever hits them.

The plan: deploy Steps 1–10 in one focused session, verify each one against real test documents and real queries (the same "prove it with a live test, not just a successful deploy" standard every other task on this site follows), then delete the OpenSearch domain and the Knowledge Base before that session ends — not "later." The full teardown commands are kept ready in this task's progress.md so there's no delay between finishing a test and shutting the billing off.

Phase 1

Foundation Infra

The three stores this design depends on, plus the storage and access role that feed them.

1

Turn on Bedrock model access

Planned, not built

Would enable: Claude · Titan Embeddings

What this would involve: Confirming model access is already granted from earlier tasks (Claude was used in 1.1–1.3), and specifically requesting access to a Titan embeddings model, which none of the earlier tasks needed — embeddings are the numeric fingerprint of a piece of text that vector search actually compares.

Why it wasn't built yet: Free to enable, but there's nothing to test it against until the S3 bucket and document set in Step 2 exist.

2

Create storage and a small set of test documents

Planned, not built

Would create: adi-1-4-documents-269737522732 · sample docs across 3 folders

What this would involve: An S3 bucket with three prefixes — technical-docs/, research-papers/, policies/ — matching the brief's three document categories, plus a handful of realistic synthetic sample files written for this project (same approach as Task 1.3's synthetic reviews/photos/calls, since no ready-made sample data ships with the assignment).

Why it wasn't built yet: This step alone is essentially free (S3 storage for a handful of small files), but it only exists to feed Steps 3–6, so it's sequenced with them rather than built in isolation.

3

Stand up the managed vector store

Planned, not built

Would create: adi-1-4-bedrock-kb-role · adi-1-4-knowledge-base

In plain terms: A Bedrock Knowledge Base is the "easy mode" vector store — point it at an S3 bucket, and AWS handles chunking the documents, turning each chunk into an embedding, and storing those embeddings, with no database to manage directly. The trade-off is less control over exactly how that storage works under the hood.

What this would involve: An IAM role letting Bedrock read from the S3 bucket, then a Knowledge Base configured with semantic chunking and the Titan embedding model, pointed at all three prefixes from Step 2. This is the managed implementation of this task's vector store — the same documents get a second, custom implementation through OpenSearch in Step 4, so both approaches can be compared side by side, which is what the brief itself asks for.

Why it wasn't built yet: This is one of the two pay-by-the-hour resources flagged in the cost note above — a Knowledge Base's backing storage has a minimum billable floor around $1/hr even completely idle, so it's held until it can be tested and torn down in the same sitting.

Cost to know

A Knowledge Base doesn't let you point it at zero infrastructure — by default it provisions an OpenSearch Serverless collection behind the scenes with its own minimum OCU (compute unit) floor, and that minimum is billed even at zero queries. That's a different bill from the OpenSearch domain in Step 4, which is a separate, manually-run cluster for the custom implementation.

4

Stand up the custom vector store

Planned, not built

Would create: adi-1-4-vector-search (OpenSearch domain, 1 node)

In plain terms: Amazon OpenSearch Service with the Neural Search plugin turned on works differently from a Knowledge Base: documents get embedded and indexed ahead of time, but at query time someone can type a plain-English question and OpenSearch converts it to a vector and runs the similarity search internally — no separate embedding step needed at search time. It can also combine that semantic search with exact keyword matching (an exact error code or API name has to match precisely; a rephrased troubleshooting question has to match by meaning) — that combination is called hybrid search, and it's something a Knowledge Base can't do out of the box.

What this would involve: A domain sized to t3.small.search, single node, single AZ — deliberately scaled down from the brief's own example (r6g.large.search × 3 nodes across 3 AZs, meant for production traffic at real scale, not a PoC), with the Neural Search plugin turned on. This is the custom implementation of the same document set from Step 2 — the one with real control over indexing (Step 8) and search behavior (Step 9), which a Knowledge Base doesn't expose.

Why it wasn't built yet: The other pay-by-the-hour item flagged above. Scaled down from ~$360/month (the brief's literal 3-node config) to ~$26/month for a single small node — still real money if forgotten, which is exactly the scenario this hold is meant to prevent.

5

Create the fast-lookup metadata store

Planned, not built

Would create: adi-1-4-document-metadata (DynamoDB, on-demand)

In plain terms: DynamoDB here isn't storing the 15 million documents themselves — it's a sub-millisecond key-value lookup for lightweight, fast-changing facts, like "was compliance rule 10b-5 updated this morning." Vector search is the wrong tool for that question; it's not a similarity search, it's a single exact lookup that needs to be instant.

What this would involve: A table keyed on document_id (partition key) and chunk_id (sort key), on-demand billing mode (no capacity to plan for at PoC scale), with a secondary index on document_type for filtering.

Why it wasn't built yet: Essentially free at this scale (DynamoDB on-demand bills per request, not per hour), but it's the last piece of Phase 1's infrastructure and gets deployed alongside the rest in the same session.

Phase 2

Document Processing Pipeline

Turning raw uploaded files into chunked, embedded, searchable records automatically.

6

Build the ingestion pipeline

Planned, not built

Would create: adi-1-4-document-processor-role · adi-1-4-document-processor

What this would involve: A Lambda triggered the instant a new file lands in S3 — extracts text (PDF/DOCX/HTML), splits it into overlapping chunks, calls Titan to embed each chunk, writes the vector into OpenSearch, and writes the chunk's metadata (title, source, chunk index) into the Step 5 DynamoDB table.

Why it wasn't built yet: Depends on Steps 3–5 already being live to write into, so it's sequenced right after them rather than deployed standalone.

7

Prove the pipeline end-to-end with real documents

Planned, not built

Would test: one upload per document type

What this would involve: Upload one technical doc, one research-paper excerpt, and one policy doc for real, and confirm chunks actually land in DynamoDB and vectors actually land in the OpenSearch index — the same "test with a real event, don't just trust the code compiles" standard every other task on this site holds to.

Why it wasn't built yet: Can't be tested before Step 6 exists to trigger.

Phase 3

Advanced Search

Making search fast and precise at scale — sharding, hierarchy, and combining keyword with meaning.

8

Set up hierarchical, multi-index search

Planned, not built

Would create: 3 OpenSearch indices with nested + knn_vector mappings

In plain terms: Splitting one giant index into several smaller ones by document type (technical docs, research papers, policies) is the same idea as splitting a huge supermarket into Dairy, Meat, and Sports sections — a query about a policy only has to search the policy shelf, not all 15 million rows. A "nested" field additionally lets one document keep parent-child structure (a case and its individual sections) inside a single index.

What this would involve: Three separate indices (technical_documentation, research_papers, company_policies) inside the Step 4 domain, each with a knn_vector field (dimension 1536, hnsw/cosine similarity) and a nested hierarchy field for parent-child document sections.

Why it wasn't built yet: Configuration inside the Step 4 domain — can't exist before that domain does.

9

Build the search coordinator

Planned, not built

Would create: adi-1-4-search-coordinator-role · adi-1-4-search-coordinator

In plain terms: A single query might need to check more than one shard/index at once (a "parallel fan-out" — like sending several assistants down different aisles at the same time instead of one person walking the whole store), then merge and re-rank the combined results before anything is returned.

What this would involve: A Lambda, invoked manually for this PoC rather than sitting behind a public API Gateway endpoint (same choice Task 1.3 made for its batch/report-style Lambdas — no public endpoint means no idle cost) — generates a query embedding, fans out across the three Step 8 indices with metadata filters applied, combines keyword (BM25) and semantic (kNN) scoring for hybrid search, and re-ranks the merged result set.

Why it wasn't built yet: Needs Step 8's indices populated with real embedded chunks (from Steps 6–7) before there's anything real to search.

10

Run real test queries and check the results make sense

Planned, not built

Would test: 3 representative queries

What this would involve: One query that needs metadata filtering (e.g. "policies only"), one that needs exact keyword precision (an exact error code or API name), and one that's purely semantic (a rephrased troubleshooting question with no exact keyword match) — checking the coordinator actually returns the right documents for each kind of question, not just that it runs without erroring.

Why it wasn't built yet: The final verification step — runs last, then the whole domain and Knowledge Base get torn down per the cost note above.

Phases 4–6

Scoped Out of This Build

External connectors, sync automation, and a full RAG web app — designed, not deployed.

Web crawler, wiki connector, DMS connector, data catalog, change detection, Step Functions sync, and an Amplify RAG app

Architecture only

What this would have involved: The brief's remaining three phases — connectors to crawl public sites and pull from Confluence/SharePoint-style systems, a unified data catalog, automated change-detection and incremental refresh via Step Functions and EventBridge, and finally a full RAG application with an Amplify-hosted web UI, conversation history, and A/B testing.

Why it wasn't scoped for a live build: None of it teaches vector-store selection or retrieval concepts — the actual AIP-C01 subject matter for this task. It's integration and frontend work (OAuth against third-party systems, webhook listeners, a deployed web app) that would multiply both cost and build time with no additional exam-relevant content. Already captured at the design level in this task's Study Notes page and its architecture diagram.
