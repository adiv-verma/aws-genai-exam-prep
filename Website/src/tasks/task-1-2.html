Domain 1 · Task 1.2 · Bonus Assignment

Picking the Right AI Model
& Keeping It Running

The goal of this project: build a system for a bank's customer-service AI that automatically picks the best AI model to use, keeps answering questions even if that model goes down, and gets specially trained on the bank's own kind of questions. This page walks through every step in the order it happened. Each AWS idea is explained in plain terms the first time it comes up, so you don't need to already know AWS to follow along.

How It Runs

Two full copies of the system, running in two different places

Dashed arrows show health checks running continuously in the background. Step-by-Step Build Log

Every step, in the order it happened

Each step below explains a new AWS idea in plain terms first (in the blue box, where it applies), then says exactly what was built, where to see it in the AWS console, and why it mattered. Kept to one topic on purpose — a bank's everyday customer questions about products like savings accounts and credit cards — to keep the project simple enough to actually finish and test properly. The last two steps were fully planned but not built, and Phase 4 explains exactly why.

Phase 1

Comparing the Models

Test 3 different AI models on the same set of questions, and score them so the choice is based on real evidence, not a guess.

1

Check that 3 models actually work

Claude Haiku 4.5 · Nova Lite · Nova Micro

In plain terms: Amazon Bedrock offers AI models from several different companies, not just one. Claude is made by Anthropic; Nova is made by Amazon itself. Using models from more than one company gives a fairer comparison than just comparing different sizes of the same company's model.

What was built: Sent a real test message to each of the 3 candidate models to confirm they actually respond. A 4th model, Claude Sonnet 5, was tried too but dropped, since it wasn't available on this account yet.

Where to check: AWS Console → Amazon Bedrock → Model access.

Why it matters: A fair comparison needs models from more than one company, not just different sizes of the same one — otherwise the "winner" might just reflect one company's general style rather than which model is actually best for this job.

2

Write test questions

data/benchmark_test_cases.json · 12 normal questions + 5 tricky ones

What was built: Wrote 12 everyday banking questions (things like "what's a savings account" or "how does a credit card work"), each with an example of a correct answer to compare against. Also wrote 5 tricky questions designed to test whether the AI does something it shouldn't — like giving personal investment advice, or asking the customer for a password.

Where to check: repo — data/benchmark_test_cases.json.

Why it matters: Without example correct answers, "how good is this answer" is just an opinion. Having a reference answer for every question is what makes the comparison in Step 3 something you can actually measure, not just eyeball.

3

Run the comparison

benchmark.py

In plain terms: "LLM-as-judge" means using one AI model to grade another AI model's answers — comparing the answer against the reference answer and giving it a score, instead of a person reading every single answer by hand.

What was built: A script that asks all 3 models all 17 questions from Step 2, times how long each answer takes, works out roughly how much each answer costs (based on published pricing), and uses a 4th AI call to grade each answer's quality and check whether the tricky questions were handled safely.

Where to check: repo — benchmark.py, data/model_evaluation_results.csv.

Why it matters: Covers all 4 things this assignment asked to compare — answer quality, speed, cost, and safety — using one script that can be re-run any time in the future, instead of a one-off manual check that goes stale.

Good to know

Using one of the 3 candidate models to also grade the others is a bit like a student grading their own test — it's not perfectly fair, since a model might unconsciously favor answers that sound like its own style. It was still used here because a stronger, independent grading model wasn't available on this account. Worth knowing as a real limit of this approach, not something to just take at face value.

4

Pick a winner

data/model_selection_strategy.json · winner = Nova Micro

What was built: Combined the 4 separate scores from Step 3 into one overall number for each model, weighted more heavily toward quality and safety than speed and cost, since this is a bank. Result: Nova Micro came out on top, then Nova Lite, then Claude Haiku 4.5. Interestingly, all 3 models gave almost equally good answers — so the fastest and cheapest one ended up winning, since there wasn't much quality difference to begin with.

Where to check: repo — data/model_selection_strategy.json.

Why it matters: This exact file is what gets loaded into the settings system in Step 5. In other words, the model actually used in production is the one the test results pointed to — not a guess made ahead of time.

Good to know

All 3 models handled the tricky safety questions correctly, just from good written instructions — no extra safety tool was added yet in this project. A real bank system would still want a dedicated safety layer as a backup (like the Guardrail built in Task 1.1), since instructions alone can sometimes be tricked by a clever enough question.

Phase 2

Auto-Switching Between Models

Make "which model to use" a setting that can change instantly, instead of something buried in code that needs a redeploy.

5

A settings file for which model to use

adi-1-2-model-config · Production · ModelSelectionStrategy

In plain terms: AWS AppConfig is a service for storing settings — like "which model is the current default" — separately from your application's code. Instead of editing and redeploying code to change a setting, you update AppConfig, and the running application picks up the new value automatically.

What was built: Set up AWS AppConfig and loaded the winning model choice from Step 4 into it as a saved setting.

Where to check: Console → AWS AppConfig → adi-1-2-model-config → Production.

Why it matters: This is what turns "switch to a different model" into a quick settings change instead of a code change. If Step 4's comparison gets re-run later and a different model wins, switching to it takes seconds — and if anything goes wrong, going back to the old setting is just as fast.

6

Permissions for the model-picker program

adi-1-2-bedrock-lambda-role

What was built: A permission set (an IAM role, the same idea explained in Task 1.1's Step 4) that only allows calling the 3 approved models and only allows reading this one settings file — nothing broader.

Where to check: IAM → Roles → adi-1-2-bedrock-lambda-role.

Why it matters: Keeps this program's access as narrow as possible — it can only do exactly what it needs to do, and nothing more, which limits the damage if anything ever goes wrong.

Error 1 · Slightly wrong permission name

What happened: Used a permission name that seemed reasonable based on which internal web address the settings service uses behind the scenes — but access was still denied.

Fix: the real error message named the exact permission needed, which turned out to be spelled a bit differently than expected, even though it does the same thing. Fixing the permission name to match the error message exactly solved it.

Good to know

An AWS service's internal web address and its exact permission name don't always match up the way you'd expect. When access is denied, the error message itself usually names the exact permission that's actually needed — better to trust that message than to guess based on the service's name.

7

The model-picker program

adi-1-2-model-abstraction

What was built: A small program (a Lambda function, the same idea explained in Task 1.1's Step 4) that reads the settings file from Step 5, picks the right model, asks it the customer's question, and sends back the answer. On purpose, it doesn't try to handle failures itself — that's a separate job, built in Phase 3.

Where to check: Lambda → adi-1-2-model-abstraction → Monitor tab.

Why it matters: This is the actual piece that makes "which model to use" a live setting instead of something baked directly into the code — it's what connects Step 5's settings file to a real, working answer.

Error 2 · Only understood one kind of request

What happened: Found and fixed before Step 9 needed it — the program only knew how to read requests shaped like a website request coming through the web entry point. A request coming from somewhere else, like the backup-plan flowchart built later, would have been silently ignored instead of answered.

Fix: updated the program to understand both shapes of request, and re-deployed it before Step 9 actually needed that to work.

8

A web address customers can call

adi-1-2-api · POST /generate · prod stage

In plain terms: Amazon API Gateway is AWS's service for creating a public web address that other applications can call over the internet. It's the front door — when a request comes in, API Gateway forwards it to a Lambda function (like the one built in Step 7) to actually handle it.

What was built: Set up a public web address that forwards incoming requests straight to the Step 7 program. Tested it for real from outside AWS entirely, not just from inside the AWS console.

Where to check: Console → API Gateway → adi-1-2-api → Stages → prod.

Why it matters: This is what makes the assistant something a real customer-facing app can actually call over the internet — it finishes the "ask a question, get an answer" path from start to end.

Phase 3

Staying Up If Something Fails

Build a backup plan, a second full copy of the system in another region, and real health checks watching both.

9

The backup plan (circuit breaker)

adi-1-2-circuit-breaker-sm

In plain terms: A "circuit breaker" pattern means trying a main option first, and automatically falling back to a backup option if it fails — and falling back again to something even simpler if that backup also fails. It's named after an electrical circuit breaker, which trips to stop a problem from spreading, instead of just letting everything fail at once.

What was built: Built a flowchart (using AWS Step Functions, the same tool explained in Task 1.1's Step 12): try the main model, and if that fails, try a backup model, and if that fails too, show a safe canned reply instead of an error message. Also added a way to deliberately fake a failure on purpose, specifically to prove each fallback step actually works — not just assume it would.

Where to check: Step Functions → adi-1-2-circuit-breaker-sm → Executions.

Why it matters: Gives the system a clear, visible failover plan instead of hidden error-handling buried in code somewhere. All 3 possible outcomes were tested and confirmed to really happen: a normal answer, a backup-model answer, and a safe canned reply when both models fail.

Good to know

Writing a flowchart that "should" fall back correctly isn't enough on its own — actually forcing a failure on purpose and watching what happens is the only way to be sure the fallback logic really works, rather than just looking correct on paper.

10

A second copy in another region

adi-1-2-cross-region-stack (CloudFormation)

In plain terms: An AWS "region" is a physically separate data center location — like Virginia (us-east-1) versus Oregon (us-west-2). If one region has an outage, a system deployed only in that region goes down with it. AWS CloudFormation is a tool for describing a whole set of AWS resources in one file, so the same setup can be deployed again elsewhere with one command instead of clicking through the console by hand each time.

What was built: Deployed a full second copy of the system in a different AWS region (Oregon), using CloudFormation so it could be built consistently in one step. Gave it its own independent settings file — not one that calls back to the first region, since that would defeat the whole purpose if the first region actually went down.

Where to check: Console → CloudFormation → Stacks → adi-1-2-cross-region-stack (region: Oregon).

Why it matters: If one AWS region has an outage, the system needs a genuinely independent copy running somewhere else to keep answering questions — not just a code copy that secretly still depends on the region that's down.

Error 3 · Same model works differently in a different region

What happened: Nova Micro showed up as available in the new region, but actually calling it failed anyway, with an error asking for a different kind of model ID than what worked in the first region.

Fix: found the correct ID format for that specific region (similar to the special ID format explained in Task 1.1's Step 1) and updated both the settings and the permissions to match. Confirmed it then worked correctly.

Minor · A "stop" button didn't do what it sounded like

What happened: Tried to quickly finish an in-progress settings update using what looked like a "stop and finish now" button.

Fix: it actually undoes the update instead of finishing it early — the opposite of what the name suggested. No real harm here, since a newer update was applied right afterward anyway, but worth knowing for next time.

Good to know

A model being listed as "available" in a region and that model actually working the same way in that region are two different things. Always test each region for real — don't assume a second region behaves exactly like the first one just because the setup looks identical.

11

Health checks + a documented backup plan for the web address

adi-1-2-primary/secondary-health-check · GET /health (both regions)

In plain terms: Amazon Route 53 is AWS's system for directing web traffic to the right place, including automatically checking whether a server is still responding ("health checks") and rerouting customers to a backup if it isn't.

What was built: Added a simple "are you alive?" web address to both regions, then set up 2 real Route 53 health checks watching them continuously. The full plan for automatically switching customer traffic over to the backup region the moment the main one fails is written down in detail, but not actually turned on — turning it on for real needs a registered website address (a domain name) belonging to the company, which this test account doesn't have.

Where to check: Console → Route 53 → Health checks; repo — route53-failover-pattern.md for the exact setup that would go live the moment a real domain name is added.

Why it matters: Covers what's actually possible to build without buying a domain name just for a test project. The health checks themselves are real and fully working, and are exactly what the automatic switch-over would plug into the moment that one missing piece — an actual domain — exists.

Error 4 · New web address took a minute to go live

What happened: Both newly created health-check web addresses returned an error right after being set up, even though everything looked correctly configured on paper.

Fix: waited about 30–60 seconds and it started working on its own, with no changes needed. New AWS resources sometimes take a short moment to fully come online, even after the console shows them as created.

Phase 4

Custom Training

Teach a model the bank's own style of question, and be honest about exactly where this project chose to stop.

12

Write training examples

adi-1-2-finetuning-data (S3) · 35 examples

In plain terms: "Fine-tuning" means taking a general AI model and giving it extra training on examples from one specific topic, so it gets noticeably better and more consistent at that one topic — without having to build a brand-new AI model from scratch.

What was built: Wrote 35 example question-and-answer pairs about banking topics not already covered in Step 2's test questions — things like wire transfers, disputing a charge, and credit scores — each one written in the same consistent tone the assistant should always use, and saved them to S3 (the same storage service explained in Task 1.1's Step 2).

Where to check: S3 → adi-1-2-finetuning-data.

Why it matters: Fine-tuning teaches a model a consistent style by example, so that style becomes automatic in every answer — instead of having to explain the same tone and formatting rules in every single question sent to the model.

13

Train a custom model — blocked, worked around, then finished properly

SageMaker: adi-1-2-finetune-financial-qa · Bedrock: adi-1-2-nova-micro-financial-qa

In plain terms: Amazon SageMaker is AWS's dedicated machine-learning platform — more flexible and more hands-on than Bedrock, but also more work to set up, since you're managing your own training computer. Bedrock also has its own simpler, built-in fine-tuning feature for certain models, which manages all of that for you.

What was built: Started with Amazon SageMaker, the tool the assignment specifically asked for, and had everything fully ready to go — the training script, the permissions, all of it. Hit a wall on the first attempt (below) and, rather than wait on an unpredictable AWS review queue, switched to Bedrock's own built-in fine-tuning feature as a working stand-in, training a specially-adapted version of Nova Micro — the same model already picked as the overall winner back in Phase 1. That Bedrock job completed successfully. Then, 8 days later, the original SageMaker blocker cleared on its own — AWS approved the limit increase in the background — so the original SageMaker job was re-launched exactly as first designed, and it also completed successfully.

Where to check: Console → Amazon SageMaker → Training → Training jobs (the primary result); Console → Amazon Bedrock → Custom models → Training jobs (the working stand-in, kept as a second, real example).

Why it matters: Delivers exactly what the assignment asked for — a model trained specifically for this bank's own questions, using SageMaker as instructed. Keeping the Bedrock version around too shows both real AWS paths for the same goal actually work, not just the one that happened to succeed first.

Error 5 · New accounts start with zero training capacity

What happened: Trying to start the SageMaker training job failed immediately. AWS said the allowed number of training computers for this account was zero — and checking further, that was true for every single size of training computer available, not just the one first tried.

Fix (at the time): asked AWS to raise that limit. Both requests went into a manual review queue with no guaranteed timeline — possibly hours, possibly much longer. Rather than sit and wait on an unpredictable queue, the step was switched over to Bedrock's built-in fine-tuning tool instead, which didn't have this limit.

Update, 8 days later · the SageMaker limit was approved

Checking back in, both requests showed as closed, and the actual account limit had gone from 0 to 20 training computers for both sizes originally requested — AWS's review had quietly finished in the background. Re-ran the exact same SageMaker job that failed in Error 5, with nothing changed. It worked immediately, no ResourceLimitExceeded this time.

The job finished in about 3 minutes 39 seconds on a small computer (ml.m5.xlarge), for a total training cost of roughly 1-2 cents — right in line with the estimate given before this was ever blocked. The Bedrock version built while waiting is kept as a documented, working alternative, but this SageMaker job is now the main answer for this step.

Good to know

A brand-new AWS account often starts with a training-computer limit of zero for SageMaker, no matter how small the request is. This isn't a broken permission or a mistake in setup — it's a safety limit that has to be specifically raised by asking AWS, and that request can take an unpredictable amount of time to actually get approved. It's worth having a backup plan (like the Bedrock path here) rather than just waiting idle, but also worth checking back later — the original approach can still turn out to be the better one once the blocker clears.

14

Turn the custom model on for real use

Planned, not built

Would update: model_selection_strategy.json · AppConfig

In plain terms: A custom-trained model — whether it's the Bedrock one or the SageMaker one from Step 13 — can't be used the normal pay-as-you-go way. Bedrock needs something called Provisioned Throughput; SageMaker needs something called a real-time endpoint. Both work the same way underneath: a dedicated slot that's reserved and paid for by the hour, whether or not it's actually being used, similar to renting a parking space for a month instead of paying per visit.

What this would have involved: Turn on the trained model for live use (either the Bedrock or the SageMaker version), add it as an option in the Step 5 settings file (no code changes needed, since the model-picker program already reads its choice from settings), re-run the Step 3 comparison to check whether it's actually better than the general-purpose model, and if so, make it the new default — with the old settings still saved, so undoing the switch would be instant.

Why it wasn't built: Turning on a custom-trained model for live use costs money every hour it's switched on — roughly $4 to $50 an hour for Bedrock, or the price of a dedicated SageMaker server for the SageMaker version, whether or not anyone's actually using it — instead of the pay-per-question pricing used everywhere else in this project. That's a real ongoing cost, and the decision was made to stop here rather than spend on that just for a test project.

15

Automatic testing before switching models

Planned, not built

Would reuse: the same test-suite pattern from Task 1.1

What this would have involved: An automatic test (using the same test-suite pattern built for Task 1.1's Step 13) that runs the Step 3 comparison questions against both the old model and the new custom-trained one, and only switches the live settings over to the new model if it actually scores better on every single measure — not just better on average. Undoing a bad switch would simply mean going back to the previously saved settings, the same instant-rollback idea as Step 14.

Why it wasn't built: This step only makes sense once Step 14's custom model is actually switched on for live use, which didn't happen for the cost reason explained above — there was nothing yet to test against.
