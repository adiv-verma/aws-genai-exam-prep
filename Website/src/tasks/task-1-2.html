Step-by-Step Build Log

Every step, in the order it happened

Kept to one topic on purpose — a bank's customer questions about everyday products like savings accounts and credit cards — to keep things simple to build and test. The last two steps were fully planned but not built; Phase 4 explains why.

Phase 1

Comparing the Models

Test 3 AI models on the same questions and score them

1

Check that 3 models actually work

Claude Haiku 4.5 · Nova Lite · Nova Micro

What: Sent a real test message to each of the 3 candidate models to confirm they respond. A 4th model, Claude Sonnet 5, was tried and dropped since it wasn't available yet.

Where to check: AWS Console → Amazon Bedrock → Model access.

Why: A fair comparison needs models from more than one company, not just different sizes of the same one. Anthropic (Claude) and Amazon (Nova) gives a real side-by-side comparison.

2

Write test questions

data/benchmark_test_cases.json · 12 normal questions + 5 tricky ones

What: Wrote 12 everyday banking questions with a correct-answer example for each, plus 5 tricky questions designed to see if the AI does something it shouldn't (like giving investment advice or asking for a password).

Where to check: repo — data/benchmark_test_cases.json.

Why: Gives the comparison something concrete to grade against, instead of just eyeballing the answers.

3

Run the comparison

benchmark.py

What: A script that asks all 3 models all 17 questions, times each answer, works out the cost, and uses a 4th AI call to grade each answer's quality and safety.

Where to check: repo — benchmark.py, data/model_evaluation_results.csv.

Why: Covers all 4 things the assignment asked to compare: answer quality, speed, cost, and safety — with a script that can be re-run any time, not a one-off manual check.

Good to know

Using one of the 3 models to also grade the others is a bit like a student grading their own test — it's not perfectly fair. It was still used here because a stronger, independent grading model wasn't available on this account, but it's worth knowing about as a limit of this approach.

4

Pick a winner

data/model_selection_strategy.json · winner = Nova Micro

What: Combined the 4 scores into one overall number, weighted toward quality and safety since this is a bank. Result: Nova Micro came out on top, then Nova Lite, then Claude Haiku 4.5. All 3 gave almost equally good answers, so the fastest and cheapest one won.

Where to check: repo — data/model_selection_strategy.json.

Why: This file is exactly what gets loaded into the settings system in Step 5 — the model actually used in production is the one the test results, not a guess, pointed to.

Good to know

All 3 models handled the tricky safety questions correctly, just from good instructions — no extra safety tool was added yet. A real bank system would still want a dedicated safety layer as backup, since instructions alone can sometimes be tricked.

Phase 2

Auto-Switching Between Models

A settings file decides which model to use, no code changes needed

5

A settings file for which model to use

adi-1-2-model-config · Production · ModelSelectionStrategy

What: Set up AWS AppConfig, a service for storing settings separately from code, and loaded the winning model choice from Step 4 into it.

Where to check: Console → AWS AppConfig → adi-1-2-model-config → Production.

Why: This is what makes "switch to a different model" a settings change instead of a code change — safer, faster, and it can be undone instantly if something goes wrong.

6

Permissions for the model-picker program

adi-1-2-bedrock-lambda-role

What: A permission set allowing only the 3 approved models to be called, and only this task's settings file to be read.

Where to check: IAM → Roles → adi-1-2-bedrock-lambda-role.

Why: Keeps this program's access as narrow as possible — it can only do exactly what it needs to.

Error 1 · Slightly wrong permission name

What happened: Used a permission name that seemed right based on which web address the settings service uses behind the scenes — but access was still denied.

Fix: the real error message named the exact permission needed, which turned out to be spelled a bit differently than expected. Fixed the permission name and it worked.

Good to know

An AWS service's web address and its permission name don't always match. When permission is denied, the error message itself usually names the exact permission needed — better to trust that than guess from the service name.

7

The model-picker program

adi-1-2-model-abstraction

What: A small program (Lambda function) that reads the settings file, picks the right model, asks it the question, and sends back the answer. On purpose, it doesn't try to handle failures itself — that's a separate job, done in Phase 3.

Where to check: Lambda → adi-1-2-model-abstraction → Monitor tab.

Why: This is the piece that makes "which model to use" a live setting instead of something baked into the code.

Error 2 · Only understood one kind of request

What happened: Found before Step 9 — the program only knew how to read requests shaped like a website request. A request from a different source (like the backup-plan flowchart) would have been silently ignored.

Fix: updated it to understand both shapes of request, and re-deployed before it was needed.

8

A web address customers can call

adi-1-2-api · POST /generate · prod stage

What: Set up a public web address that forwards requests straight to the Step 7 program. Tested it for real from outside AWS, not just from within the console.

Where to check: Console → API Gateway → adi-1-2-api → Stages → prod.

Why: This is what makes the assistant something a real app can actually call over the internet, finishing the "ask a question, get an answer" path end to end.

Phase 3

Staying Up If Something Fails

A backup plan, a second copy in another region, and real health checks

9

The backup plan (circuit breaker)

adi-1-2-circuit-breaker-sm

What: Built a flowchart: try the main model, and if that fails, try a backup model, and if that fails too, show a safe canned reply instead of an error. Added a way to fake a failure on purpose, specifically to prove each fallback step actually works.

Where to check: Step Functions → adi-1-2-circuit-breaker-sm → Executions.

Why: A clear, visible failover plan instead of hidden error-handling in code. Tested and confirmed all 3 outcomes really happen: normal answer, backup-model answer, and safe canned reply.

Good to know

It's not enough to write a flowchart that "should" fall back correctly — actually forcing a failure and watching it happen is the only way to be sure the fallback logic really works, not just that it looks right on paper.

10

A second copy in another region

adi-1-2-cross-region-stack (CloudFormation)

What: Deployed a full second copy of the system in a different AWS region (Oregon), with its own settings file — not one that calls back to the first region, since that would defeat the purpose if the first region went down.

Where to check: Console → CloudFormation → Stacks → adi-1-2-cross-region-stack (region: Oregon).

Why: If one AWS region has an outage, the system needs its own independent copy elsewhere to keep working — not just a code copy that still depends on the region that's down.

Error 3 · Same model works differently in a different region

What happened: Nova Micro showed as available in the new region, but calling it failed anyway, asking for a different kind of model ID.

Fix: found the right ID format for that region and updated the settings and permissions to match. Confirmed it then worked correctly.

Minor · A "stop" button didn't do what it sounded like

What happened: Tried to quickly finish an in-progress settings update using what looked like a "stop and finish" button.

Fix: it actually undoes the update instead of finishing it early. No harm here since a newer update was applied right after, but worth knowing for next time.

Good to know

A model being "available" in a region and a model actually working the same way in that region are two different things. Always test for real in each region — don't assume it behaves like the first one.

11

Health checks + a documented backup plan for the web address

adi-1-2-primary/secondary-health-check · GET /health (both regions)

What: Added a simple "are you alive?" check to both regions, then set up 2 real Route 53 health checks watching them. The full plan for automatically switching customer traffic to the backup region is written down, but not turned on — that needs a company's own website address, which this test account doesn't have.

Where to check: Console → Route 53 → Health checks; repo — route53-failover-pattern.md for the exact setup that would go live the moment a real domain is added.

Why: Covers what's actually possible to build without buying a domain name just for a test project. The health checks are real and ready to be used the moment that piece exists.

Error 4 · New web address took a minute to go live

What happened: Both new health-check web addresses returned an error right after being created, even though everything looked correctly set up.

Fix: waited about 30–60 seconds and it started working on its own. New AWS resources sometimes take a short moment to become fully live.

Phase 4

Custom Training

Training data, a real training job, and where this task stopped

12

Write training examples

adi-1-2-finetuning-data (S3) · 35 examples

What: Wrote 35 example question-and-answer pairs about banking topics not already covered in Step 2's test questions (wire transfers, disputes, credit scores, and more), each written in the same tone the assistant should always use.

Where to check: S3 → adi-1-2-finetuning-data.

Why: Fine-tuning means teaching the model a consistent style by example, so that style becomes automatic — instead of having to explain it in every single question.

13

Train a custom model — switched tools partway through

amazon.nova-micro-v1:0:128k → adi-1-2-nova-micro-financial-qa

What: Started with Amazon SageMaker, the tool the assignment specifically asked for, and had everything ready to go. Hit a wall (below) and switched to Bedrock's own built-in training tool instead, training a special version of Nova Micro — the same model already picked as the winner in Phase 1.

Where to check: Console → Amazon Bedrock → Custom models → Training jobs.

Why: Still delivers what the assignment asked for — a model trained specifically for this bank's questions — just through a different, and arguably simpler, AWS tool. The training finished successfully.

Error 5 · New accounts start with zero training capacity

What happened: Trying to start the SageMaker training job failed right away: AWS said the allowed number of training computers for this account was zero — for every size of computer available, not just one.

Fix: asked AWS to raise that limit. Both requests went into a manual review queue with no fixed wait time — possibly hours, possibly longer. Rather than wait on that, switched the whole step over to Bedrock's built-in training instead.

Good to know

A brand-new AWS account often starts with zero allowed usage for SageMaker training, no matter how small the request. This isn't a broken permission — it's a limit that has to be raised by asking AWS, and that request can take an unpredictable amount of time to get approved.

14

Turn the custom model on for real use

Planned, not built

Would update: model_selection_strategy.json · AppConfig

What this would have been: Switch on the newly trained model for live use, add it as an option in the settings file from Step 5 (no code changes needed, since the model-picker program already reads its choice from settings), re-run the Step 3 comparison to see if it's actually better, and if so, make it the new default — with the old settings still saved, so undoing it is instant.

Why it wasn't built: Turning on a custom-trained model for live use isn't pay-per-question like everything else in this project — it needs a dedicated, always-on slot that costs money every hour it's switched on, whether or not anyone's using it (roughly $4–50 an hour). That's a real ongoing cost, and the decision was made to stop here rather than spend on that for a test project.

15

Automatic testing before switching models

Planned, not built

Would reuse: the same test-suite pattern from Task 1.1

What this would have been: An automatic test that runs the Step 3 comparison questions against both the old and new model, and only switches the settings file to the new one if it actually scores better on every measure — not just on average. Undoing a bad switch would just mean going back to the previous saved settings.

Why it wasn't built: This step only makes sense once Step 14's custom model is actually switched on for live use, which didn't happen for the cost reason above.
