Step-by-Step Build Log

Every step, in the order it happened

Scoped to a single narrowed scenario — personal-banking product Q&A for a financial-services assistant — per the brief's own "start narrow" advice. The last two steps were designed in full but deliberately not executed; see why in Phase 4.

Phase 1

FM Assessment & Benchmarking

Live-test access, build a test set, score 3 candidates on 4 axes

1

Confirm access for 3 benchmark candidates

Claude Haiku 4.5 · Nova Lite · Nova Micro

What: Live-tested bedrock-runtime converse for each. Claude Sonnet 5 was also tried and dropped — still not entitled on this account, same as Task 1.1.

Where: Console → Amazon Bedrock → Model access.

Why: A meaningful benchmark needs more than one model provider, not just two Claude tiers — Anthropic + Amazon gives a real cross-provider quality/latency/cost comparison.

2

Financial-domain benchmark dataset

data/benchmark_test_cases.json · 12 QA + 5 compliance cases

What: 12 personal-banking QA pairs with ground-truth answers, plus 5 compliance cases (unauthorized investment advice, guaranteed returns, credential/PII sharing, competitor disparagement, prompt injection) each with an expected_behavior.

Where: repo — data/benchmark_test_cases.json.

Why: Gives the benchmark concrete ground truth to score quality against, and concrete pass/fail criteria for the guardrail-compliance axis.

3

Benchmark script: latency, cost, LLM-as-judge quality

benchmark.py

What: Runs via the aws CLI (no boto3 in this environment). Measures latency and per-request cost (published token pricing) for all 3 models on all 17 cases, and uses Claude Haiku 4.5 as an LLM-as-judge for QA quality and compliance pass/fail.

Where: repo — benchmark.py, data/model_evaluation_results.csv.

Why: Covers all 4 of the brief's comparison axes with a re-runnable script, not a one-time manual check.

Exam tip

Using one of the candidates as its own judge risks mild self-preference bias — a real limitation, accepted here because no stronger independent judge (Sonnet 5) was accessible on this account. The same judge across all 3 candidates keeps the relative ranking fair even if the absolute scores aren't perfectly independent.

4

Analysis & model-selection strategy

data/model_selection_strategy.json · primary = Nova Micro

What: Weighted score (quality 0.40, compliance 0.30, latency 0.20, cost 0.10) across the 3 candidates. Result: Nova Micro (0.917) > Nova Lite (0.902) > Claude Haiku 4.5 (0.700) — quality was nearly saturated across all 3 (4.92–5.00/5), so latency and cost ended up the real differentiators.

Where: repo — data/model_selection_strategy.json.

Why: This exact file is what Step 5's AppConfig deployment is seeded from — the production routing decision is the one the benchmark actually justified.

Exam tip

All 3 models passed every compliance case at the prompt-instruction level alone — no Guardrail resource exists in this task. A real deployment would still want an independent Guardrail layer (per Task 1.1's own conclusion) rather than relying on prompt instructions as the only defense.

Phase 2

Dynamic Model-Selection Architecture

AppConfig-driven routing behind a Lambda and API Gateway

5

AWS AppConfig for model-selection rules

adi-1-2-model-config · Production · ModelSelectionStrategy

What: Application → Production environment → AWS.Freeform configuration profile (not AWS.AppConfig.FeatureFlags, despite the brief's own sample CLI using that type — the payload is a full strategy object, not on/off flags). Deployed Step 4's strategy JSON as version 1 via the predefined AppConfig.AllAtOnce strategy.

Where: Console → AWS AppConfig → adi-1-2-model-config → Production.

Why: Safe, monitored, gradual rollout — changing the primary model later is a new configuration version, not a Lambda redeploy, and a bad change is catchable/rollback-able during the bake window.

6

IAM role for the model-abstraction Lambda

adi-1-2-bedrock-lambda-role

What: Least-privilege: bedrock:InvokeModel/Converse scoped to exactly the 3 candidate models, plus appconfig:StartConfigurationSession/GetLatestConfiguration scoped to this task's AppConfig profile.

Where: IAM → Roles → adi-1-2-bedrock-lambda-role.

Why: The shared execution role for this task's Lambda pipeline.

Bug 1 · Wrong IAM action namespace for AppConfig data-plane calls

Symptom: First policy used appconfigdata:StartConfigurationSession/GetLatestConfiguration — a reasonable guess, since config-retrieval calls do hit a separate appconfigdata.<region>.amazonaws.com API endpoint. Live Lambda test threw AccessDeniedException anyway.

Fix: the real error named the actual required action: appconfig:StartConfigurationSession — the IAM action namespace stayed appconfig: even though the runtime endpoint is appconfigdata. Corrected both actions; confirmed via iam simulate-principal-policy before re-testing live.

Exam tip

A service's control-plane/data-plane API endpoint split doesn't always imply a matching IAM action-namespace split. The authoritative source is the real AccessDeniedException message, not the SDK client name.

7

Lambda: model abstraction layer

adi-1-2-model-abstraction

What: Reads the AppConfig strategy (session cached per warm container), selects a model by use_case (falling back to primary_model), invokes Bedrock Converse, returns {model_used, response, latency_ms}. Deliberately no retry/fallback logic of its own — that's Phase 3's job.

Where: Lambda → adi-1-2-model-abstraction → Monitor tab.

Why: The brief's "model abstraction layer" — which model gets called becomes a runtime AppConfig lookup, not something baked into client code.

Bug 2 · Only parsed API-Gateway-shaped events

Symptom: Found before Step 9 — the handler assumed event["body"] was always a JSON string. A direct Step Functions/Lambda invocation with a plain JSON payload would have silently dropped the request.

Fix: added a _parse_body() helper that accepts either an API Gateway proxy event or a plain JSON payload, and redeployed before Step 9 needed it.

8

API Gateway for client access

adi-1-2-api · POST /generate · prod stage

What: REST API, AWS_PROXY integration to the Step 7 Lambda, deployed to prod. Live-tested the actual public HTTPS endpoint with curl, not just lambda invoke.

Where: Console → API Gateway → adi-1-2-api → Stages → prod.

Why: Makes the assistant callable by a real client over plain HTTPS — closes out the "prompt in, response out" path end to end.

Phase 3

Resilient System Design

Circuit breaker, a second live region, and real health checks

9

Step Functions circuit breaker

adi-1-2-circuit-breaker-sm

What: TryPrimaryModel → TryFallbackModel → GracefulDegradation, matching the brief's own example structure. Two new Lambdas built for the fallback and degradation stages; added fault-injection flags (simulate_primary_failure, simulate_fallback_failure) specifically to prove each Catch branch actually fires.

Where: Step Functions → adi-1-2-circuit-breaker-sm → Executions.

Why: A deterministic, inspectable failover graph, tested for all 3 real outcomes via get-execution-history: normal (primary only), forced-primary-failure (falls to Nova Lite), forced-both-failure (canned degraded response, no Bedrock call).

Exam tip

The brief's own sample ASL retries and catches on States.TaskFailed for everything. A Lambda's own unhandled exception actually surfaces as Lambda.Unhandled/the exception class name, not literally States.TaskFailed — this build scoped Retry only to genuine transient Lambda service errors, and used broad States.ALL for Catch, so a real function-code error routes to fallback immediately instead of being retried twice first.

10

Cross-region deployment (us-west-2)

adi-1-2-cross-region-stack (CloudFormation)

What: A second, fully independent AppConfig replica in us-west-2 (not a cross-region call back to us-east-1 — that would defeat the point), deployed via CloudFormation, reusing the existing global IAM role rather than duplicating it (IAM roles aren't regional).

Where: Console → CloudFormation → Stacks → adi-1-2-cross-region-stack (region: Oregon).

Why: "Cross-region model deployment for high availability" — the secondary region needs its own configuration source to actually survive a primary-region outage, not just a code copy.

Bug 3 · Same model, different on-demand availability by region

Symptom: Nova Micro showed ACTIVE in list-foundation-models --region us-west-2, but the first live call failed: ValidationException: ...on-demand throughput isn't supported...use an inference profile — even though the bare model ID worked fine for the exact same model in us-east-1.

Fix: confirmed via list-inference-profiles that us.amazon.nova-micro-v1:0/nova-lite-v1:0 profiles exist in us-west-2. Deployed a region-specific strategy variant using those profile IDs, and extended the IAM role.

Minor · stop-deployment on a baking AppConfig deployment rolls back, doesn't finish early

Symptom: Needed to start deploying strategy v2 while v1 was still in its 10-minute BAKING window; stop-deployment seemed like "finish now."

Fix: it actually reverts to ROLLED_BACK, not "complete early." Harmless here since v2 immediately superseded it — but not the right tool if the in-flight config actually needed to stay live.

Exam tip

"Listed as ACTIVE in this region" and "supports on-demand invocation in this region" are two different facts about a Bedrock model. A real multi-region design has to verify both, per region — not assume the primary region's behavior carries over.

11

Route 53 health checks + documented failover pattern

adi-1-2-primary/secondary-health-check · GET /health (both regions)

What: Added a GET /health mock route (no Lambda/Bedrock dependency) to both regional APIs, then created 2 real Route 53 health checks against them. The actual failover A/alias record set is documented, not deployed — this AWS account has no registered domain to attach one to.

Where: Console → Route 53 → Health checks; repo — route53-failover-pattern.md for the exact record set that would go live the moment a domain exists.

Why: "Set up Route 53 for cross-Region routing" — scoped honestly to what's actually deployable without buying a domain for a PoC. Nothing here is throwaway; the health checks are the real piece a failover record would reference.

Bug 4 · API Gateway deployment propagation lag

Symptom: Both new /health endpoints returned 403 MissingAuthenticationTokenException immediately after deployment, despite test-invoke-method and the deployment's own snapshot confirming the route was configured correctly.

Fix: resolved on its own after roughly 30–60s — the same propagation-lag pattern already seen for IAM (Step 6) and in Task 1.1 (trail creation). A resource being "created" and "actually live at the edge" are different moments.

Phase 4

Model Customization & Lifecycle

Fine-tuning data, a real training job, and where this task chose to stop

12

Financial-domain fine-tuning dataset

adi-1-2-finetuning-data (S3) · 35 examples

What: 35 synthetic {prompt, completion} pairs covering personal-banking topics beyond the benchmark set (wires, disputes, POA, IRA limits, PMI, HELOC, credit utilization), each completion written in the same consistent tone/structure the assistant already uses — the actual point of fine-tuning is instilling that style so it's baked in, not re-specified per prompt.

Where: S3 → adi-1-2-finetuning-data.

Why: "Prepare a fine-tuning dataset" — a real, checked-in training set, format-agnostic to the eventual platform choice.

13

Fine-tuning job — SageMaker blocked, pivoted to Bedrock

amazon.nova-micro-v1:0:128k → adi-1-2-nova-micro-financial-qa

What: Started with SageMaker (the brief's literal instruction) — training script, IAM role, and a packaged distilgpt2 job on a cheap CPU instance were all fully staged. Pivoted to Bedrock Custom Model fine-tuning after hitting a real account-level blocker (below), launching a job on amazon.nova-micro-v1:0:128k — the fine-tunable customization variant of the exact same model this task already benchmarked and picked as primary.

Where: Console → Amazon Bedrock → Custom models → Training jobs.

Why: "Fine-tune a model for financial domain" — still the same deliverable, via Bedrock's managed path instead of self-managed training, and arguably more idiomatic for a Bedrock-Converse-centric build like this one.

Bug 5 · SageMaker training-instance quotas default to 0 on an unused account

Symptom: create-training-job failed immediately: ResourceLimitExceeded: ...'ml.m5.xlarge for training job usage' is 0 Instances. Checked broadly across every training instance type (including smaller ones like ml.m5.large) — all 0, confirming it isn't size-dependent.

Fix: submitted Service Quotas increase requests; both moved to CASE_OPENED (manual AWS review, unpredictable timeline — hours to longer, not minutes) rather than auto-approving. Rather than wait on an unbounded queue, pivoted the whole step to Bedrock fine-tuning instead.

Exam tip

Unlike most EC2-family quotas, SageMaker training-job instance quotas start at 0 for an account that's never run a training job — regardless of instance size. A ResourceLimitExceeded here means "file a Service Quotas request," not an IAM or config fix, and that request can land in a manual review queue with no guaranteed turnaround.

14

Model versioning + deployment workflow

Designed, not built

Would extend: model_selection_strategy.json · AppConfig

What it would have been: Provision Bedrock Provisioned Throughput for the Step 13 custom model, add a "financial_qa_specialist" entry to the AppConfig strategy so adi-1-2-model-abstraction could route to it with zero Lambda code changes, re-run the Step 3 benchmark against it for a real before/after comparison, then promote via a new AppConfig deployment version — the same safe-rollout mechanism already used in Step 5.

Why not built: Bedrock custom models cannot run on the normal pay-per-request tier at all — they require Provisioned Throughput, billed hourly per model unit (roughly $4–50/hr, no on-demand alternative), the first cost commitment in this task that isn't pay-per-request. Stopped here rather than spend on that for a PoC, by explicit choice.

15

Automated testing + rollback

Designed, not built

Would reuse: Task 1.1's validator-Lambda + Step Functions Map pattern

What it would have been: A Step Functions test harness running the Step 3 benchmark's 17 test cases against both the base and fine-tuned models, gating promotion so AppConfig only gets updated if the fine-tuned model beats the base model's scores on every axis, not just on average. Rollback would be identical to Step 14's mechanism — AppConfig's own version history.

Why not built: Directly depends on Step 14's custom model actually being live behind Provisioned Throughput, which this task stopped short of for the same cost reason.
