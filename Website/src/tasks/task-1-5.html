The brief's full 6-phase build calls for chunking, embedding, three parallel provisioned vector stores to benchmark against each other, hybrid/rerank search on top of that, query decomposition, and an API layer. This build takes the first two phases all the way to real, verified results — a Lambda that chunks the same source documents three different ways, and a Lambda that embeds every chunk with two different models — while deliberately leaving the vector-store shootout and everything built on top of it as a documented plan, not a deployment. Phase 1

Document Processing & Segmentation

Sample data, storage, permissions, and a Lambda that chunks the same documents three different ways.

1

Storage, sample documents, and permissions

adi-1-5-documents-269737522732 · adi-1-5-lambda-role

In plain terms: Before any chunking or embedding logic can be tested, it needs real text to run against. The brief's own example is AWS technical documentation, not the law-firm scenario used on this task's Study Notes page — those are two intentionally separate things, the same split Task 1.4 makes between its own build and its notes page.

What was built: An S3 bucket (versioned, all public access blocked), 6 hand-authored synthetic technical articles covering S3 storage classes, Lambda concurrency, DynamoDB capacity modes, Bedrock Knowledge Bases, OpenSearch vector search, and Step Functions — each with 4–5 distinct ## sections, written specifically so fixed-size chunking would sometimes cut mid-section while the other two strategies could recover section boundaries cleanly. Also hand-authored a 12-query test set, each query mapped to exactly which document and section should answer it (ground truth for a future evaluation step). An IAM role was created scoped to only S3 read/write on this one bucket and bedrock:InvokeModel on just the two embedding models used later — nothing broader.

Where to check: S3 → adi-1-5-documents-269737522732 → raw-docs/ (6 objects) and test-queries/ (1 object). IAM → Roles → adi-1-5-lambda-role.

Why it matters: Confirmed Bedrock embedding access already worked (both Titan and Cohere returned real vectors on a test call) before building anything else — unlike Task 1.4, which assumed model access might need requesting, this task verified it up front instead of guessing.

Good to know

The sample documents were deliberately written to make the three chunking strategies actually disagree with each other — multiple substantial sections per document, not one short paragraph. A trivially short test document would make every chunking strategy produce nearly identical output, which proves nothing about which strategy is actually better.

2

The chunking engine — three strategies, one Lambda

adi-1-5-chunking-engine

In plain terms: "Chunking" means splitting a document into smaller pieces before it can be searched or embedded — a whole document is usually too big and too unfocused to compare against a short question. How you draw those cut lines changes what actually gets retrieved later.

What was built: A Lambda, triggered automatically the moment a file lands in raw-docs/, that runs the same source document through three different chunking methods:

  • Fixed-size — cuts every 800 characters with 100 characters of overlap, nudged to the nearest sentence ending nearby. Simple, but blind to the document's actual structure.
  • Hierarchical — splits on the document's own ## headings, so each section becomes exactly one chunk. Structure-aware by construction.
  • Semantic — embeds every individual sentence with Titan, measures how similar each sentence is to the one right before it, and cuts wherever that similarity drops meaningfully below that specific document's own average (not one fixed number reused across every document, since raw similarity scores aren't comparable across different content).

Where to check: Lambda → adi-1-5-chunking-engine → Configuration → Triggers (shows the S3 event source); Monitor → Logs (6 invocations, zero errors). S3 → chunks/fixed/, chunks/hierarchical/, chunks/semantic/ — 33 + 36 + 30 chunks.

Why it matters: This is the actual exam-tested content of Phase 1 — not reading about the three strategies, but running identical source text through all three and seeing exactly where they agree and disagree.

What the results actually showed

On the S3 storage-classes document, fixed-size chunking visibly cut mid-sentence (one chunk literally starts mid-word, "ency and high throughput…"). Hierarchical recovered all 6 sections cleanly, one chunk per heading. Semantic chunking produced 5 chunks that mostly tracked section boundaries too — but it merged the "Standard-IA / One Zone-IA" section with the following "Glacier storage classes" section into a single chunk, because their content was similar enough in meaning (both are about lower-cost, infrequent-access storage tiers) that the similarity score never dropped enough to justify a split. A purely structural strategy would never make that call — that's a real, observed difference between "structure-aware" and "meaning-aware" chunking, not just a definition.

Good to know

"Semantic chunking" in the actual exam-tested sense means detecting topic shifts by comparing embedding similarity between consecutive sentences — it is not asking an LLM to creatively decide where to split text (which is one way it's sometimes implemented, but not the technique being tested here). Building the embedding-similarity version directly is what surfaced the section-merging behavior above; a prompt-based LLM splitter would likely have just followed the headings and never shown that trade-off at all.

Phase 2

Embedding Generation & Optimization

Turn every chunk from Phase 1 into vectors with two different embedding models, side by side.

3

The embedding generator — Titan and Cohere, side by side

adi-1-5-embedding-generator

In plain terms: An embedding is a list of numbers that represents what a piece of text means, generated by a model trained for exactly that purpose. Two different embedding models will produce different numbers for the same text, and won't necessarily agree on which two chunks are "similar" — that's why comparing them matters, not just picking one by reputation.

What was built: A Lambda, invoked manually rather than sitting behind any public endpoint (same "no idle cost" choice Task 1.4 planned for its own search-coordinator), that lists every chunk from all 3 strategies and embeds each one with both amazon.titan-embed-text-v1 (1,536 dimensions) and cohere.embed-english-v3 (1,024 dimensions). Titan only accepts one input per call, so it's looped one chunk at a time; Cohere natively accepts a batch, so those calls are grouped 20 texts at a time — a real, observable difference between the two APIs, not just a line in a comparison table.

Where to check: Lambda → adi-1-5-embedding-generator → Monitor → Logs (single invocation, {"titan": 99, "cohere": 99, "total_chunks": 99}). S3 → embeddings/titan/ and embeddings/cohere/ — 99 objects each, 198 total.

Why it matters: Produces the two embedding sets a future evaluation step would need to score Titan vs. Cohere head-to-head on identical chunk sets — and confirms both models actually work end-to-end against this project's own data, not just in an isolated test call.

What the results actually showed

All 198 embeddings (99 chunks × 2 models) generated successfully in about 27 seconds, with zero errors. The batch-vs-single-call difference showed up directly in the code, not just in documentation: Titan's API rejects more than one input text per call, while Cohere's texts parameter accepts a list — confirmed by building both paths against the real Bedrock endpoints, matching exactly what project.md's own sample code assumes.

Good to know

Batching isn't just a performance optimization here — it changes how many billed API calls happen. 99 chunks through Titan is 99 separate invoke_model calls; the same 99 chunks through Cohere is 5 calls (99 ÷ 20, rounded up). At this project's tiny scale the cost difference is pennies either way, but the same ratio at real production volume (millions of chunks) is the difference between millions of calls and tens of thousands.

Evaluation & Phases 3–6

Scored on purpose, then deliberately left as a plan

Phases 1–2 above already produced the useful part of this task for free — real chunking divergence and real embeddings from two models, with zero provisioned infrastructure. What follows is what would come next, and exactly why it's documented rather than deployed.

Why the vector-store comparison (Phase 3) stays a plan, not a deployment

project.md's Phase 3 asks for three parallel provisioned or managed vector stores at once, purely to benchmark them against each other: an OpenSearch Service domain (the brief's own config is 2 data nodes plus 3 dedicated master nodes — 5 nodes total), Aurora PostgreSQL with the pgvector extension, and a Bedrock Knowledge Base backed by OpenSearch Serverless. This is the same cost profile that kept Task 1.4 at plan-only — just with a third always-billing service added on top.

Bedrock Knowledge Base (min. OCU floor)~$1/hr~$700
OpenSearch domain (brief's own 5-node config)~$0.84/hr~$600
Aurora PostgreSQL + pgvector (provisioned instance)~$0.08–0.29/hr~$60–210

Phases 4–6 (hybrid search tuning, query decomposition via Step Functions, an API integration layer) all sit on top of whichever store Phase 3 stands up, so they inherit the same call. All of it is covered conceptually on the Study Notes page already.

Retrieval evaluator — brute-force search, no vector database

Planned, not built

Would create: adi-1-5-retrieval-evaluator

In plain terms: A vector store is really just an index over embeddings that makes similarity search fast at scale. For a corpus this small (99 chunks), comparing a query's embedding against every stored chunk embedding directly — a brute-force linear scan — finds the exact same "most similar" result a managed vector database would, just without needing one deployed. Managed indexes (OpenSearch's HNSW, for example) only start to matter once brute-force search would take too long, which is a scale problem, not an accuracy problem.

What this would involve: A Lambda, manually invoked, that for each of the 6 (strategy × embedding model) combinations from Phases 1–2: embeds each of the 12 test queries, runs cosine-similarity search across that combination's 99 stored chunk embeddings in S3, checks whether the correct section (from the Step 1 ground-truth file) came back in the top results, and computes Hit-Rate@3 and Mean Reciprocal Rank per combination — plus a pure embedding-quality check comparing Titan vs. Cohere on known-similar and known-dissimilar chunk pairs.

Why it wasn't built: Not a cost concern this time — brute-force search over 99 embeddings costs nothing to run. Left as a documented next step because Phases 1–2 already delivered concrete, verifiable results (the chunking divergence and the batch-vs-single-call embedding difference above) without it; scoring which of the 6 combinations retrieves best is the natural next session's work if this task gets picked back up.

Three-way vector store deployment, hybrid search, query decomposition, API layer

Architecture only

What this would have involved: Standing up OpenSearch Service, Aurora + pgvector, and a Bedrock Knowledge Base against the same document set, benchmarking query latency/recall across all three; layering hybrid (vector + BM25) search and a reranker on top of whichever store won; a Lambda/Step Functions pipeline for expanding and decomposing complex multi-part queries; and a standardized API layer with function-calling support for foundation-model integration.

Why it wasn't scoped for a live build: Three concurrent pay-by-the-hour services purely to compare them is the exact pattern this project has consistently avoided (see Task 1.4). All of it — store trade-offs, hybrid search, query decomposition, MCP/function-calling integration — is already covered conceptually on this task's Study Notes page.
