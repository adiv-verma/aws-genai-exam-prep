Domain 2 · Task 2.1

Agentic Customer
Support System

An internet service provider wants support handled by agents that reason with real tools, remember customers across turns, coordinate several foundation models, protect themselves from runaway loops and failing dependencies, and stop for a human before doing anything expensive. Built and live-tested end to end across all five parts of the brief — including six defects found along the way, three of them in the reference material itself. Study notes for this task →

Part 1 of the brief could not be built as written — Bedrock Agents is closed to new accounts

create-agent was rejected outright: "Bedrock Agents is in Maintenance Mode. New agent creation is not available for accounts without prior service usage." This account had never created one, so it falls on the wrong side of that grandfather clause — and no IAM change or quota request gets around it. Amazon Bedrock AgentCore is the successor and is available here.

Rather than skip Part 1, the agent loop was written out by hand with the bedrock-runtime Converse API — the same Reason → Act → Observe cycle a managed agent runs internally — with memory in DynamoDB. That turned out to be the more instructive version: every part the managed service hides is visible and tunable. It is also what the study notes prescribe, since Section 1.5 names DynamoDB explicitly for all three memory tiers, and Section 6 asks for a GSI design a managed memory service would have hidden.

Worth carrying into the exam: an answer naming classic Bedrock Agents for a greenfield build is now describing a service new accounts cannot provision.

Step-by-Step Build Log

Every step, in the order it happened

Everything here is pay-per-use — on-demand Bedrock calls, Lambda, Step Functions Standard, and DynamoDB on-demand. No provisioned capacity, no container, no hourly-billed resource anywhere in the build. Standing cost when idle is effectively zero.

Phase 0

Foundations

Prove model access before building on it, then the two IAM roles everything else assumes.

1

Verify model access and replace the brief's retired models

Claude Haiku 4.5 · Claude Sonnet 4.5 · Amazon Nova Micro

In plain terms: Every model named in the brief has been retired. Checking that a model actually answers takes five seconds; discovering it doesn't, three states deep into a workflow, takes considerably longer.

What was done: Invoked three candidate models with a minimal prompt. All answered. anthropic.claude-3-sonnet-20240229-v1:0 is no longer on-demand invocable and amazon.titan-text-express-v1 is retired entirely — only Titan embedding models remain. Replacements: Claude Haiku 4.5 as the default reasoning model, Claude Sonnet 4.5 as the escalation target, Amazon Nova Micro as the cheap classifier that replaces Titan Text.

Where to check: Bedrock → Model access (us-east-1), and Bedrock → Cross-region inference for the profile IDs.

Why it matters: Reference architectures written against a model ID go stale. Keeping the ID in configuration rather than in code is what makes the swap a one-line change.

Exam tip

No current Claude model on Bedrock supports a bare on-demand model ID. They all require a cross-region inference profile — a us. or global. prefix. "Why does InvokeModel fail with ValidationException on a model I can see in the console?" is an inference-profile question, not a permissions one.

2

IAM roles for the agent and the Lambdas

adi-2-1-agent-role · adi-2-1-lambda-role

In plain terms: An agent that gets talked into calling a destructive tool still cannot do anything the execution role was never granted. The boundary sits below the model, where no prompt can reach it.

What was built: Two roles, each with one tightly-scoped inline policy. The agent role trusts bedrock.amazonaws.com narrowed by aws:SourceAccount and aws:SourceArn — the confused-deputy guard. The Lambda role grants logs scoped to /aws/lambda/adi-2-1-*, invoke on exactly three models, DynamoDB item operations on table/adi-2-1-* with no dynamodb:*, no DeleteTable and no Scan, and Step Functions task-token callbacks.

Where to check: IAM → Roles → each role → Permissions tab and Trust relationships tab.

Why it matters: This is the study notes' Section 4, layer 1, made concrete: action groups are not security boundaries; IAM policies are.

Finding · Least privilege has a ceiling

The states:SendTaskSuccess statement uses Resource: "*", and that is not laziness — that API does not support resource-level permissions at all. The authorization is carried by the task token itself, a single-use secret issued per paused execution. So the control moves from IAM to protecting the token. Knowing which layer actually enforces a given operation matters more than reflexively writing narrow ARNs.

Exam tip

Granting an inference-profile ARN is not enough. The profile fans out to regional foundation-model endpoints and the call is authorized against those too. The us. Sonnet profile routes to us-east-1, us-east-2 and us-west-2 — omit those foundation-model/* ARNs and you get an AccessDeniedException naming a region you never configured.

Phase 1

The Agent and Its Memory

Tools first, then the three memory tiers, then the loop that ties them together.

3

Action group backend: tool Lambda and OpenAPI schema

adi-2-1-support-tools · adi-2-1-agent-schemas-269737522732

In plain terms: Three read-only tools — look up an account, check for an outage in an area, run a line diagnostic — plus a schema whose prose teaches the agent which to reach for and in what order.

What was built: A Python 3.12 Lambda behind an OpenAPI 3.0 schema in S3, with a resource policy letting only Bedrock invoke it. Sample data covers three accounts across three service areas with two active outages, deliberately rigged so the reasoning is visible: ACC-1001 has a degraded line and an area outage, so "reboot your modem" is the wrong answer; ACC-1002 is past due with a perfectly healthy line, so billing is the real cause.

Where to check: Lambda → adi-2-1-support-tools → Configuration → Permissions; S3 → adi-2-1-agent-schemas-269737522732.

Why it matters: The action group is the agent's hands. Building it before the brain means the agent has something real to call the moment it exists.

Exam tip

Design tool errors for the model, not for a log reader. An unknown account returns the valid alternatives alongside an error_class of fixable, retryable or fatal — so the agent self-corrects on the next turn instead of apologising to the customer. A bare 404 just ends the turn.

4–5

Path decision, then the three-tier memory hierarchy

adi-2-1-session-memory · adi-2-1-decision-scratchpad · adi-2-1-strategic-memory

In plain terms: Three tables, not because memory needs three technologies, but because the three kinds of memory have different lifetimes and get read in different ways.

What was built: Operational memory keyed on sessionId + turnTimestamp with a TTL; a tactical scratchpad keyed on caseId + stepId with a shorter TTL; and strategic memory keyed on patternKey + observedAt with no TTL and a GSI on issueCategory. All on-demand billing.

Where to check: DynamoDB → Tables → each table. TTL is under Additional settings; the GSI is under Indexes on the strategic table.

Why it matters: The sort key is chosen so "the last N turns of this conversation, in order" is a single Query with a Limit — no filter, no scan. Operational and tactical memory expire because a stale scratchpad is worse than none; strategic memory does not, because outliving the incident is the entire point of the tier.

Exam tip

A GSI is how you avoid paying for a Scan. When the question the business asks uses a different partition key than the write path does — "every billing issue this week" versus "what happened to this case" — that is the signal for a secondary index. Reaching for Scan with a filter instead is the wrong answer.

6

The agent loop, over the memory tiers

adi-2-1-support-agent

What was built: The Reason → Act → Observe loop written out explicitly. Converse with toolConfig returns either tool calls or a final answer; tool results are handed back and the loop repeats until the model stops or a hard iteration ceiling of 6 is hit. Prior turns are reloaded at the start of every invocation and written back with a 90-day TTL, so context survives across separate invocations.

Where to check: Lambda → adi-2-1-support-agent; DynamoDB → adi-2-1-session-memory, query a sessionId to see the turns.

Verified: ACC-1001 reported the fibre cut and restore time and correctly did not suggest rebooting. Asked "what plan am I on?" on a later invocation, it answered from memory with zero tool calls. ACC-1002 spent one tool call, not three — the schema description told it a past-due balance explains a dead connection on its own, so it never reached for the diagnostic.

Bug 1 · The agent confidently invented the customer's plan

What happened: Asked "remind me what plan I am on?" on turn 2, the agent answered "You're on the 100 Mbps plan." The real plan is Fibre 500 Mbps. No tool call, no hesitation.

Root cause: Operational memory stores the conversation — what the agent said out loud. Turn 1's answer was about the outage and never mentioned the plan, so turn 2's reloaded context had no plan fact in it. The tactical scratchpad did have it, but nothing read that tier back.

Fix: query the scratchpad partition and inject the established facts into the system prompt as authoritative. Turn 2 now answers "Fibre 500 Mbps" with zero tool calls.

Exam tip

A prompt cannot fix a missing-context problem. The system prompt already said "never invent a plan, balance or speed" when Bug 1 happened. Instructions govern behaviour over the context the model has; they cannot conjure information that was never loaded. When an agent fabricates a specific value, inspect its context before rewriting the prompt.

Phase 2

ReAct with Step Functions

The same loop, with the macro structure lifted out of the model's hands and into a state machine.

7

The ReAct state machine

adi-2-1-react-workflow · 5 Lambdas · adi-2-1-sfn-role

In plain terms: The developer owns the shape of the workflow — a fixed, auditable sequence of states. The model owns only the judgement inside each state. Macro-deterministic, micro-non-deterministic.

What was built: Nine states over five Lambdas. ParseUserRequest uses regex, not an LLM — intent and account-id extraction that runs in microseconds, costs nothing, and always applies the same rules. Then an LLM planner picks one of troubleshoot / billing / escalate / none, a Choice routes to three action branches, an LLM reasoner judges whether the facts explain the issue, and a guard decides whether to loop. Every Task state has Retry with exponential backoff; the two LLM states have Catch routing to GenerateResponse, so a planner failure degrades to an answer rather than a dead execution.

Where to check: Step Functions → State machines → adi-2-1-react-workflow → Executions. The visual graph shows the three branches and the loop-back edge.

Verified: all three branches. "Crawling all morning" took the troubleshoot branch at confidence 0.95; "overcharged on my last bill" took billing; "I want to cancel" escalated and opened a ticket.

Bug 2 · The brief's own state machine can loop forever

What happened: project.md's NeedMoreActions state loops back to DetermineAction whenever the model says needMoreActions: true — with no iteration bound at all. The only thing between that workflow and unbounded Bedrock spend is the model eventually choosing to say false, which is precisely the judgement Section 4 says never to trust.

Fix: replaced with MaxIterationsGuard, which Ands the model's vote together with iteration < 3. The model still votes; it cannot outvote the ceiling.

Finding · How a ReAct loop actually wastes money

The billing run took the loop-back edge twice, and the billing branch executed twice with identical inputs, gathering nothing new the second time. The planner has no memory of what it already did — each pass reasons afresh and judged the same evidence insufficient again.

That is the real failure mode: not an agent going haywire, but one politely repeating itself. Note that confidence fell to 0.75 against 0.95 for the clean single-pass runs — exactly the signal that routes a case to a human in Phase 5.

Exam tip

Workflow-based chain-of-thought is recoverable; prompt-based is not. Each handler writes its output to the scratchpad before returning, so a failure at the reasoning step leaves the parse and action results durable and inspectable. The same reasoning inside a single LLM call vanishes entirely when it fails.

Phase 3

Safeguards

A timeout the model cannot outlast, and a breaker that stops calling a dependency that is failing.

8

Timeout budget, circuit breaker, alarm

adi-2-1-guarded-invoke · adi-2-1-circuit-breaker · adi-2-1-circuit-open-alarm

In plain terms: A retry policy pushes harder on something that is already failing. A circuit breaker stops calling it — which is what gives it room to recover.

What was built: The timeout budget is derived from context.get_remaining_time_in_millis() minus a reserve and applied as a botocore read_timeout, so the model can never be the thing that runs the function out of time. The breaker counts failures in a rolling 300-second window, opens above 50% over at least 5 calls, waits 60 seconds, then allows a single probe that either closes it or re-opens it.

Where to check: DynamoDB → adi-2-1-circuit-breaker (watch status change live); CloudWatch → Alarms, and Metrics → adi-2-1/Safeguards.

Verified: driven through the full cycle with injected failures — healthy call, four failures opening the circuit at an 80% rate, a fifth call refused without touching the model or the counters at all, then a successful probe after cooldown closing it again.

Bug 3 · The brief's circuit-breaker code does not run

What happened: project.md's record_call_result() uses SET calls = if_not_exists(calls, :empty_list) + :call. Run verbatim against DynamoDB: ValidationException: Incorrect operand type for operator or function: +, operand type: L.

Fix: + in an update expression is arithmetic only; list concatenation needs list_append(). Two further problems even once fixed: that calls list grows without bound toward the 400 KB item limit and is re-read and filtered on every call, and error_rate > 0.5 with no minimum sample size means the first failed call is a 100% error rate and trips the breaker for every user. Rebuilt with ADD counters over a rolling window and a minimum of 5 calls.

Bug 4 · The brief's IAM policy grants nothing at all

What happened: project.md offers a policy capping token count and temperature via bedrock:MaxTokens and bedrock:Temperature conditions. Run through iam simulate-custom-policy it returns implicitDeny — and it still returns implicitDeny when both keys are supplied and satisfied (500 < 2000, 0.2 ≤ 0.5).

Fix: those are not real condition keys, so the condition never matches and the Allow never applies. IAM authorizes on action, resource ARN and published condition keys — it cannot inspect request body parameters. Inference caps belong in application code, which is where they live here.

Bug 5 · The alarm was watching a metric that does not exist

What happened: the alarm sat at OK through two separate breaker trips, reporting "no datapoints received".

The first diagnosis was wrong. CloudWatch ingestion latency looked like the culprit, and the alarm period was widened from 60 to 300 seconds on that theory. It made no difference, because that was not the problem.

Root cause: put-metric-alarm was called with a namespace and metric name but no dimensions, while the Lambda publishes with ServiceName. A CloudWatch metric is identified by namespace plus name plus its complete dimension set — so the alarm was watching a genuinely different metric, one that had never received a single datapoint. Querying it directly proved it: 0 datapoints without dimensions, 3 with them.

Fix: recreated with matching dimensions and re-verified against a live trip. The 300-second period was kept — still the right setting for a one-off event metric, just not the fix for this.

Exam tip

Catching your own errors hides you from CloudWatch. This Lambda returns HTTP 200 with a fallback, which is correct behaviour — and means the built-in AWS/Lambda Errors metric stays flat while the system is fully degraded. Graceful degradation has to emit its own signal. A dashboard that looks healthy during an outage is the failure mode to design against.

Phase 4

Model Coordination

A classifier costing four millionths of a dollar decides where a call fifty times more expensive goes.

9

The routing layer

adi-2-1-model-router

In plain terms: "Which model is best" is the wrong question. "What does this particular request actually need" is the right one — and a tiny model can answer it before the expensive call is made.

What was built: Nova Micro classifies each request by taskType × complexity, a routing table picks the model, runtime signals can downgrade that choice, and a fallback chain covers failure. Every decision is priced from live AWS Pricing API rates: Nova Micro $0.035/$0.14 per million tokens, Haiku 4.5 $1.10/$5.50, Sonnet 4.5 $3.30/$16.50.

Where to check: Lambda → adi-2-1-model-router → Test, or its CloudWatch Logs for the routing decision on each call.

Verified — six cases, costs measured rather than asserted:

"What time does your support line open?"classification / lownova-micro$0.0000141$0.0007689
Credits promised twice, speed short, disputed fee, legal threatreasoning / highsonnet$0.0019365$0.0019272
Same request, latency requirement setreasoning / highhaiku (downgraded)$0.0005908$0.0017457

Why it matters: the first row is the whole argument — the same answer, 54× cheaper, because "what time do you open" never needed a frontier model. The second row is the router declining to save money when the request genuinely warrants Sonnet. Latency told the same story: 470 ms against 3,819 ms. Dynamic selection does not make any model faster; it stops most requests being sent to the slow one.

Improvement on the brief · Complexity is a second axis

The brief routes on taskType alone. Task type cannot separate "summarise this note" from "summarise this five-way dispute" — and the second genuinely needs the better model. Rows 2, 3 and 4 above are all the same reasoning/high input landing on three different models once runtime signals are applied.

Exam tip

Ensembles are the high-cost, high-confidence option. Running N models and combining by majority vote or weighted average costs N calls — but the useful output is the disagreement, which is a ready-made escalation signal. Not built here, deliberately: it would have cost the most and demonstrated the least.

Phase 5

Human in the Loop

An execution that parks for free until a person answers — and a gate that cannot be talked out of stopping.

10

Task-token review gate

adi-2-1-hitl-workflow · adi-2-1-human-reviews · 5 Lambdas

In plain terms: Confidence says how sure the model is. Sensitivity says how much a mistake would cost. They are different questions, and the second one always wins.

What was built: Seven states implementing the escalation bands — above 0.9 sent immediately, 0.7 to 0.9 sent and logged for later review, below 0.7 parked for a human, and anything high-sensitivity parked regardless of confidence. Reviews land in a table with two GSIs, storing the model's draft and the human's correction side by side.

Where to check: Step Functions → adi-2-1-hitl-workflow — a parked execution sits in RequestHumanReview and shows as RUNNING at zero cost; DynamoDB → adi-2-1-human-reviews.

Verified — the pause and resume cycle: a cancellation request parked with a 660-character task token stored in DynamoDB, stayed RUNNING with zero state transitions, and resumed the instant SendTaskSuccess arrived with a rejection and a correction — the human's text replacing the model's draft in the final output.

Improvement on the brief · A token, not a poll loop

The brief uses Wait → CheckStatus → Choice → Wait. That bills a state transition per poll, adds latency averaging half the poll interval, and still needs the reviewer's answer stored where the poller can read it. .waitForTaskToken inverts it: the execution parks at zero cost and zero transitions until someone calls SendTaskSuccess. A 24-hour timeout is caught into an escalation path, so timing out never silently sends an unreviewed reply.

Bug 6 · Every customer with an "issue" was escalated to a human

What happened: sensitivity was matched with a plain substring check, and "sue" is a substring of "issue". "I have an issue with my internet", "my connection has issues", "pursue a complaint" — all flagged HIGH sensitivity and routed to synchronous human approval.

Root cause & why it went unnoticed: "issue" is one of the most common words in support traffic, so this quietly sent a large share of ordinary tickets to a human — destroying the automation the system exists to provide, while looking like a conservative safety setting. It failed in the safe direction, which is exactly why nobody would notice.

Fix: word-boundary regex, with \w* on the stems meant as prefixes so "cancellation" and "compensation" still match, plus a negative lookahead so "credit card" no longer reads as a credit request.

Finding · A design flaw that only testing could surface

The first AUTO test parked instead of auto-approving: "Is there an outage in my area?" scored 0.35. Nothing was broken — the review workflow has no tools, so the model was correctly unsure about a fact it had no way to look up. But a confidence gate placed in front of a tool-less model sends nearly everything to a human.

Adding a facts channel that carries the ReAct workflow's findings into the evaluation changed the identical question from 0.35 → SYNC_REVIEW to 0.92 → AUTO. The gate has to run after fact-gathering, not instead of it.

Exam tip

Low confidence is usually a context problem, not a model problem. Before tuning a threshold or swapping models, check what the model was actually given. Nothing about the model, the prompt bands or the threshold changed between 0.35 and 0.92 — only the facts supplied.

Exam tip

GSIs exist so the answer does not require a Scan. Querying "every cancellation review" through the index scanned 1 item and returned 1; the same question as a Scan with a filter scanned all 6 and threw 5 away. ScannedCount is the number that matters — invisible at six rows, the difference between a dashboard and an outage at six million.
