Domain 1 · Task 1.3 · Bonus Assignment

Turning Messy Customer Feedback
Into AI-Ready Data

The goal of this project: a made-up electronics company sells wireless earbuds, and customer feedback about them shows up in four completely different shapes — written reviews, photos, support call recordings, and survey forms. None of that is something an AI model can just read directly. This page walks through building the pipeline that checks it, cleans it, understands each type using the right AWS tool, packages it into the shape Claude actually expects, and — in the last step — lets Claude's own judgment feed back into the quality checks at the start. Every AWS idea is explained in plain terms the first time it comes up.

How It Runs

Four different kinds of feedback, one pipeline, one AI at the end

A review, a photo, a phone call, and a survey form have almost nothing in common as raw files — so each one needs its own AWS tool before they can all be brought back together for Claude to read as one consistent picture. The dashed arrow at the bottom is the part that makes this a genuine loop, not a one-way pipeline: Claude's own opinion of how solid a piece of feedback is flows back and can lower that record's quality score. Resource names below leave off the shared adi-1-3- prefix that every resource in this project starts with, just to save space.

Step-by-Step Build Log

Every step, in the order it happened

Each step below explains a new AWS idea in plain terms first (in the blue box, where it applies), then says exactly what was built, where to see it in the AWS console, and why it mattered. Kept to one product line on purpose — wireless earbuds, made up for this project — with sample data (reviews, photos, call recordings, survey rows) written and generated specifically to test this pipeline, since no ready-made sample data came with the assignment.

Phase 1

Checking the Data First

Before anything expensive happens to a piece of feedback, make sure it's actually trustworthy — and prove that bad data really does get caught, not just assumed to pass.

1

Set up storage and write test data

S3 bucket · 12 reviews · 4 photos · 2 call recordings · 12 survey rows

What was built: A private, locked-down S3 storage bucket (the same idea explained in Task 1.1's Step 2) to hold everything. Since no sample data came with this assignment, realistic test data was written and generated by hand for all four types: written reviews (two of them deliberately broken — one far too short, one missing required fields — specifically to prove the quality check in Step 3 actually catches bad data), simple product-box photos with real text drawn onto them, and — the more interesting part — two real support-call recordings, created by having Amazon Polly (AWS's text-to-speech service) actually speak out two sample conversations, so the transcription step later on has genuine speech to work with instead of a silent file.

Where to check: S3 → adi-1-3-customer-feedback-269737522732 → raw-data.

Why it matters: A quality check that's never tested against genuinely bad data doesn't prove anything. Building two intentionally-broken sample reviews right from the start means Step 3 can be judged on whether it actually rejects bad input, not just on whether it runs without crashing.

2

Check the survey numbers are sound

AWS Glue Data Quality · score 1.0 out of 1.0

In plain terms: AWS Glue Data Quality lets you write plain rules for a table of data — "this column can never be empty," "this number has to be between 1 and 5" — and it automatically checks every row against those rules and gives back a pass/fail score. It's built for exactly this kind of structured, spreadsheet-shaped data, like the survey rows in this project.

What was built: A Glue Crawler scanned the survey file and figured out its structure automatically, then 8 quality rules were written against it — every required field filled in, every date in the right format, every rating actually between 1 and 5. Ran for real: all 8 rules passed, a perfect score.

Where to check: AWS Glue → Data Quality → adi-1-3-survey-quality-ruleset.

Why it matters: Structured data (rows and columns, like the survey) and unstructured data (free-form text, like a review) need different kinds of checking. This is the structured half — Step 3 covers the unstructured half.

Error 1 & 2 · The checking program couldn't report its own results

What happened: The quality check ran as its own separate mini-program behind the scenes, and that program needs permission to report its own status back — that's different from just having permission to read the data. It was missing that permission, twice in a row (two different report-back permissions were each missing in turn).

Fix: added both missing permissions once the exact error named them. After that it ran clean.

Error 3 · A quality rule that looked fine actually never passed

What happened: The very first real run scored only 50%, with two rule types failing on data that was actually correct — including the date-format rule failing on every single row. The cause: a typing mistake doubled up a special character in the rule, so it was quietly looking for something that could never appear in real dates.

Fix: corrected the typo, and also switched the rating rule to a clearer, simpler style ("must be one of 1, 2, 3, 4, 5") instead of a "between" range, to remove any doubt about whether the endpoints count. Re-ran and got a perfect score.

Good to know

If a data-quality rule fails on 100% of rows, or fails on exactly the edge values (like exactly 1 or exactly 5), that's almost always a mistake in how the rule itself was written — not real data suddenly all being wrong. Worth double-checking the rule's own spelling before assuming the data is bad.

3

Check the written reviews are sound

adi-1-3-text-validation · scores from 0.14 to 1.0

What was built: A small program (a Lambda function) that runs automatically the instant a new review file is uploaded. It runs 7 checks — is it long enough, does it actually mention the product, does it sound like an opinion, are all the required fields filled in, is the star rating actually 1–5, is the date in the right format — and turns those into one score out of 1.0. Uploaded all 12 test reviews for real and let the real trigger fire, rather than just testing the code by itself.

Where to check: Lambda → adi-1-3-text-validation; S3 → validation-results/reviews.

Why it matters: This is the safety net that stops obviously broken data from ever reaching the more expensive AI steps later on. Proof it actually works: the good reviews scored close to 1.0, and the two deliberately-broken ones scored 0.43 and 0.14 — genuinely told apart, not rubber-stamped.

4

A dashboard to watch data quality over time

adi-1-3-CustomerFeedbackQuality

In plain terms: Amazon CloudWatch is AWS's monitoring service — it can collect numbers your programs report (like a quality score) and turn them into a chart you can actually watch over time, instead of only finding out about a problem after it's already caused damage.

What was built: A dashboard showing the review quality scores from Step 3 over time, plus the Step 3 program's own health (how often it runs, whether it's erroring). On purpose, left out a chart for a number the original assignment example mentioned but never actually sets up anywhere — a dashboard pointed at a number nothing ever reports just shows an empty, misleading chart.

Where to check: CloudWatch → Dashboards → adi-1-3-CustomerFeedbackQuality.

Why it matters: Turns "did data quality get worse recently" from a question nobody's watching into something visible at a glance — and this same dashboard is exactly where Step 13's feedback loop shows up later, closing the circle.

Phase 2

Understanding Each Type

A review, a photo, a phone call, and a spreadsheet row all need a different AWS tool built for that specific kind of data.

5

Read the reviews for meaning

adi-1-3-text-processing · Amazon Comprehend

In plain terms: Amazon Comprehend is AWS's ready-made text-understanding service — no training needed, it just reads text and tells you the overall sentiment (positive, negative, mixed), the important phrases, and named things it recognizes.

What was built: A second small program that only picks up reviews that already passed Step 3's check, and runs them through Comprehend for sentiment, key phrases, and entities. Tested by uploading all 12 reviews for real and watching the two checks chain together automatically.

Where to check: Lambda → adi-1-3-text-processing; S3 → processed-data/reviews.

Why it matters: Exactly 10 of the 12 reviews got processed — the 2 deliberately-broken ones were correctly held back. That's the whole point of Step 3's check: bad data never even reaches this more expensive step. Spot-checked one review about a cracked case and missing earbud — Comprehend scored it 99.99% negative, matching a human reading it.

6

Read the photos for text and content

adi-1-3-image-processing · Textract + Rekognition

In plain terms: Amazon Textract reads printed or handwritten text out of an image or document. Amazon Rekognition is a separate service that looks at what's actually in a photo — objects, scenes, general labels — rather than reading text. Using both together on a product photo gets the full picture: what it says, and what it shows.

What was built: A program that runs both services on every uploaded product photo and saves the combined result.

Where to check: Lambda → adi-1-3-image-processing; S3 → processed-data/images.

Why it matters: On a test photo of a cracked earbud case with "CASE CRACKED ON ARRIVAL" drawn onto it, Textract correctly read that exact phrase back out, and Rekognition independently recognized real shapes in the image — proof both tools genuinely looked at the picture rather than just running without erroring.

Looked broken, wasn't · a mixed-up log made it look like the trigger never fired

What happened: After uploading photos, nothing showed up in the results for several minutes, and checking the logs seemed to confirm the program had never even run once.

Fix: a direct manual test proved the program itself worked fine. The real story: AWS had reused the same log window for two separate runs, and reading the full window (not just its name) showed the trigger genuinely had fired — one run succeeded, and a second one failed with a one-off, temporary error from the photo-reading service itself. Trying that exact same photo again seconds later worked with no changes, confirming it was just a brief hiccup, not a real bug.

7

Transcribe the support calls, the safe way

adi-1-3-audio-transcription-sm · Step Functions + Transcribe

In plain terms: Amazon Transcribe turns speech into text, but a transcription job takes time to finish — you start it, then have to check back later. A single small program (a Lambda) has a hard 15-minute time limit, so sitting there in a loop waiting for a long phone call to finish transcribing risks it simply timing out. AWS Step Functions (the flowchart tool from Task 1.1's Step 12) solves this by having the *waiting* live in the flowchart itself, which has no such time limit, while the small program only does the two real jobs: kick the transcription off, and handle the finished result.

What was built: A flowchart: start the transcription → wait 20 seconds → check if it's done yet → if not, wait again → once done, read the transcript and analyze it with Comprehend for sentiment and key phrases.

Where to check: Step Functions → adi-1-3-audio-transcription-sm → Executions.

Why it matters: Both real test calls transcribed with genuinely high accuracy — the AI-spoken audio from Step 1 came back as an almost word-for-word transcript, correctly picked up the specific complaint in each call, and correctly scored the sentiment of each. This is exactly the exam's "why Step Functions over a single Lambda" scenario, built and proven for real rather than just described.

Good to know

The two test recordings each used one AI voice reading both sides of the conversation, so the "who's speaking" feature correctly reported just one speaker for the whole call — not a bug, just an honest limit of the practice audio, not the pipeline.

8

Turn survey rows into readable summaries

adi-1-3-survey-processing · Amazon SageMaker Processing

In plain terms: A SageMaker Processing job is a temporary computer that AWS spins up just to run one script, and automatically shuts down and stops charging the moment the script finishes — different from a SageMaker endpoint (used in Task 1.2), which stays on and keeps charging by the hour until someone turns it off.

What was built: A script that cleans up the survey rows and writes a short plain-English summary for each customer (like "Customer X was dissatisfied overall, rated the product 2 out of 5, and suggested improving battery life"), plus overall statistics across all responses.

Where to check: SageMaker → Processing → adi-1-3-survey-processing; S3 → processed-data/surveys.

Why it matters: Confirmed ahead of time (back before Phase 1 even started) that this specific kind of SageMaker job wasn't blocked by the same brand-new-account limit that stopped a different part of Task 1.2 — and running it for real confirmed that: the whole job, computer and all, finished in under 2 minutes and cost a fraction of a cent.

Caught before it cost anything · a spreadsheet tool silently corrupted a field

What happened: Running the script on a laptop first, before ever paying for the real cloud job, showed that rows meant to say "no improvement area suggested" were coming out blank instead. The spreadsheet-reading tool treats the literal word "None" as a special "this cell is empty" marker by default, and was quietly throwing that value away.

Fix: told the tool to treat every cell as literal text, re-tested on the laptop, confirmed it was fixed, and only then ran the real paid job — avoiding paying to generate summaries with a hidden data bug already baked in.

Good to know

Testing a script on a laptop with a small sample of real data, before ever running it as a paid cloud job, is a cheap way to catch exactly this kind of silent, no-error data bug — the script never crashed, it just quietly produced wrong output.

Phase 3

Getting It Ready for Claude

Four very differently-shaped results have to become one consistent shape before an AI model can make sense of any of them.

9

Package everything the same way

adi-1-3-bedrock-formatting · 28 formatted records

In plain terms: Claude (like most AI models on Bedrock) expects every request in one specific shape: a short "system" instruction saying what job it's doing, then a "message" containing the actual content — and for a photo specifically, that message can include the real image itself, not just a text description of it, so Claude can genuinely look at the picture.

What was built: One program that reads whichever of the four processed results just showed up, and builds it into that exact request shape — a shared instruction ("you're a customer-insights analyst, tell me the issue, whether to escalate it, and what to do next") plus the specific content for that record. For a photo, it genuinely attaches the real image bytes alongside the Textract/Rekognition summary.

Where to check: Lambda → adi-1-3-bedrock-formatting; S3 → formatted-data.

Why it matters: All 28 records across all four types (10 reviews, 4 photos, 2 calls, 12 surveys) came out correctly packaged and ready to send to Claude exactly as-is — proven in Step 10 by actually sending them.

Caught before deploying · raw image data can't go straight into a saved file

What happened: A photo's actual pixel data is raw binary bytes, which can't be written directly into a plain text/JSON file — every single photo record would have crashed the moment it tried to save.

Fix: converted the image into a safe text format (base64) before saving it, with a clear note that it needs converting back to real bytes right before actually sending it to Claude. Caught by reading through the code carefully before ever running it for real.

A different kind of "looked broken, wasn't" · a copy trick that silently failed

What happened: The usual trick used earlier in this project to re-trigger a step on already-existing files (copy a file onto itself to force a fresh "new file" event) silently failed 16 times in a row here — AWS actually refuses to copy a file onto its own exact same name unless something about it is genuinely changing, and the error had been accidentally hidden.

Fix: stopped relying on that trick altogether — instead, re-uploaded the four original raw-data files again, which naturally cascades through every earlier step and proves the whole chain end-to-end, not just this one piece.

10

Actually send it to Claude and check the answers make sense

Claude Haiku 4.5 · 4/4 test calls

What was built: A quick test script that picks one formatted record of each type and sends it for real to Claude Haiku 4.5 (the same model confirmed working back in Task 1.2), then reads the actual answer.

Where to check: re-run scripts/test_bedrock_invoke.py locally — this step doesn't save anything new, it's a check that Step 9's packaging actually works.

Why it matters: All four came back with sensible, correctly-flagged answers — including the cracked-case photo, where Claude's answer specifically referenced the crack, proving it genuinely looked at the actual image and not just the text summary next to it.

Phase 4

Closing the Loop

Spot the big-picture trends, clean up messy text before anything reads it, and let the AI's own judgment feed back into quality checks.

11

Spot the recurring themes across all reviews

adi-1-3-theme-aggregation · insights/reviews_theme_summary.json

What was built: A program that reads every processed review at once and rolls them up into one report: overall sentiment split, sentiment split by product model, and the most commonly repeated phrases and named things across all of them.

Where to check: S3 → insights/reviews_theme_summary.json.

Why it matters: A single review is a data point; a hundred reviews rolled up together is a business trend. This is a batch report run on demand (like the benchmark script in Task 1.2), not something that runs per-file — it's meant to be checked periodically, not on every single new review.

Error · a permission "condition" that quietly never matched

What happened: The program was denied access to read files it clearly should have had permission for. The cause: two different permissions (listing files, and reading a file) were combined into one rule with one extra condition attached — but that condition only actually makes sense for the "listing files" half, so for the "reading a file" half, the condition simply never matched anything and silently blocked it.

Fix: split it into two separate, simpler rules — one for listing, one for reading, each written plainly with no shared condition to get confused about.

12

Clean up messy text before anything reads it

Updated adi-1-3-text-processing · normalized_text field

What was built: Updated Step 5's program to clean review text up before Comprehend ever sees it — stripping out stray HTML tags, unscrambling HTML symbols, expanding shorthand ("w/" → "with", "BT" → "Bluetooth", "mins" → "minutes"), and squashing extra spaces. Both the original and the cleaned-up version get saved, so nothing's silently thrown away. Two new test reviews, written specifically with this kind of noise in them, were used to actually prove it works.

Where to check: S3 → processed-data/reviews — look for the normalized_text field next to original_text.

Why it matters: On the real test review, Comprehend correctly picked out "20 minutes" and "no Bluetooth dropouts" as key phrases — phrases that only exist in the cleaned-up version, proving Comprehend genuinely analyzed the clean text, not the noisy original.

Error · a shorthand fix that silently never fired

What happened: Tested locally first (same habit as Step 8) and found "w/" was never actually being replaced with "with," even though the rule looked correct at a glance.

Fix: the rule required a clean word-boundary on both sides of the match, but a slash followed by a space doesn't count as one on the right-hand side — so it could never match there. Rewrote it to specifically look for a space (or the end of the text) right after the slash instead, tested locally again, confirmed it worked, then updated the real program.

13

Let Claude's own confidence adjust the quality score

adi-1-3-feedback-loop · the actual feedback loop

In plain terms: Just because a review is well-formed — right length, has an opinion, correct fields — doesn't mean it's actually useful for a business decision. "It's fine I guess" passes every formatting check but tells a product team nothing. This step asks Claude directly: does this feedback actually contain enough real detail to act on? And if Claude says no, that review's saved quality score genuinely gets lowered — not just noted somewhere and ignored.

What was built: A program that sends each formatted review to Claude with a second, focused question — is this specific enough to act on, and how confident are you? If Claude says no, or isn't confident, the original quality score from Step 3 gets multiplied down and re-saved, and a new metric appears on the very same dashboard built in Step 4.

Where to check: Lambda → adi-1-3-feedback-loop; S3 → validation-results/reviews (look for the updated score) and quality-feedback/reviews (the full reasoning).

Why it matters: Tested on 4 real reviews, both directions: a genuinely vague one got marked down hard (score dropped from 0.86 to 0.13); a genuinely specific complaint about a cracked case kept its full score unchanged. A real surprise along the way — even a clearly positive review ("I love these earbuds, battery lasts all day") got marked down too, because it has no actual specifics for a product team to act on. That's not a bug, it's the whole point: "sounds fine" and "is actually useful" turned out to be two different things, and only a step like this one catches the difference. A final test review — about an earbud catching fire while charging — ran through the entire 13-step pipeline completely on its own, with zero manual steps, end to end.
