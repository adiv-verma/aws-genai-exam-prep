Step-by-Step Build Log

Every step, in the order it happened

Each step says what was built and why, plus any error hit while building it — the same order kept in this task's progress.md file so work can pick back up any time. Kept to one support topic (EC2 troubleshooting) on purpose, so it stayed simple to build and test.

Phase 1

Foundation

Check model access, then set up storage and compute

1

Check access to the AI model

Claude Haiku 4.5 · us.anthropic.claude-haiku-4-5-20251001-v1:0

What: Confirmed the model could actually be called in us-east-1. Tried Claude Sonnet 5 first, then switched to Claude Haiku 4.5 after hitting the error below.

Where to check: AWS Console → Amazon Bedrock → Model access.

Why: Everything else in this build depends on this model, so it's worth testing with a real call first — not just trusting what the console says.

Error 1 · Access looked approved, but calls still failed

What happened: Accepted Claude Sonnet 5's usage terms, and the console said access was approved — but calling the model still failed with an access-denied error.

Fix: approval can take a little time to fully apply on AWS's side. Switched to Claude Haiku 4.5 instead, which was already working.

Error 2 · Wrong model ID format

What happened: Calling the model by its plain ID failed with: "on-demand throughput isn't supported...use an inference profile."

Fix: use the special cross-region ID instead — us.anthropic.claude-haiku-4-5-... — which some newer models require.

Good to know

The console can say access is approved before it actually works — there's a short delay behind the scenes. And some newer Bedrock models need a special "inference profile" ID instead of their plain model ID, or calls fail with a confusing error.

2

Storage bucket for prompt templates

adi-1-1-prompt-templates

What: Created an S3 bucket to store prompt templates, with version history turned on and all public access blocked.

Where to check: S3 → adi-1-1-prompt-templates → Properties tab (Bucket Versioning: Enabled).

Why: Every prompt file gets saved as a new version automatically. If a change goes wrong, going back is just picking an older version — no rebuild needed.

Good to know

This bucket's version history is separate from Bedrock's own prompt version history (Steps 5–6). This bucket is just backup storage — the versions the app actually uses live in Bedrock Prompt Management.

3

Database for conversation history

adi-1-1-support-conversations

What: Created a DynamoDB table to store each conversation, with old entries set to auto-delete, and pay-as-you-go pricing.

Where to check: DynamoDB → adi-1-1-support-conversations → Additional settings (Time to live: expiresAt, Enabled).

Why: The AI model has no memory of its own — every call starts fresh. This table is what lets the assistant remember earlier messages in the same conversation, by saving each one and reading them back before every reply.

Good to know

DynamoDB's auto-delete feature isn't instant — AWS says it can take up to 48 hours. It's good for cleaning up old data over time, but don't rely on it to remove something the exact moment it expires.

4

Permissions for the Lambda functions

adi-1-1-bedrock-lambda-role

What: Created a permission set (IAM role) that only Lambda functions can use. Started small, and only added more permissions later (Steps 9, 11) when a real error showed one was missing.

Where to check: IAM → Roles → adi-1-1-bedrock-lambda-role → Permissions.

Why: This is the shared permission set every Lambda function in this project uses to talk to AWS. Keeping it narrow limits the damage if anything ever goes wrong.

Good to know

Build permissions from real errors, not guesses. When something fails with "access denied," the error tells you exactly what's missing — add just that. This approach fixed nearly every permission problem in this build (Steps 9, 11, 13).

Phase 2

Prompt Management & Governance

Saved instructions for the AI, with version history and access control

5

Base instructions for the assistant

adi-1-1-support-assistant-persona (v2)

What: Saved the assistant's core instructions in Bedrock Prompt Management — its role, tone, and how answers should be formatted.

Where to check: Bedrock → Prompt management → adi-1-1-support-assistant-persona.

Why: Keeps the assistant's personality and rules in one saved, versioned place instead of buried in application code.

Error 3 · Two settings clashed

What happened: First live test failed: "temperature and top_p cannot both be specified for this model."

Fix: removed one of the two conflicting settings (topP), keeping only temperature. Saved as version 2.

Good to know

Not every model accepts every setting — always test a new prompt for real before trusting it. Also: the "draft" copy of a prompt is for editing; a saved, numbered version is what the app should actually use, so fixing a bad edit later is just pointing at an older version, not a redeploy.

6

Prompts for each situation

adi-1-1-scenario-diagnostic · adi-1-1-scenario-clarification · adi-1-1-scenario-escalation

What: Three more saved prompts, each carrying the base instructions plus extra guidance for one situation: diagnosing a problem, asking a follow-up question, or handing off to a person.

Where to check: Bedrock → Prompt management.

Why: Different situations need different responses. Step 12's decision logic picks between these three prompts based on what the customer needs.

Good to know

Bedrock's Prompt Management doesn't let one prompt "inherit" from another, so the shared base instructions had to be copied into all three prompts by hand. That's just a real limit of the tool.

7

Audit logging

adi-1-1-cloudtrail-logs · /aws/cloudtrail/adi-1-1-support-assistant · adi-1-1-cloudtrail-cwlogs-role · adi-1-1-support-assistant-trail

What: Set up a single log trail that records every action to both an S3 bucket (long-term storage) and a CloudWatch log group (viewable right away).

Where to check: CloudTrail → Trails → adi-1-1-support-assistant-trail (status: Logging).

Why: Covers two needs with one trail: a permanent record of every action (S3), and logs you can search right away without extra setup (CloudWatch).

Minor · Too soon after creating a permission

What happened: Creating the trail right after creating its permission role failed with an invalid-role error.

Fix: waited about 15 seconds and tried again — it worked. New permissions just need a moment to fully apply.

Good to know

A brand-new permission role can take a few seconds before other services can use it. If something fails right after creating a role, waiting a bit and retrying is usually the fix — not rewriting the permissions.

8

Separate access for editing prompts

adi-1-1-prompt-editor-role

What: A permission set that can write and update prompts, but is specifically blocked from running the AI model — and has no other access at all.

Where to check: IAM → Roles → adi-1-1-prompt-editor-role.

Why: Keeps "who can change the instructions" separate from "who can run them" — the kind of separation a real approval process would rely on.

Good to know · how this was checked

Actually logging in as this role would have meant creating real, temporary credentials — a security risk not worth taking just to test. Instead, used a built-in AWS tool that checks what a role is allowed to do without ever creating real credentials. It confirmed: editing prompts — allowed; running the model — blocked; everything else — blocked too.

Phase 3

Guardrails

A safety layer that works even if the prompt gets tricked

9

Safety guardrail

adi-1-1-support-assistant-guardrail

What: Built a Bedrock Guardrail that blocks three risky topics (sharing credentials, promising unreleased features, talking about competitors), blocks things like AWS keys and passwords, filters harmful content, and catches attempts to trick the AI into ignoring its instructions. Tested it against all 4 target cases and it worked as expected.

Where to check: Bedrock → Guardrails → adi-1-1-support-assistant-guardrail.

Why: This safety check runs separately from the prompt itself, so it still works even if someone finds a way to trick the AI into ignoring its instructions.

Good to know

Bedrock already knows how to detect things like AWS access keys and secret keys — no custom setup needed for that. And blocking topics like "competitor talk" works by understanding meaning, not just matching exact words, which is why it catches rephrased attempts too.

Phase 4

Orchestration

Two Lambda functions and a flowchart that makes every decision visible

10

Lambda: figure out what the customer needs

adi-1-1-detect-intent

What: Reads a customer message and figures out the topic, pulls out any instance ID mentioned, scores how confident it is, checks the customer's mood using Amazon Comprehend, and flags whether a human should step in.

Where to check: Lambda → adi-1-1-detect-intent → Monitor tab.

Why: Turns a raw message into clear signals the flowchart in Step 12 can act on — that's what decides whether to diagnose, ask more, or hand off to a person.

Error 4 · Mood alone triggered too many handoffs

What happened: A normal troubleshooting message ("won't start, stuck in pending") scored as 96% negative in mood and wrongly triggered a handoff to a human — but it was just an ordinary technical complaint.

Fix: stopped using mood by itself as a handoff trigger. It's still measured and saved, but handoffs are now only triggered by specific keywords or billing issues. Tested again: the same message no longer triggers a handoff, but a genuinely angry billing complaint still does.

Good to know

Mood detection is built for everyday text, and ordinary technical complaints often score as very negative. Don't use mood alone to trigger something important like a handoff — pair it with a clearer signal, like specific keywords.

11

Lambda: ask the model and save the answer

adi-1-1-invoke-model

What: Picks the right saved prompt, calls Bedrock with the safety guardrail turned on, checks that the answer looks right, and saves both sides of the conversation to the database. This step had the most real problems to fix — three in a row.

Where to check: Lambda → adi-1-1-invoke-model → Monitor tab.

Why: This is where the saved prompt, the safety guardrail, and conversation memory all come together in one call.

Error 5 · Wrong permission type for saved prompts

What happened: Kept getting "not authorized," even after granting full model-calling permission every way possible.

Fix: calling a model through a saved prompt actually needs two different, specific permissions (Converse and RenderPrompt) — not the general model-calling permission. Once those were granted, it worked.

Error 6 · Request went to the wrong AWS region

What happened: After fixing Error 5, a new error appeared — the request was denied because it landed in a different AWS region than expected.

Fix: the special cross-region model ID can send requests to more than one region behind the scenes. Updated the permission to allow any region, not just one.

Error 7 · Guardrail blocked a perfectly normal question

What happened: With permissions finally fixed, a harmless question ("instance stuck in pending for 10 minutes") got blocked by the safety guardrail.

Fix: the guardrail's strictest setting was too sensitive and mistook a normal, structured question for a trick attempt. Lowered the strictness one notch, tested it — it now lets real questions through while still catching real trick attempts.

Good to know

Some AWS permissions are tied to very specific actions — a broad "allow everything" permission won't always cover a narrower, differently-named action. Also, guardrail strictness is a dial, not a switch: turning it up catches more tricks but also blocks more real, harmless questions — worth testing and tuning, not just leaving on the default.

12

The decision flowchart

adi-1-1-support-assistant-sm

What: Built the full flowchart: get the question → figure out what's needed → decide (hand off / ask more / diagnose) → ask the model → check the answer → reply. If anything fails along the way, it falls back to a simple apology message instead of crashing. Worked on the first try — tested all three paths and double-checked the actual steps taken, not just the final answer.

Where to check: Step Functions → adi-1-1-support-assistant-sm → Executions (see a visual map of each run).

Why: Every decision is a visible, named step with a clear reason — easy to review later, instead of guessing why the AI did what it did.

Good to know

Step Functions has two speeds: "Standard" (slower, but keeps a full visual history of every run) and "Express" (faster and cheaper, less detail). Standard was picked here specifically because being able to see exactly what happened in each run matters more than raw speed.

Phase 5

QA & Monitoring

Automatic tests, plus a dashboard and alerts that catch problems early

13

Test suite

adi-1-1-validate-output · adi-1-1-test-harness-sm

What: A Lambda function that checks whether a response met expected criteria, plus a flowchart that runs 5 built-in test questions through the full assistant and checks each result.

Where to check: Step Functions → adi-1-1-test-harness-sm → latest run's output.

Why: Covers the brief's ask for tests on tricky cases (angry customers, vague requests) plus two extra security tests (prompt tricks, credential requests) that are supposed to fail safely. Result: 5 out of 5 passing, including confirming the two risky test cases correctly got blocked by the guardrail.

Error 8 · Missing permission for a nested test run

What happened: Creating the test flowchart failed right away with a permission error.

Fix: a state machine that runs another state machine and waits for it needs an extra, specific permission to manage a background event rule. Added it, and it worked.

Error 9 · Tried to convert data that was already converted

What happened: The first full test run failed with a data-format error.

Fix: checked the raw run details and found the nested result was already in the right format — it didn't need converting. Removed the unnecessary conversion step.

Good to know

A flowchart that runs another flowchart and waits for the result needs a specific extra permission — easy to miss. And when a nested result's format is unclear, check the actual run details rather than guessing from general documentation.

14

Dashboard and alerts

adi-1-1-alerts · 5 alarms · adi-1-1-support-assistant-dashboard

What: Added logging that tracks bad answers, guardrail blocks, and response speed. Built an alert topic (left with no email/text hooked up yet — that's a choice for the account owner, not something to decide automatically), 5 alarms, and one dashboard showing everything together.

Where to check: CloudWatch → Dashboards → adi-1-1-support-assistant-dashboard; CloudWatch → Alarms (search adi-1-1).

Why: Catches problems automatically instead of relying on someone noticing by hand. Two of the alarms directly cover the kinds of bugs found in Steps 4 and 7 above — if something similar happens again, it triggers an alert instead of going unnoticed.

Error 10 · A dashboard feature doesn't work in alarms

What happened: Tried to build an alarm that automatically adds up a metric across categories — failed with "not supported on Metric Alarms."

Fix: that shortcut only works in dashboards, not alarms. Replaced it with three separate entries added together by hand — one per category. Also had to add a missing time-window setting to one part of the alarm.

Good to know

Adding custom tracking to a Lambda function needs no extra permissions — it's just structured log lines, which the function can already write. And a feature that works fine on a dashboard doesn't always work the same way in an alarm — alarms need a fixed, clearly defined list of what to measure.
