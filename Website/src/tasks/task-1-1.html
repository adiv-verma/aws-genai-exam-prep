Insurance Claims
Document Processor

An insurance company wants to automate processing of claim documents — extract the key facts (claimant, policy number, incident date, claim amount, description), match the claim to its policy, and generate a short summary for an adjuster, using Amazon Bedrock. Built and live-tested end to end on 3 differently-formatted sample claims, plus a real head-to-head comparison of two Bedrock models on the summary-generation step.

Step-by-Step Build Log

Every step, in the order it happened

Everything here is pay-per-use — S3 storage plus on-demand Bedrock calls, no provisioned or hourly-billed resource anywhere in this build.

Step 1

Design The Architecture (Skill 1.1.1)

Confirm model access and pick which Bedrock model handles which job.

Architecture + model selection

Claude Haiku 4.5 · Claude Sonnet 4.6

In plain terms: Different Bedrock models trade off speed, cost, and capability differently. Picking one model for every job in a pipeline is simpler, but not always the best choice — worth actually testing before assuming.

What was done: Confirmed AWS identity and live-tested invoke access to two current-gen models via bedrock-runtime converse: Claude Haiku 4.5 (already proven reliable in this account) and Claude Sonnet 4.6 (via its cross-region inference profile — the bare model ID rejects on-demand invocation, same pattern found elsewhere in this project). Both replied correctly. Architecture: S3 holds raw claims and policy documents → an S3-upload-triggered Lambda extracts fields, matches the policy, validates, and summarizes via Bedrock → result written back to S3.

Why it matters: Every later step calls one of these two models, so access had to be proven with a real request/response first. Picking Haiku for extraction and comparing both for summarization (Step 4) gives the brief's "compare model performance" requirement a real, meaningful axis to measure.

Step 2

Sample Data

Storage plus three claim documents, deliberately written in three different formats.

S3 bucket, sample claims, and policy documents

adi-1-1-claims-documents-269737522732

What was built: An S3 bucket (versioned, all public access blocked). Three synthetic insurance claims, each written in a genuinely different style: a narrative email-style auto claim, a structured intake-form property/water-damage claim, and a terse "quick submit" urgent-care claim — plus three matching policy documents, each with real coverage limits, deductibles, and exclusions.

Where to check: S3 → adi-1-1-claims-documents-269737522732 → raw-claims/ (3 objects) and policies/ (3 objects).

Why it matters: Three different formats means the extraction step (Step 3) actually has to generalize, rather than just parsing one fixed template — a single consistent format would have proven far less.

Step 3

Implement PoC + Reusable Components (Skills 1.1.2 & 1.1.3)

The processing pipeline itself, built from three named, reusable pieces.

Claims processor: extraction, policy lookup, validation, summary

adi-1-1-claims-processor

In plain terms: Rather than one script that does everything, this is split into three small, reusable pieces: something that holds the prompt text, something that calls the model, and something that checks the model's answer looks right — each one usable on its own, not tangled together.

What was built: An S3-triggered Lambda, containing three reusable components:

  • Prompt template manager — holds the extraction and summary prompt text by name, so either can be tuned without hunting through code.
  • Model invoker — a thin wrapper around Bedrock's Converse API, one place every model call goes through.
  • Content validator — checks the extracted JSON has all 5 required fields, that the claim amount parses as a number and the date has a real year, before summarization runs.

Flow: read the claim → extract 5 fields via Bedrock → validate → look up the matching policy document directly by policy number (the brief's "simple RAG component" — a plain S3 lookup is enough at this scale, same reasoning used elsewhere in this project for why a managed vector database isn't needed for a handful of documents) → generate a summary, explicitly prompted to reference the matched policy's actual coverage terms → write the result to processed/. Wired a real S3 event trigger and re-uploaded all 3 sample claims to fire it live, not just tested via manual invoke.

Where to check: Lambda → adi-1-1-claims-processor → Monitor → Logs. S3 → processed/ — 3 result objects.

What the results actually showed

All 3 claims extracted correctly despite the different formats, matched the right policy every time, and passed validation:

  • Auto claim (narrative): pulled out claimant, policy number, date, $4,200 claim amount, and incident description correctly. The summary — unprompted with any specific numbers — correctly cited the policy's $500 deductible and its rule that claims over $2,000 need a police report, both facts pulled from the policy document, not the claim text.
  • Property claim (form): extracted the $8,750 water-damage claim correctly; summary cited the $75,000 coverage limit and the photographic-evidence requirement for claims over $5,000.
  • Health claim (terse): extracted correctly even from the sparsest format; summary correctly applied the $50 urgent-care deductible.

Every summary demonstrably used the matched policy's real terms — confirming the RAG lookup is actually feeding the summary step, not just sitting there unused.

Step 4

Test And Evaluate

A real, measured comparison between two Bedrock models on the same claim.

Model comparison: Claude Haiku 4.5 vs. Claude Sonnet 4.6

What was done: Ran both models against the identical summary prompt for the property claim (real extracted data + matched policy excerpt), measuring latency, token usage, and actual output quality.

What the results actually showed

ModelTimeOutput tokensNotable behavior
Claude Haiku 4.51.76s162Concise single paragraph; states the claim falls within the coverage limit.
Claude Sonnet 4.64.71s257~2.7× slower; adds markdown structure unprompted; actually computes the net payout after the deductible ($8,750 − $1,000 = $7,750) — a real, useful detail Haiku's summary didn't include.

Recommendation: Haiku 4.5 for extraction (both models were equally reliable at structured JSON output in this test, and Haiku is faster/cheaper for a step that runs per-document at volume). Sonnet 4.6 for summary generation specifically — its willingness to actually perform the deductible arithmetic is a real accuracy advantage for an adjuster-facing summary, worth the added latency for a step that doesn't run at extraction volume.

Good to know

The brief's own sample code targets claude-v2 and claude-instant-v1 via the older invoke_model API — both models are now retired on this account. This build uses the current Converse API against Claude Haiku 4.5 and Sonnet 4.6 instead, the same substitution already made across every other task in this project.
