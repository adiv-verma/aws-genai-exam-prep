Customer Support AI Assistant
Architecture & Governance PoC

The goal of this project: build a chatbot that helps AWS customers fix a specific kind of problem (an EC2 server that won't start or respond), using Amazon Bedrock — the AWS service that gives you access to AI models like Claude. This page walks through every step in the order it happened. Each AWS idea is explained in plain terms the first time it shows up, so you don't need to already know AWS to follow along.

How It Runs

One question, followed from start to finish

Here's what happens, in order, when a customer asks a question. Solid arrows show the path the question actually takes to get an answer. Dashed arrows show logging and monitoring happening at the same time in the background — they record what's going on, but they don't slow the answer down or change it. Resource names below leave off the shared adi-1-1- prefix that every resource in this project starts with, just to save space.

Step-by-Step Build Log

Every step, in the order it happened

Each step below explains an AWS idea in plain terms first (in the blue box, where it's a new idea), then says exactly what was built, where to go look at it in the AWS console, and why it mattered. Any error hit while building that step is included right where it happened, along with the fix. This whole project was kept to one topic on purpose — EC2 troubleshooting only — so it stayed simple enough to actually finish and test properly, instead of trying to cover everything at once.

Phase 1

Foundation

Before building anything AI-related, set up the basic storage and permissions everything else depends on.

1

Check access to the AI model

Claude Haiku 4.5 · us.anthropic.claude-haiku-4-5-20251001-v1:0

In plain terms: Amazon Bedrock is an AWS service that gives you access to AI models — like Claude, made by Anthropic — without having to run the AI yourself. But not every AWS account can use every model right away; some models need to be turned on for your account first, a bit like requesting access to a private app.

What was built: Sent a real test message to the model and confirmed it actually replied, in the us-east-1 AWS region. Tried Claude Sonnet 5 first, then switched to Claude Haiku 4.5 after hitting the error below.

Where to check: AWS Console → Amazon Bedrock → Model access.

Why it matters: Every other step in this project calls this model. It's worth testing with a real question and a real answer first, instead of just trusting a green checkmark in the console that might not mean what it looks like.

Error 1 · Access looked approved, but calls still failed

What happened: Accepted Claude Sonnet 5's usage terms, and the console said access was approved — but actually calling the model still failed with an access-denied error.

Fix: approval can take a little time to fully apply behind the scenes, even after the console says yes. Switched to Claude Haiku 4.5 instead, which was already working right away.

Error 2 · Wrong model ID format

What happened: Calling the model by its plain name failed with a message saying "on-demand throughput isn't supported...use an inference profile."

Fix: some newer models need a special ID (starting with us.) instead of their plain name — this is called a cross-region inference profile, and it lets AWS route the request to whichever nearby data center has room, instead of just one fixed location. Using that special ID fixed the error.

Good to know

The console can say access is approved before it's actually usable — there's a short delay behind the scenes that the console doesn't show you. And some newer Bedrock models need that special "inference profile" ID instead of their plain model name, or calls fail with a confusing error that doesn't obviously point to the real fix.

2

Storage bucket for prompt templates

adi-1-1-prompt-templates

In plain terms: Amazon S3 is AWS's basic file storage service — think of it like a folder in the cloud that can hold any kind of file, accessible from anywhere. "Versioning" means every time a file gets replaced, the old copy is kept too, so nothing is ever truly overwritten.

What was built: Created an S3 bucket (a named storage container) to hold prompt files, turned on version history, and blocked all public access so only this project's own systems can read it.

Where to check: S3 → adi-1-1-prompt-templates → Properties tab (Bucket Versioning: Enabled).

Why it matters: If a prompt file gets edited and saved, the previous version stays available. Undoing a bad change later just means pointing back at an older version — no need to rebuild or remember what the old text was.

Good to know

This bucket's version history is separate from Bedrock Prompt Management's own version history (Steps 5–6), which is a different feature entirely. Think of this S3 bucket as a backup copy — the actual versions the app uses to answer questions live in Bedrock Prompt Management, not here.

3

Database for conversation history

adi-1-1-support-conversations

In plain terms: DynamoDB is AWS's database for storing small pieces of structured data — like rows in a spreadsheet — that can be looked up very quickly. Unlike S3 (which stores files), DynamoDB is built for storing and searching lots of small records, like one row per message in a conversation.

What was built: Created a DynamoDB table where every message in a conversation is saved as its own row, set old rows to automatically delete after a while, and used pay-as-you-go pricing so there's no cost when nobody's using it.

Where to check: DynamoDB → adi-1-1-support-conversations → Additional settings (Time to live: expiresAt, Enabled).

Why it matters: AI models don't remember anything between calls — each request starts completely fresh, with no memory of what was said before. This table is what gives the assistant memory: every message gets saved here, and before each new reply, the earlier messages are read back and included, so the conversation feels continuous.

Good to know

DynamoDB's auto-delete feature isn't instant — AWS says it can take up to 48 hours after the set expiry time. It's a good way to clean up old data over time and save on storage costs, but don't rely on it to remove something at the exact moment you need it gone.

4

Permissions for the Lambda functions

adi-1-1-bedrock-lambda-role

In plain terms: AWS Lambda lets you run a small piece of code without setting up or managing a server — you just upload the code, and AWS runs it whenever it's needed. IAM (Identity and Access Management) is how AWS controls who — or what — is allowed to do what. An "IAM role" is a named set of permissions that a piece of code, like a Lambda function, can be given.

What was built: Created an IAM role that only Lambda functions can use, starting with a small, narrow set of permissions. More permissions were only added later (Steps 9, 11), and only when a real error proved one was actually missing.

Where to check: IAM → Roles → adi-1-1-bedrock-lambda-role → Permissions.

Why it matters: This is the shared permission set every Lambda function in this project runs with. Keeping it as narrow as possible — only what's actually needed — limits how much damage could happen if something ever went wrong, like a bug or a leaked credential.

Good to know

Build up permissions based on real errors, not guesses about what might be needed. When something fails with "access denied," the error message usually tells you exactly what permission is missing — add just that one, nothing extra. This approach is how nearly every permission problem in this build got fixed (Steps 9, 11, 13).

Phase 2

Prompt Management & Governance

Save the assistant's instructions in one place, with version history and controlled access to editing them.

5

Base instructions for the assistant

adi-1-1-support-assistant-persona (v2)

In plain terms: Bedrock Prompt Management is a place to save and version the instructions ("prompts") you give an AI model, instead of hardcoding that text inside your application. It works a bit like the prompt templates page — you write the instructions once, save them, and every part of your app can reuse the same saved version.

What was built: Saved the assistant's core instructions — its role, its tone, and how it should format its replies — as a Prompt Management entry.

Where to check: Bedrock → Prompt management → adi-1-1-support-assistant-persona.

Why it matters: Keeps the assistant's personality and rules in one saved, versioned place, instead of scattered through application code where it's easy to lose track of and hard to update safely.

Error 3 · Two settings clashed with each other

What happened: The very first live test failed with: "temperature and top_p cannot both be specified for this model." (Both of these are settings that control how random or predictable the AI's wording is.)

Fix: removed one of the two conflicting settings (topP), and kept only temperature. Saved that as version 2.

Good to know

Not every AI model accepts every setting the same way — always test a new prompt for real before trusting it works. Also worth knowing: the "draft" copy of a saved prompt is meant for editing, while a saved, numbered version is what the real app should actually use. That way, fixing a bad edit later just means pointing back at an older version — not a full redeploy of anything.

6

Prompts for each situation

adi-1-1-scenario-diagnostic · adi-1-1-scenario-clarification · adi-1-1-scenario-escalation

What was built: Three more saved prompts, each one carrying a copy of the base instructions from Step 5, plus extra guidance for one specific situation: diagnosing a technical problem, asking a follow-up question when details are missing, or handing off to a human when needed.

Where to check: Bedrock → Prompt management.

Why it matters: Different situations call for different kinds of replies. The decision flowchart built in Step 12 picks between these three prompts automatically, based on what the customer actually needs at that moment.

Good to know

Bedrock's Prompt Management has no way for one prompt to automatically reuse another prompt's text — there's no "inherit from" feature. So the shared base instructions had to be manually copied into all three prompts. That's just a real limit of the tool, not a mistake in how it was used.

7

Audit logging

adi-1-1-cloudtrail-logs · /aws/cloudtrail/adi-1-1-support-assistant · adi-1-1-cloudtrail-cwlogs-role · adi-1-1-support-assistant-trail

In plain terms: CloudTrail is AWS's built-in activity log — it automatically records almost every action taken in an AWS account (who did what, and when), which is essential for security reviews later. CloudWatch is AWS's monitoring and logging dashboard, used to view logs and metrics in near real time.

What was built: Set up a single log trail that records every action twice: once permanently in an S3 bucket, and once in a CloudWatch log group where it can be viewed and searched right away.

Where to check: CloudTrail → Trails → adi-1-1-support-assistant-trail (status: Logging).

Why it matters: Covers two different needs with one trail — a permanent, hard-to-tamper-with record of every action (in S3), and logs that can be searched right away without any extra setup (in CloudWatch).

Minor · Tried to use a permission too soon after creating it

What happened: Creating the trail right after creating the permission role it needed failed with an invalid-role error.

Fix: waited about 15 seconds and tried again — it worked. Brand-new permissions just need a short moment to fully apply across AWS's systems.

Good to know

A brand-new IAM role can take a few seconds before other AWS services are able to use it — even though the console shows it as already created. If something fails right after creating a role, waiting a bit and retrying is usually the right fix, not rewriting the permissions themselves.

8

Separate access for editing prompts

adi-1-1-prompt-editor-role

What was built: A permission set that's allowed to write and update saved prompts, but is specifically blocked from ever running the AI model itself — and has no other access to anything else in this project.

Where to check: IAM → Roles → adi-1-1-prompt-editor-role.

Why it matters: Keeps "who's allowed to change the instructions" separate from "who's allowed to run them" — the kind of separation a real approval process would depend on, so one person changing a prompt can't also secretly run up AI usage costs, and vice versa.

Good to know · how this was checked

Actually logging in as this role to test it would have meant creating real, temporary AWS credentials — a security risk not worth taking just to check a permission set. Instead, a built-in AWS tool was used that simulates what a role is allowed to do, without ever creating real credentials. It confirmed: editing prompts — allowed; running the AI model — blocked; everything else — blocked too. That's a safer way to test permissions than actually using them.

Phase 3

Guardrails

Add a safety check that works separately from the prompt, so it still catches problems even if someone tries to trick the AI.

9

Safety guardrail

adi-1-1-support-assistant-guardrail

In plain terms: A Bedrock Guardrail is a separate safety check that sits between the customer and the AI model. It can block certain topics, certain kinds of sensitive information, and even attempts to trick the AI into ignoring its instructions — checking the conversation independently of whatever the prompt itself says.

What was built: Built a guardrail that blocks three risky topics (sharing login credentials, promising unreleased AWS features, and talking about competitors), blocks sensitive data like AWS access keys and passwords, filters out harmful content, and specifically catches attempts to trick the AI into ignoring its own rules. Tested it against all 4 of these cases and it worked as expected every time.

Where to check: Bedrock → Guardrails → adi-1-1-support-assistant-guardrail.

Why it matters: This safety check runs completely separately from the prompt's own instructions. That means it still works even if someone finds a clever way to trick the AI into ignoring what it was told to do — the guardrail doesn't rely on the AI "listening" to stay safe.

Good to know

Bedrock already knows how to recognize things like AWS access keys and secret keys automatically — no custom setup needed for that specific case. And blocking a topic like "talking about competitors" works by understanding the meaning of what's being said, not just matching exact words, which is why it also catches someone rephrasing the same idea in different words.

Phase 4

Orchestration

Wire everything together: two Lambda functions and a flowchart that makes every decision visible and easy to review.

10

Lambda: figure out what the customer needs

adi-1-1-detect-intent

In plain terms: Amazon Comprehend is an AWS service that reads text and tells you things about it — like whether it sounds positive, negative, or neutral. That's called "sentiment," and it's basically an automatic mood-reader for written text.

What was built: A Lambda function that reads a customer's message and figures out: the general topic, any server ID mentioned in the text, how confident it is about what's actually being asked, the customer's mood (using Amazon Comprehend), and whether the situation looks serious enough to flag for a human.

Where to check: Lambda → adi-1-1-detect-intent → Monitor tab.

Why it matters: Turns a raw, messy customer message into clear, structured information the decision flowchart in Step 12 can act on — that's exactly what decides whether to diagnose the problem right away, ask a follow-up question, or hand off to a person.

Error 4 · Mood alone triggered too many handoffs

What happened: A completely normal troubleshooting message ("won't start, stuck in pending") scored as 96% negative in mood, and wrongly triggered a handoff to a human — even though it was just an ordinary technical complaint, not an angry customer.

Fix: stopped using mood by itself as a trigger for handing off to a human. Mood is still measured and saved for later use, but handoffs are now only triggered by specific keywords or billing-related issues. Tested again afterward: the same message no longer triggers a handoff, while a genuinely angry billing complaint still correctly does.

Good to know

Mood-detection tools like Comprehend are built for everyday text, and ordinary technical complaints often score as surprisingly negative — that's just how frustrated troubleshooting language reads. Don't use mood by itself to trigger something important like a handoff to a human; pair it with a clearer, more specific signal, like exact keywords.

11

Lambda: ask the model and save the answer

adi-1-1-invoke-model

What was built: A Lambda function that picks the right saved prompt for the situation, calls Bedrock with the Step 9 safety guardrail turned on, checks that the reply actually looks like a proper answer, and saves both sides of the conversation to the Step 3 database. This step had the most real problems to work through — three in a row.

Where to check: Lambda → adi-1-1-invoke-model → Monitor tab.

Why it matters: This is the one place where the saved prompt, the safety guardrail, and conversation memory all come together in a single call — it's the actual "answer the question" step of the whole system.

Error 5 · Wrong permission type for saved prompts

What happened: Kept getting "not authorized" errors, even after granting full model-calling permission in every way that seemed reasonable.

Fix: it turns out calling a model through a saved prompt (instead of a plain model ID) needs two different, more specific permissions — Converse and RenderPrompt — not the general model-calling permission that was tried first. Once those exact two were granted, it worked.

Error 6 · Request landed in the wrong AWS region

What happened: After fixing Error 5, a new error appeared — the request got denied because it landed in a different AWS region than expected.

Fix: the special cross-region model ID from Step 1 can send requests to more than one region behind the scenes, depending on where there's capacity. The permission had only allowed one specific region, so it was updated to allow any region.

Error 7 · Guardrail blocked a perfectly normal question

What happened: With permissions finally sorted out, a completely harmless question ("instance stuck in pending for 10 minutes") got blocked by the safety guardrail from Step 9.

Fix: the guardrail's strictest setting was too sensitive, and mistook a normal, clearly-structured question for a trick attempt. Turning the strictness down one notch fixed it — real questions now get through, while genuine trick attempts still get caught.

Good to know

Some AWS permissions are tied to very specific actions — a broad "allow everything" permission doesn't always cover a narrower, differently-named action, so it's worth checking the exact permission name an error asks for. Also, a guardrail's strictness setting works like a dial, not an on/off switch: turning it up catches more trick attempts, but it also blocks more real, harmless questions — it's worth testing and tuning, not just leaving it on the strictest default.

12

The decision flowchart

adi-1-1-support-assistant-sm

In plain terms: AWS Step Functions lets you build a visual flowchart out of your application's steps — each box is a task or a decision, and you can watch a real request move through the boxes one at a time. It's a way of making "what happens next, and why" visible and reviewable, instead of buried inside code.

What was built: The full flowchart: get the customer's question → figure out what's needed (Step 10) → decide what to do (hand off, ask more, or diagnose) → ask the model for an answer (Step 11) → check that answer looks right → reply. If anything fails along the way, it automatically falls back to a simple apology message instead of crashing or showing a raw error. This worked on the first try — all three decision paths were tested, and the actual steps taken were double-checked, not just the final answer shown.

Where to check: Step Functions → adi-1-1-support-assistant-sm → Executions (shows a visual map of exactly what happened in each run).

Why it matters: Every decision the system makes is a visible, named step with a clear reason attached — easy to review after the fact, instead of having to guess why the AI ended up doing what it did.

Good to know

Step Functions comes in two speeds: "Standard" (a bit slower, but keeps a full visual history of every single run, forever) and "Express" (faster and cheaper, but with much less detail kept afterward). Standard was picked here specifically because being able to see exactly what happened in each run — for review and debugging — mattered more than raw speed for this use case.

Phase 5

QA & Monitoring

Build automatic tests, plus a dashboard and alerts that catch problems early — before a customer notices.

13

Test suite

adi-1-1-validate-output · adi-1-1-test-harness-sm

What was built: A Lambda function that checks whether a given response actually met a set of expected criteria, plus a second flowchart that automatically runs 5 built-in test questions through the entire assistant and checks each result against what it should have done.

Where to check: Step Functions → adi-1-1-test-harness-sm → latest run's output.

Why it matters: Covers testing tricky cases like angry customers and vague requests, plus two extra security-style tests (someone trying to trick the AI, and someone asking for login credentials) that are specifically supposed to fail safely, not succeed. Result: 5 out of 5 tests passing, including confirming that the two risky test cases correctly got blocked by the guardrail instead of slipping through.

Error 8 · Missing permission for a nested test run

What happened: Creating the test flowchart failed right away with a permission error.

Fix: a flowchart that runs a second flowchart and waits for its result needs one extra, specific permission to manage a background event rule that AWS uses internally for that waiting behavior. Adding that one permission fixed it.

Error 9 · Tried to convert data that was already converted

What happened: The first full test run failed with a data-format error.

Fix: checked the actual raw details of the run and found the nested result had already come back in the right format — it didn't need converting at all. Removing that unnecessary conversion step fixed it.

Good to know

A flowchart that runs another flowchart and waits for its result needs a specific extra permission — easy to forget, since it's not obvious from the plain "run this" permission alone. And when a nested result's format is unclear, it's worth checking the actual run details directly, rather than guessing based on general documentation that might describe a slightly different situation.

14

Dashboard and alerts

adi-1-1-alerts · 5 alarms · adi-1-1-support-assistant-dashboard

What was built: Added extra logging that specifically tracks bad answers, guardrail blocks, and response speed. Built an alert topic (left with no actual email or text message hooked up yet, since that's a decision for whoever owns the account, not something to decide automatically), 5 alarms watching for specific problems, and one dashboard showing all of it together in one place.

Where to check: CloudWatch → Dashboards → adi-1-1-support-assistant-dashboard; CloudWatch → Alarms (search for adi-1-1).

Why it matters: Catches problems automatically instead of relying on someone happening to notice by hand. Two of these alarms directly cover the same kinds of bugs found in Steps 4 and 7 above — if something similar ever happens again, it triggers an alert right away instead of quietly going unnoticed.

Error 10 · A dashboard feature doesn't work in alarms

What happened: Tried to build an alarm that automatically adds up a number across several categories — it failed with "not supported on Metric Alarms."

Fix: that automatic-adding shortcut only works when building dashboards, not when building alarms. Replaced it with three separate entries added together by hand, one per category. Also had to add a missing time-window setting to one part of the alarm before it would work.

Good to know

Adding custom tracking to a Lambda function needs no extra permissions at all — it's just structured log lines, and the function can already write logs by default. Also worth knowing: a feature that works fine on a dashboard doesn't always work the same way inside an alarm — alarms need a fixed, clearly defined list of exactly what to measure, with no automatic shortcuts.
