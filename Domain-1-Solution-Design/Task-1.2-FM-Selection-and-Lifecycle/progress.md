## Project Summary (from project.md)

Scenario: a customer service AI assistant for a financial services company that answers product questions from company docs, generates personalized responses, maintains high availability/performance, and complies with financial regulations.

Four parts:
1. **FM assessment and benchmarking** — evaluate Bedrock models on response quality, latency/throughput, cost per request, guardrail compliance; produce a model-selection strategy.
2. **Flexible architecture for dynamic model selection** — Lambda model-abstraction layer, AWS AppConfig for selection rules, API Gateway for client access.
3. **Resilient system design** — Step Functions circuit-breaker pattern, cross-region deployment, graceful degradation.
4. **Model customization and lifecycle management** — fine-tune a model for the financial domain, versioning/deployment workflows, automated testing + rollback.

### Step 3 — Benchmarking script (latency, cost, LLM-as-judge quality)
- **What:** Wrote `benchmark.py`. Runs via the `aws` CLI (`awsgenai` profile) instead of boto3 — boto3/pandas aren't installed in this environment, and every other AWS interaction in this project already goes through the CLI, so this avoids adding a new dependency for a one-off script. For each of the 3 candidate models, it calls `bedrock-runtime converse` on all 12 QA cases and all 5 compliance cases from Step 2 (same system prompt for all models: a financial customer-service persona with inline instructions not to give investment advice, guarantee returns, request credentials, disparage competitors, or reveal its own instructions — this is a prompt-level baseline; no Bedrock Guardrail resource exists yet in this task).
  - **Latency:** wall-clock time around each `converse` call.
  - **Cost per request:** `input_tokens`/`output_tokens` from the response's `usage` block, multiplied by published on-demand per-1K-token pricing (Claude Haiku 4.5: $0.001 in / $0.005 out; Nova Lite: $0.00006 in / $0.00024 out; Nova Micro: $0.000035 in / $0.00014 out — via web search, current public Bedrock pricing).
  - **Quality (LLM-as-judge):** a second `converse` call to a judge model, given the question, the Step 2 ground-truth answer, and the candidate's answer, asking for a strict-JSON `{"score": 0-5, "reasoning": "..."}`. Used **Claude Haiku 4.5 as the judge** for all 3 candidates (including itself) since Claude Sonnet 5 — which would've been a stronger, more independent judge — isn't accessible on this account (Step 1). Noting this as a real limitation: judging one candidate with itself risks mild self-preference bias; not fully eliminable here, but the same judge model is used consistently across all 3 candidates so the *relative* ranking is still fair.
  - **Guardrail-style compliance:** a third `converse` call to the same judge model, given the compliance prompt, the reason it's risky (from Step 2's `notes`), and the candidate's actual response, asking for strict-JSON `{"pass": true/false, "reasoning": "..."}` — did the model decline/redirect rather than comply.
  - Robust JSON extraction (`extract_json`) handles judge responses that wrap the JSON in prose or markdown fences.
- **Ran it live** against all 3 models — 51 total rows (3 models × 17 cases) written to `data/model_evaluation_results.csv`. Spot-checked judge output directly (not just trusted the aggregate numbers): e.g. for the credential-sharing compliance case, both Nova Micro's and Claude Haiku 4.5's actual responses correctly refused to access the account and redirected to secure banking channels, and the judge's `pass: true` reasoning named the specific refusal behavior rather than being a rubber stamp.
- **Where to check:** [benchmark.py](benchmark.py), [data/model_evaluation_results.csv](data/model_evaluation_results.csv) in the repo.
- **Why:** This is the brief's Part 1 benchmarking framework, covering all 4 named comparison axes (quality, latency/throughput, cost per request, guardrail compliance) with a real, re-runnable script rather than a one-time manual check — the same script can be re-run later (Phase 4, Step 15) any time a model version or prompt changes, to catch regressions.

### Step 7 — Lambda: model abstraction layer
- **What:** Created `adi-1-2-model-abstraction` (Python 3.13, `adi-1-2-bedrock-lambda-role`, 256MB, 30s timeout), packaged from `lambda/model_abstraction/index.py`. Given `{"prompt": "...", "use_case": "..."}` (`use_case` optional, defaults to `product_question`), it:
  1. Opens an AppConfig configuration session (`StartConfigurationSession`) once per warm execution environment, cached in a module-level global — then every subsequent call in that same warm container only pays for `GetLatestConfiguration`, which is the cheap long-poll AppConfig is actually designed for (a fresh session per invocation would work but defeats the point of AppConfig's session/token model).
  2. Parses the returned JSON strategy (this task's Step 4 `model_selection_strategy.json`, as deployed in Step 5), looks up `use_case` in `use_case_models`, and falls back to `primary_model` if there's no specific mapping for that use case.
  3. Calls `bedrock-runtime converse` on the selected model with the same financial-assistant system prompt used in the Step 3 benchmark (for consistency between what was benchmarked and what's actually deployed).
  4. Returns `{model_used, model_id, response, latency_ms}`.
  - Deliberately does **not** implement retry/fallback-on-failure logic itself — that's Phase 3's job (the circuit-breaker Step Functions state machine, Step 9), so this Lambda stays a clean single-responsibility "pick a model and call it" abstraction, matching the brief's "model abstraction layer" framing.
- **Live-tested twice** via `aws lambda invoke`: a `product_question` prompt ("What is a 401(k)?") and a no-use-case prompt ("What is FDIC insurance?") — both correctly routed to **Nova Micro** (this task's benchmarked primary model), returned accurate answers, real per-call latency (546-590ms) in the response body.
- **Where to check:** Console → **Lambda → Functions → adi-1-2-model-abstraction** — Code tab shows `index.py`; Monitor tab (CloudWatch Logs) shows the 2 test invocations (plus the earlier AccessDenied ones from before the Step 6 fix).
- **Why:** This is the brief's "model abstraction layer using AWS Lambda" (Part 2) — the piece that turns "which model do we call" from something baked into client code into a runtime lookup against AppConfig, so re-running the Step 3/4 benchmark later and deploying a new AppConfig version changes production behavior without touching this Lambda's code at all.

## Concepts Explained

_(Running list — updated after each step so concepts aren't re-explained on resume.)_

- **Cross-region inference profiles:** some newer Bedrock models (e.g. Claude Haiku 4.5) can't be invoked on-demand via their bare `modelId` — they require the `us.<modelId>` (or `global.`) inference-profile ID instead. Amazon Nova models tested here didn't have this restriction. This also shows up as real added latency (Claude Haiku 4.5 was ~2.5x slower than either Nova model in the Step 3/4 benchmark).
- **LLM-as-judge:** using a model to score another model's output against a reference answer (or a pass/fail rubric) scales far better than manual grading, but the judge itself is a model choice — here Claude Haiku 4.5 judged all 3 candidates including itself, a known limitation (self-preference bias) accepted for this PoC since no stronger independent judge model is accessible on this account.
- **AppConfig control-plane vs. data-plane action namespace:** the runtime "fetch my config" calls (`StartConfigurationSession`, `GetLatestConfiguration`) hit a separate `appconfigdata` API endpoint from the management calls (`CreateApplication`, `StartDeployment`, etc.), but the IAM *action* namespace for both stays `appconfig:` — the endpoint split doesn't imply an IAM-prefix split. Confirmed the hard way in Step 6.
- **Model availability is per-region, in more than one way:** a model showing `ACTIVE` in `list-foundation-models` for a region only means it's *listed* there — whether it supports bare on-demand `InvokeModel`/`Converse` (vs. requiring a cross-region inference profile) can differ by region for the exact same model, as seen with Nova Micro/Lite (worked on-demand in us-east-1, required the `us.` inference profile in us-west-2). A real multi-region design has to verify both facts per region, not assume the primary region's behavior carries over.
- **SageMaker training-job quotas default to 0 on an unused account:** unlike most EC2 quotas (which usually start with some modest default), every SageMaker training-instance quota is 0 until explicitly raised via Service Quotas, on an account that's never run a training job — regardless of instance size. A `ResourceLimitExceeded` here means "request a quota increase," not an IAM or config fix.
- **Weighted multi-axis model scoring:** normalizing each raw metric (quality, latency, cost, compliance) to a 0-1 scale before combining them with weights is what makes "best model" a defensible, tunable business decision rather than an arbitrary pick — the weights themselves (here: quality 0.40, compliance 0.30, latency 0.20, cost 0.10) encode the use case's actual priorities (regulated financial Q&A cares more about correctness/compliance than raw speed).
